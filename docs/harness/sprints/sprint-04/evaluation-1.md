## 改善提案（合格判定には影響しないが推奨）

### m1（Minor）: 要約のタイルの数値が左揃え
- 契約の第4章と C11-1 は「要約（数値は右揃え、3桁区切り）」としている。実際は、タイルの中で左揃えになっている。3桁区切りは付いている（`4,000 銘柄`）。
- 数値が1つだけのタイルでは、左揃えでも読みにくくない。桁をそろえる目的は、表（右揃え・tabular）で果たされている。そのため不合格にはしない。契約の文言とそろえるか、契約の側を直すとよい。

### m2（Minor）: 前後に空白のある入力で、URL が正規化されない
- 再現: 「銘柄コード」に ` 99991 ` を入れて「確認」を押すと、URL は `/imports?code=+99991+` になる（カードは正しく表示され、入力欄も `99991` に正規化される）。
- 契約の C1-2 は「URL が `/imports?code=<コード>` になり」としている。共有やブックマークのために、正規化したコードで遷移し直す（またはリダイレクトする）とよい。

### m3（Minor）: 確認カードの項目名が折り返す
- 1280px のカードでも、「データ期間の開始日」が「データ期間の開始 / 日」に折り返す。「データ期間開始以前から上場（9年 / 超）」も折り返す。項目名の列が 7.5rem 固定のため（自己評価にも記載がある）。
- 崩れではないが、項目名の列を `max-content` にするか、項目名を短くするとよい。

### m4（改善）: `stock_listing_ages` は、全銘柄で plpgsql 関数を行ごとに評価する
- 銘柄を 4,000 件、初出日を 4,000 件入れて測った（後で削除した）。
  - 「初出日の新しい銘柄」の並べ替えのクエリ: 約 310ms
  - `/imports` の表示: 約 420ms
  - 今の規模なら許容できる。
- Sprint 6 の絞り込み（`listing_years_exact <= X`）と並べ替えは、同じビューを全件で評価する。財務の条件と組み合わせると、さらに重くなる可能性がある。
- 提案: `listing_years_between` を SQL 関数（インライン化できる形）にする。または、基準日ごとに結果を持つ。Sprint 6 の契約で性能の目標を決めておくとよい。

### m5（注記）: dev の E2E 中に、サーバーのログに `Error: The destination stream closed early.` が2回出た
- `cross_origin` の画面の文言のテスト（応答を差し替えたうえで、ページを閉じる）の直後に出た。ブラウザ側のエラーは無く、テストも成功した。ストリーミング中に接続が閉じられたときの dev の出力とみられる。実害は見つからなかった。
- 同じく、評価のスクリプトでスクリーンショットを撮った直後に、一度だけハイドレーションの不一致（入力欄の `style="caret-color: transparent"`）が出た。これは Playwright のスクリーンショット（キャレットを隠す処理）がハイドレーションの前に入ったためで、アプリの問題ではない。撮影を `networkidle` の後にすると、0件になった。

### その他
- 自己評価の既知の問題の妥当性は次のとおり。
  - ネイティブのラジオへの変更: キーボードの操作（Tab でグループに入り、矢印で選択が変わる）、名前、フォーカスの枠が正しく動いた。ダークでの未選択の枠のコントラストは、実測で約 4.6:1。妥当と判断した。
  - `allowedDevOrigins: ["127.0.0.1"]`: 開発時にだけ効く設定で、本番の同一オリジンの確認には関係しない。妥当と判断した。
  - 既存の E2E の2件の変更: Cron の `runs` の要素数を2に直したもの。同時要求のテストは「勝った側の行だけ」を厳密に比べている。緩めていない。ただし、「Cron の銘柄マスタが終わった直後に手動が始まり、Cron の株価が `skipped` になる」という競合は、このテストの対象外（単体テストで確認済み）。
- 取り込み状況の画面の「J-Quants: 最終成功」は、株価の成功の実行（保存0件でも）で更新される。仕様上の問題は無い。
