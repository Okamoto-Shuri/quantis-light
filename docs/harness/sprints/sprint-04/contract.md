# Sprint 04 契約: F4 株価の初出日と上場年数

## 1. 対象機能

F4 株価の初出日の取り込みと上場年数の推定。J-Quants の株価四本値（日足）から、銘柄ごとに「株価データの初出日」を求めて保存する。保存した初出日と基準日（最新の株価の取り込み日）から、推定上場年数を算出する。取り込みの対象に「株価（`daily_quotes`）」を加え、Sprint 3 の取り込み基盤（実行履歴、二重実行の防止、応答の無くなった実行の後片付け）の上で動かす。起動経路は、Sprint 3 と同じく手動（取り込み状況の画面）と Cron（日次）の2つ。

保存した初出日と推定上場年数は、取り込み状況の画面の新しい区画「株価の初出日と推定上場年数」と `GET /api/stocks` で確認できる。スクリーニング（Sprint 6）と銘柄詳細（Sprint 7）は、ここで作る算出（DB の1か所）をそのまま使う。

あわせて、Sprint 3 の評価（`sprint-03/evaluation-1.md`）の改善提案のうち、次の2点をこのスプリントで直す（扱わない M3〜M5 は第9章）。
- **M2**: 正しいシークレット付きの `HEAD /api/cron/daily` でも取り込みが走る。Cron が株価も取り込むようになり、1回の実行が重くなるので、このスプリントで直す。
- **M1**: 正規でないホスト名（`http://127.0.0.1:3100` など）で開くと、手動取り込みが 403 になり、「ログインし直してください」と誤った案内が出る。このスプリントで手動取り込みの画面と API に手を入れるので、あわせて直す。ログアウト（`POST /auth/signout`）も同じ判定を使っているので、共通の判定にそろえる。

### 仕様書の受け入れ基準（引用）

- AC4.1 （キーあり環境）取り込み後、各銘柄に株価データの初出日と推定上場年数が保存され、取り込み状況画面にこの処理の実行結果が表示される。
- AC4.2 データベースに初出日が「基準日の3年前」の銘柄を投入すると、推定上場年数は約3.0年と表示される。
- AC4.3 初出日が取得可能なデータ期間の開始日と同じ銘柄は「データ期間開始以前から上場（N年超）」と表示され、年数が特定できないことがわかる。
- AC4.4 2回目以降の取り込みでは、既に初出日が確定している銘柄の初出日は変わらない（新規上場銘柄だけが追加される）。

用語定義（仕様書「用語と算出ルール」より）: 上場年数（推定）は、保存済みの株価データで、その銘柄が最初に登場した日（初出日）から基準日（最新の取り込み日）までの年数。初出日が取得可能なデータ期間の開始日と同じ場合は、それより前から上場していた可能性があるため「データ期間開始以前から上場（N年超）」として扱い、「上場X年以内」の条件は満たさない。画面には「株価データの初出日からの推定」であることを明記する。

## 2. 仕様上の論点と、このスプリントでの解釈

仕様を変えずに、次のように解釈する。評価者は、この解釈が妥当かも判断してほしい。

1. **使う API**
   J-Quants API V2 の株価四本値 `GET https://api.jquants.com/v2/equities/bars/daily`（公式: https://jpx-jquants.com/ja/spec/eq-bars-daily）を、Sprint 3 と同じ `x-api-key` ヘッダーで呼ぶ。`code` か `date` のどちらかが必須で、`from`／`to` で期間を絞れる。応答は `{"data":[...], "pagination_key": "..."}` で、`pagination_key` があれば次のページを取る。初出日の判定に使うのは、各行の `Date` と `Code` だけ（四本値そのものは保存しない）。公式ドキュメントによると、売買停止の日や売買の無い日も行はあり、四本値と出来高が null になる。そのため、行があれば、その日に上場していたものとみなす（終値の有無は問わない）。

2. **Standard プランの取得可能期間と「上場5年以内」の判定への影響（公式ドキュメントで確認）**
   - 公式の「契約ごとに利用可能なAPIとデータ格納期間」（https://jpx-jquants.com/ja/spec/data-spec）では、株価四本値を取得できる期間は次のとおり。Free「12週間前〜2年12週間前まで」、Light「5年前まで」、**Standard「10年前まで」**、Premium「20年前まで」（Premium の起点は 2008/5/7）。「年前まで」は、今日から遡る**移動する期間**である。
   - したがって、Standard プランで見える株価は、今日から約10年前以降に限られる。約10年より前から上場している銘柄は、どれも初出日が「データ期間の開始日」になり、本当の上場日はわからない。
   - **「上場5年以内」（既定の閾値）への影響は無い**。上場5年以内の銘柄は、上場日がデータ期間（約10年）の中にあるので、初出日は実際の最初の取引日になる。閾値を 10 年近くまで上げた場合だけ、データ期間の開始日に張り付いた銘柄が「データ期間開始以前から上場（N年超）」になり、条件を満たさない側に倒れる（仕様どおり）。閾値の上限を 10 年未満にするかどうかは、スクリーニング画面の Sprint 6 で決める。
   - 期間が移動するので、同じ銘柄でも、取り込む日によって「データ期間の開始日」は変わる。そこで、初出日を確定したときのデータ期間の開始日を、銘柄ごとに一緒に保存する（第6章の `data_start_date`）。いったん「データ期間開始以前から上場」と確定した銘柄は、その後も変わらない。基準日が進むと、N は増える。
   - Light プランのキー（5年分）で動かすと、5年より前から上場している銘柄がすべて「データ期間開始以前から上場（5年超）」になる。「上場5年以内」の判定は正しく外れる側になるが、この契約は Standard プランを前提とし、期間は 10 年の定数にする（仕様の制約が Standard プランのため。環境変数にはしない）。

3. **データ期間の開始日の求め方**
   公式ドキュメントには、期間の開始日を返す API は無い。そこで、取り込みの開始時に次の手順で求める。
   - 実行の開始日（日本時間）を D とし、S = D の10年前の翌日（暦で。2月29日は2月28日にする）とする。「10年前まで」の境目の解釈の違いで期間外にならないよう、1日だけ内側から始める。
   - `GET /equities/bars/daily?date=S` から1日ずつ進めて、最大 14 日分を試す。最初に行が1件以上返った日を、この実行の**データ期間の開始日 W**とする。
   - 探索の各日の応答は、次の表で扱う（公式の response-status https://jpx-jquants.com/ja/spec/response-status に基づく）。

     | 応答 | 扱い | 根拠 |
     |---|---|---|
     | 200 で行が1件以上 | その日を W にする | |
     | 200 で行0件 | 休場日として次の日へ | 公式:「該当するデータが存在しない場合もエラーにはならず、200 で data に空配列」 |
     | 210 | 次の日へ | 公式:「210 No Content (Partial): 取得可能時間外…等の理由で、データが取得できませんでした」 |
     | 400 | 期間外の日付への応答とみなして次の日へ | 期間外の日付の応答は公式に記載が無いため |
     | 403 で、本文の `message` がキーの無効（`The incoming api key is invalid or expired.`）またはキーの欠如（`The api key is required.`） | **すぐに失敗**（要求は1回で終わる）。Sprint 3 の 403 の文言 | 実 API で確認済みの本文（契約レビューの実測）。キーの確認はパラメータの検証より先に行われる |
     | 上記以外の 403（本文が読めない場合を含む） | 契約プランの範囲外（期間外）への応答とみなして次の日へ | 公式の 403 の原因の2番目「契約プランの範囲外のデータ・エンドポイントへのアクセス」 |
     | 401、429、そのほかの状態コード、接続できない、形式の違い | 失敗（Sprint 3 の表の文言） | |

   - 14 日のうちに行のある日が無ければ、「株価データの取得可能期間の開始日を特定できませんでした（14 日分を試し、最後の応答は HTTP 403）」（数字は最後に受けた状態コード。行0件の 200 なら `HTTP 200（0件）`）で失敗にする。`details.dataStartProbe` に、試した日ごとの状態コードと行数（本文は入れない）を残す。キーありの環境で、期間の境界の応答がわかるようにするため。
   - **この扱いにする理由**: 期間外の日付に 403 が返る場合に、有効なキーでも「キーが無効」で毎日失敗し続けることを防ぐ。一方、無効なキーは、実測した本文で見分けて最初の1回の要求で失敗が確定する。本文の文言が将来変わった場合でも、無効なキーは 14 回の要求の後に「開始日を特定できませんでした（…最後の応答は HTTP 403）」で失敗になり、無言で成功することは無い（その場合の文言の不正確さは許容する）。
   - 本文の `message` は分類にだけ使い、実行履歴やログには出さない（市場データではないが、Sprint 3 の方針どおり応答の本文は記録しない）。
   - 取引日カレンダー API（`/v2/markets/calendar`）で最初の営業日を求める方法も検討したが、期間外の応答の扱いは同じく必要で、呼び出しは数回しか減らないため、使わない。
   - W の日の全銘柄の行（ページ送りも含めてすべて）に現れるコードは、W の時点で上場していた。これらの銘柄は、**初出日 = W、データ期間の開始日 = W**（「データ期間開始以前から上場」）として保存する。仕様の「初出日が取得可能なデータ期間の開始日と同じ」を、そのまま「`first_price_date = data_start_date`」で表す。
   - W の行に現れない銘柄は、W より後に上場した。この銘柄は `GET /equities/bars/daily?code=<コード>&from=W` をページ送りも含めてすべて取得し、最も古い `Date` を初出日にする（並び順は仮定しない。公式の pagination にも並び順の保証は無い）。データ期間の開始日は W にする。初出日は W より後になる。
   - コード別の取得の応答は、次のように扱う。200 で行0件と **210** は「株価データなし」（`noPriceData`。失敗には数えない）。キーの無効・欠如の本文の 403、401、429 は、その実行を打ち切る（第5章）。それ以外の 403、400、500 などの状態コード、形式の違いは、その銘柄だけを「取得に失敗」（`failed`）に数えて次の銘柄に進む。
   - この方法だと、Standard プランの全銘柄の初回の取り込みでの API 呼び出しは、W の日の一覧（数回）と、約10年以内に上場した銘柄の数（約 1,000）になる。全銘柄を1つずつ取得する（約 3,800 回）より少ない。

4. **初出日の限界（推定であることの理由）**
   初出日は、J-Quants の株価データに東証の銘柄として最初に現れた日である。次の場合、実際の上場日（または企業の歴史）と一致しない。画面の注記で「株価データの初出日からの推定」と明記し、これ以上の補正はしない（仕様の範囲）。
   - 他の取引所（名証・札証・福証の単独上場）や TOKYO PRO MARKET から東証の市場に移った銘柄
   - 株式移転による持株会社化、合併、コードの変更などで、新しいコードで上場し直した銘柄
   - J-Quants の保存期間の外の上場日（第2章の2）
   - 銘柄コードの再利用。上場廃止の後に同じコードが別の会社に割り当てられると、`code=X&from=W` に前の会社の行が混ざって初出日が古くなる（または W の一覧に出て「データ期間開始以前から上場」になる）。J-Quants の株価四本値は、保存期間内の上場廃止銘柄も含むため起こりうる

5. **基準日**
   仕様の「基準日（最新の取り込み日）」を、**`target = 'daily_quotes'` で結果が「成功」または「一部失敗」の実行のうち、最も新しい終了日時の日付（日本時間）**とする。株価の取り込みの実績が1件も無いときは、基準日は「なし」とし、推定上場年数は表示しない（今日の日付で代用しない）。初出日の行を直接投入して確かめるときは、評価者が `daily_quotes` の成功の実行の行も投入する（第6章の投入例）。

6. **推定上場年数の算出**
   - 暦の年で数える。初出日に n 年を足した日が基準日以下になる最大の整数を n とし、端数は「初出日＋n 年」から基準日までの日数 ÷「初出日＋n 年」から「初出日＋(n+1) 年」までの日数とする。年数 = n ＋端数（丸める前の値。以下「正確な年数」）。計算は `numeric` で行い、浮動小数点の誤差を入れない。
   - 表示は**小数点以下1桁に切り上げ**、「3.0年」の形にする（正確な年数がちょうど 3 なら 3.0 のまま）。
     - 理由: 小数点以下1桁までの閾値 X（5、4.5 など）に対して、「切り上げた表示 ≤ X」と「正確な年数 ≤ X」が必ず一致する。つまり「上場X年以内」の判定と、画面の数値を見比べた結果が食い違わない。切り捨てにすると、正確には 5 年を最大約 36 日超えた銘柄が「5.0年」と表示され、「5年以内」を満たさないのに表示上は満たしているように見える。
     - **Sprint 6 の絞り込みは、正確な年数（`listing_years_exact`）が閾値以下かどうかで判定する**。並べ替えも正確な年数で行う。上のとおり、閾値が小数点以下1桁までなら、表示の値で判定した結果と一致する（Sprint 6 の閾値の入力は小数点以下1桁までにする前提。Sprint 6 の契約で改めて確かめる）。
   - 例（基準日 2026-09-24）: 初出日 2023-09-24 → 3.0年（ちょうど3）。2023-09-25 → 3.0年（2.997…）。2023-09-23 → 3.1年（3.002…）。2021-09-24 → 5.0年（ちょうど5）。2021-09-25 → 5.0年（4.997…）。2021-09-23 → 5.1年（5.002…）。2016-09-27 → 10.0年（9.997…）。初出日＝基準日 → 0.0年。
   - うるう日: 初出日 2024-02-29 に3年を足すと 2027-02-28（Postgres の `date + interval` と同じ）。基準日 2027-02-28 → 3.0年、2027-03-01 → 3.1年、2027-02-27 → 3.0年（2.99…）。
   - 「データ期間開始以前から上場（N年超）」の N は、データ期間の開始日から基準日までの正確な年数の**整数部分**（切り上げない）。「N年超」が必ず正しい（実際に N 年以上のデータがあり、上場はそれより前）ようにするため。
     - W は「実行日の10年前の翌日」以降なので、取り込んだ当日の基準日から W までは10年に少し足りない。**取り込み直後の N は 9** で、基準日が W＋10年に達したとき（最大で約2週間後）に **10** になる。
   - 初出日が基準日より後になる行（基準日より後に取り込んだデータを投入した場合など）は、年数を 0.0年 と表示する（負の年数を出さない）。
   - 算出は DB の1か所（ビューまたは関数）で行い、画面と API の両方がそれを読む。Sprint 6 のスクリーニングの絞り込み（SQL）もそれを使う。

7. **一度確定した初出日は変えない（AC4.4）**
   - 初出日の行があるコードは、取り込みの対象にしない（API を呼ばない）。保存の関数も、既存の行を更新しない（`on conflict do nothing`）。
   - 毎日の取り込みでは、`public.stocks` にあって初出日の行が無い銘柄（新規上場で銘柄マスタに加わったもの、前回までに処理しきれなかったもの、株価がまだ無かったもの）だけを処理する。
   - 株価データが1行も無い銘柄（銘柄マスタには載ったが、まだ取引が始まっていない新規上場など）は、行を作らずに「未確定」のまま残し、次回の取り込みで再び試す。

8. **時間と呼び出し回数の制限（一部完了）**
   - 公式ドキュメント（https://jpx-jquants.com/ja/spec/rate-limits）では、Standard プランの上限は 1 分あたり 120 回で、429 が返ったら 1 分以上待つこと、大きく超えると約5分間すべてが拒否されることがある、とされている。株価の取り込みでは、J-Quants への要求の間隔を 600 ミリ秒以上あける（1 分あたり 100 回以下）。
   - Vercel の関数は 300 秒で打ち切られる（Sprint 3 の `maxDuration = 300`）。株価の取り込みは、ルートの処理の開始から **210 秒**を過ぎたら、新しい要求を始めない（1回の要求のタイムアウト 30 秒と保存の時間を足しても 300 秒に収まる）。Cron は、銘柄マスタの後に同じ要求の中で株価を取り込むので、210 秒はルートの開始から数える。
   - 時間内に処理しきれなかった銘柄は、次の実行で処理する（第2章の7のとおり、行の無い銘柄だけを処理するので、自然に続きから再開する）。このとき、実行は「一部失敗」（`partial`）で、残りの銘柄数を記録する。初回の取り込みは、1回（約 3.5 分で約 300 銘柄）では終わらず、数回（Cron なら数日、手動で続けて押せば数回）で終わる見込み。
   - 保存は銘柄の小さなまとまり（例: 50 銘柄）ごとに行い、そのたびに実行の処理件数（`processed_count`）を増やす。途中で関数が打ち切られても、保存済みの銘柄と件数は残る（その実行は、Sprint 3 の後片付けで 15 分後に「失敗」になるが、件数は残る）。
   - 429 の再試行（待ってから再試行）と、銘柄ごとの失敗の一覧は Sprint 11 で扱う。Sprint 4 では、429 を受けたらその実行を打ち切る（第5章）。

9. **実行の単位と Cron**
   - 手動取り込みは、Sprint 3 と同じく対象ごとに1回の実行にする。画面で対象（「銘柄マスタ」または「株価（初出日）」）を選んで「今すぐ取り込み」を押す。
   - Cron（`GET /api/cron/daily`）は、銘柄マスタ → 株価 の順に、それぞれ別の実行として動かす。銘柄マスタが失敗しても、株価の取り込みは保存済みの銘柄マスタで動かす（それぞれの失敗を、それぞれの行に記録する）。
   - 株価の取り込みは、`public.stocks` が0件のときは失敗にする（キーの確認の後）。

## 3. 起動方法

ポート 3000 は別のプロジェクトが使っているので、このスプリントの確認はすべて **3100 番**で行う（別のプロジェクトのサーバーは止めない）。

```bash
cd /Users/shuriokamoto/dev/quantis-light
pnpm install
pnpm db:start          # Docker が必要（未起動なら open -a Docker）
pnpm db:reset          # Sprint 4 のマイグレーションを含めて適用
pnpm env:local         # .env.local を生成（既存の JQUANTS_API_KEY などの行は保持する）
pnpm seed:users        # owner@quantis.local / Quantis-Owner-2026!（許可ユーザー）
CRON_SECRET=local-cron-secret-0123456789 pnpm dev -p 3100
# 本番相当: pnpm build && CRON_SECRET=local-cron-secret-0123456789 pnpm start -p 3100
```

- アプリ: http://localhost:3100
- Postgres: `postgresql://postgres:postgres@127.0.0.1:54322/postgres`
- 評価用ユーザー: `owner@quantis.local` / `Quantis-Owner-2026!`
- E2E: `E2E_PORT=3100 pnpm test:e2e`（3100 番でサーバーが動いていなければ自動で起動する。`playwright.config.ts` は Sprint 3 から `E2E_PORT` に対応している）
- 環境変数は Sprint 3 と同じ（`JQUANTS_API_KEY`、`EDINET_API_KEY`、`CRON_SECRET`）。Sprint 4 で追加する環境変数は無い。

## 4. 画面・エンドポイント・Cron の設定

### 画面

### エンドポイント

| メソッドとパス | 認証 | Sprint 4 の変更 |
|---|---|---|
| `POST /api/ingestion/runs` | `requireApiUser()` ＋同一オリジンの確認 | `target` に `daily_quotes` を受け付ける。同一オリジンの確認を直す（M1。下記） |

| `HEAD /api/cron/daily` | なし | **405**（M2。`Allow: GET`）。シークレットの有無にかかわらず取り込みを始めず、実行履歴も増えない |
| `GET /api/stocks` | `requireApiUser()` | 各行に初出日と推定上場年数の項目を加える。`?code=` で1銘柄に絞れる。`meta.referenceDate` を加える（C5） |
| `POST /auth/signout` | 同一オリジンの確認 | 確認の方法を手動取り込みと同じにする（M1） |

- **同一オリジンの確認（M1）**: `Origin` ヘッダーのホスト（ポートを含む）が、要求のホスト（`X-Forwarded-Host` があればその最初の値、無ければ `Host`）と一致するときだけ受け付ける。Next.js の Server Actions の CSRF 対策と同じ比べ方で、サーバーの既定のホスト名（`request.nextUrl.origin`）とは比べない。`Origin` が無い、`null`、URL として読めない、ホストが違う、はどれも 403 `{"error":"cross_origin"}`。判定は1つの関数にまとめ、手動取り込みとログアウトの両方で使う。
  - **リダイレクト先のホスト（R1）**: `GET /auth/signout` のリダイレクト先（`/login?...` や `next`）は、`request.nextUrl.origin`（サーバーの既定のホスト名）で作らず、相対パス（`Location: /login?...`）にする。`127.0.0.1:3100` で開いた利用者が `localhost:3100` に移され、Cookie の無い別のホストに着く、ということを起こさない。
  - 別のサイトのページからの `fetch` やフォームの送信は、`Host` を自分で書き換えられず（`X-Forwarded-Host` を付けると CORS のプリフライトになり、このアプリは許可しない）、`Origin` は攻撃者のオリジンになるので、拒否される。
- `GET /api/cron/daily` の応答: `{ "data": { "runs": [ {"runId":..,"target":"stock_master",...}, {"runId":..,"target":"daily_quotes",...} ] } }`。各要素は Sprint 3 と同じ形（`runId`、`target`、`status`、`processedCount`）。
  - 最初の対象（銘柄マスタ）を開始する時点で、ほかの実行が「実行中」なら、Sprint 3 と同じく 409 `{"error":"already_running"}` で、実行履歴は増えない。
  - 銘柄マスタの後、株価を開始する時点で、ほかの実行（手動など）が「実行中」になっていたら、株価は実行せず、200 で `"skipped": ["daily_quotes"]` を加えて返す。
- 応答はすべて `jsonNoStore`。

### Vercel Cron の設定

`vercel.json` は Sprint 3 のまま（`/api/cron/daily`、`0 11 * * *` = 毎日 20:00 JST）。J-Quants の株価四本値は、取引日の夕方に当日分が更新されるので、20:00 の実行で当日の新規上場銘柄の初日の株価まで取り込める。画面の「定期実行」の対象の表示だけを変える。

1. **開始**: Sprint 3 と同じ DB 関数で、実行を `target = 'daily_quotes'`、`status = 'running'` で記録する（二重実行の防止と後片付けも同じ）。
2. **キーの確認**: `JQUANTS_API_KEY` が未設定なら、外部 API を呼ばずに「失敗」、処理件数 0、「J-Quants の API キーが設定されていません」。
3. **銘柄マスタの確認**: `public.stocks` が0件なら、外部 API を呼ばずに「失敗」、「銘柄マスタが未取り込みのため、株価の初出日を取り込めません。先に銘柄マスタを取り込んでください」。
4. **対象の決定**: `public.stocks` にあって初出日の行が無いコード（コード順）。0件なら、外部 API を呼ばずに「成功」、処理件数 0、`details.pending = 0`。
5. **データ期間の開始日 W**: 第2章の3のとおり。W の日の一覧に現れた対象のコードを、`first_price_date = data_start_date = W` で保存する。
6. **残りの銘柄**: コード順に `code=<コード>&from=W` を取得し、最も古い `Date` を初出日にして保存する。行が0件なら保存せず「株価データなし」に数える。
7. **要求の間隔と時間**: J-Quants への要求は 600 ミリ秒以上あける。ルートの開始から 210 秒を過ぎたら、新しい要求を始めない（第2章の8）。
8. **保存**: 50 銘柄ごと（と最後）に、DB 関数で `on conflict do nothing` で保存し、実行の `processed_count` に新しく保存した行数を足す。実行がすでに「実行中」でなければ（後片付けで「失敗」にされていたら）、保存せずに処理をやめる。
9. **終了**: 結果とエラーメッセージは次のとおり。`processed_count` は、この実行で新しく保存した銘柄数。
   | 状況 | 結果 | エラーメッセージ |

   | すべての対象を処理した（株価データなしの銘柄があってもよい） | 成功 | なし |
   | 時間内に処理しきれなかった | 一部失敗 | `時間内に処理しきれなかったため、残り 812 銘柄は次回の取り込みで処理します` |
   | 一部の銘柄で、予期しない応答（500 など）や形式の違いがあった（その銘柄は飛ばして続ける） | 一部失敗 | `3 銘柄で株価を取得できませんでした。次回の取り込みで再試行します`（時間切れと重なったら、両方を「。」でつなぐ） |
   | コード別の取得で 200 の行0件、または 210 | （その銘柄を「株価データなし」に数えて続ける。結果には影響しない） | なし |
   | 途中で 429 を受けた（そこで打ち切る） | 保存済みが1件以上なら一部失敗、0件なら失敗 | Sprint 3 の 429 の文言。一部失敗のときは、続けて `残り N 銘柄は次回の取り込みで処理します` |
   | 401、またはキーの無効・欠如の本文の 403 を受けた（そこで打ち切る。第2章の3） | 同上 | Sprint 3 の文言（`J-Quants の API キーが無効か、契約プランでは利用できません（HTTP 403）`） |
   | W の日の一覧の取得に失敗した（接続できない、形式の違い、500 など） | 失敗 | Sprint 3 の表の文言 |
   | データ期間の開始日を特定できなかった（14 日すべてが行0件・210・400・キー以外の 403） | 失敗 | `株価データの取得可能期間の開始日を特定できませんでした（14 日分を試し、最後の応答は HTTP 403）` |
   | 保存に失敗した | 保存済みが1件以上なら一部失敗、0件なら失敗 | `株価の初出日の保存に失敗しました` |

10. **応答の形式の検証**: 1行ずつ、`Date`（`YYYY-MM-DD`）と `Code`（`^[0-9A-Z]{4,5}$`）だけを必須にする。四本値などのほかの項目は検証しない（null でも、欠けていてもよい）。`data` が配列でない、JSON でない、`Date`・`Code` が欠けている・形式が違う行がある場合は「J-Quants の応答の形式が想定と異なります」。コード別の取得で、応答に別のコードの行が混ざっていたら、形式の違いとして扱う。

## 8. 評価者への補足（キーの無い環境での合否判定）

- キーの無い環境では、C10 を除くすべての完了条件を確認できる。C10 は、有効な J-Quants Standard のキーがある場合だけ確認し、無い場合は「対象外（キーなし）」として合否に含めない。代わりに、C7（無効なキーで実 API に問い合わせ、403 の失敗が記録される）、C3・C4（算出と取り込みの単体テスト・DB 込みの結合テスト）、C1・C2・C5（DB に投入した行の表示と API）で、成功の経路を確かめる。
- ジェネレーターは J-Quants のキーを持っていない。株価四本値の応答の形は、公式ドキュメント（https://jpx-jquants.com/ja/spec/eq-bars-daily）の項目名に基づいてフィクスチャを作る。次の2点は公式ドキュメントに記載が無く、キーが無いと確かめられない。キーのある環境で違いが見つかった場合はバグとして扱い、修正する。
  - 休場日を `date=` で指定したときの応答（行0件の 200 を想定）
  - 取得可能期間の外の日付を指定したときの応答。公式の response-status の 403 の原因「契約プランの範囲外のデータへのアクセス」から、403 の可能性がある。400、行0件、210 の可能性もある。どれでも次の日に進む（キーの無効・欠如の本文の 403 だけは、すぐに失敗）
  - 210（公式では「取得可能時間外または存在しない銘柄コード等」。前場四本値など一部の API で使うとされ、株価四本値で返るかはわからない）。W の探索では次の日へ、コード別の取得では「株価データなし」として扱う
- 実際の株価（四本値）は、このスプリントでは保存しない。保存するのは初出日と、データ期間の開始日だけ。
