# Sprint 04 契約レビュー

## 判定: 修正依頼

契約の大部分は妥当です。スコープは仕様の AC4.1〜AC4.4 を削っていません。キーなしで判定できる完了条件（C1〜C9、C11、C12）もそろっています。第2章の解釈の多くも公式ドキュメントと合っています。
ただし、次の3点は、実運用（キーあり）で毎日の取り込みが止まる危険、Sprint 6 の「上場X年以内」の判定との食い違い、契約の記述の誤りにつながります。直してから実装に入ってください。

## 論点ごとの判断

### 1. Standard の遡及期間と「上場5年以内」への影響 — 妥当（ただし N の記述は誤り → 必須修正3）
- 上場5年以内の銘柄は、上場日が約10年の期間の中にあるので、初出日は実際の最初の取引日になる。この判断は正しい。
- `data_start_date` を銘柄ごとに保存し、「データ期間開始以前から上場」を `first_price_date = data_start_date` で表す方法も、仕様の定義をそのまま表しており妥当。
- Light プランでも判定が安全側（満たさない側）に倒れる、という分析も正しい。

### 2. W の探索（`date=` で S から最大14日） — 方針は妥当。応答の扱いが不足（必須修正1）
- 期間の開始日を返す API が無い以上、「期間の内側の日から順に試し、最初に行のある日を W とする」は合理的。S を1日内側にする配慮も適切（手動を 08:00 JST に実行した場合も、UTC との1日のずれを吸収できる）。
- 全銘柄を1つずつ取得せず、W の一覧に出た銘柄をまとめて確定する設計は、呼び出しの回数の点で良い。
- 問題は、期間外や境界の日付への応答として 400 しか想定していないこと。公式からは、403（契約の範囲外）や 210 の可能性が読み取れる。今の契約では、境界の解釈が1日でもずれて 403 が返ると、キーが有効でも「キーが無効か、契約プランでは利用できません（HTTP 403）」で失敗する。しかも毎日同じ日付から探すので、**毎日失敗し続ける**。キーなしの評価では見つからず、利用者のキーで初めて表に出る。

### 3. 基準日と年数の計算 — 基準日は妥当。端数の処理の根拠が逆（必須修正2）
- 基準日を「`daily_quotes` の成功・一部失敗の実行のうち、最新の終了日時の日本時間の日付」とする解釈は、仕様の「最新の取り込み日」に合う。今日の日付で代用しない点も良い。C1-6・C1-7 で判定できる。
- 暦年で数える計算（`初出日 + n 年`、うるう日の扱いは Postgres と同じ）は妥当で、例も正しい。
- **小数1桁への切り捨ての根拠が逆になっている**。契約は「表示が 5.0年 なのに実際は 5 年を超えている、という状態を作らないため」に切り捨てるとしている。しかし、切り捨てはまさにその状態を作る（実際 5.08 年 → 表示 5.0年）。表示の値が実際の値以下になるのが切り捨てで、「X年以内」（実際 ≤ X）と表示が食い違わないのは切り上げのほうである。Sprint 6 がこの値をそのまま使うと、次のどちらかになる。
  - 切り捨てた値で絞り込む: 実際には 5 年を最大約36日超えた銘柄が「上場5年以内」に入る（仕様違反）。
  - 正確な値で絞り込む: 「5.0年」と表示された銘柄が「5年以内」を満たさない側になり、利用者が混乱する。

### 4. AC4.4 の担保 — 妥当
- 初出日の行があるコードは API を呼ばない。保存は `on conflict do nothing`。既存の行を更新・削除する経路は無い。この三重の担保で十分。C4-2（`first_price_date`・`data_start_date`・`determined_at`・`run_id` が変わらないこと、`code=` の要求が無いこと）と C10-5 で判定できる。
- 銘柄マスタの取り込み（Sprint 3 の `upsert`）は `stocks` を削除しないので、`on delete cascade` で初出日が消えて作り直される経路も今のところ無い（確認済み）。上場廃止を扱う Sprint 11 で `stocks` を削除する場合は、AC4.4 が壊れないよう注意すること（改善提案 R4）。

### 5. 600ms 間隔・210秒の打ち切り・一部失敗からの継続 — 妥当
- 600ms は 100 回/分で、上限の 120 回/分に余裕がある。二重実行の防止があるので、手動と Cron が同時に要求を出すことも無い。
- 210 秒＋1回の要求の上限 30 秒＋保存でも 300 秒に収まる。Cron で、銘柄マスタの分をルートの開始から数える点も正しい（C8-6 で確認できる）。
- 行の無い銘柄だけを処理する設計なので、次の実行で自然に続きから再開する。50 銘柄ごとの保存と `processed_count` の加算、後片付けされた実行に書かない点も、Sprint 3 の方針と一貫している。C4-9・C4-12・C4-13 で判定できる。
- `details` の恒等式（`pending = …`）は、テストで確かめやすく良い。

### 6. M1・M2 — 妥当
- `Origin` のホストを `X-Forwarded-Host`（最初の値）または `Host` と比べる方法は、Next.js の Server Actions の CSRF 対策と同じ。`X-Forwarded-Host` を信用しても CSRF の防御は弱くならない。別のサイトのページは、この値を付けると CORS のプリフライトになり、送れない。ブラウザ以外（curl など）は `Origin` 自体を自由に付けられるので、この確認はもともと防御の対象外。Vercel では、プラットフォームが `X-Forwarded-Host` を設定する。
- 403 の文言を `cross_origin` と `forbidden` で分ける点、判定を1つの関数にまとめてログアウトにも使う点も良い。C9-1〜5 で判定できる。
- M2 は `HEAD` を明示して 405（`Allow: GET`）。C8-3 で判定できる。

### 7. キーなしでの判定可能性 — おおむね良い
- C10 以外はキーなしで判定できる。成功の経路は、C4（fetch だけを差し替えた DB 込みの結合テスト）と C1・C2・C5（直接投入）で確かめられる。C7 は実 API の 403 を使うので、上の実測（`The incoming api key is invalid or expired.`）と合う。
- 必須修正1を反映した後も、C7 の無効なキーでは、**最初の1回の要求で**失敗が確定すること（14 日分を試さないこと）を条件に加えてほしい。

## 必須の修正項目

1. **W の探索とコード別の取得での、210・403・400 の扱いを定める（第2章の3、第5章の表と10、C4、C7）**
   - 公式の response-status に載っている **210**（データを取得できなかった）を、W の探索では「行0件と同じ（次の日へ）」、コード別の取得では「株価データなし（`noPriceData`）」として扱う。
   - W の探索で受けた **403** を2つに分ける。本文の `message` が無効なキー（`The incoming api key is invalid or expired.`）やキーの欠如（`The api key is required.`）のときは、すぐに失敗にする（今の C7 どおり。要求は1回）。それ以外の 403（契約の範囲外・期間外の可能性）は、400 と同じく次の日に進む。14 日すべてが行0件・210・400・403（範囲外）だった場合は、「株価データの取得可能期間の開始日を特定できませんでした」で失敗にする。最後に受けた状態コードを `details` に残すと、キーありの環境で原因がわかる。
     - `message` の文字列で分けるのを避けるなら、代わりの方法でもよい。たとえば、S を境界からさらに内側（例: +7日）にし、探索の最初の日の 403 だけをキーの問題とみなす。どの方法でも、「期間外の 403 で毎日失敗し続けない」ことと「無効なキーは1回の要求で失敗が確定する」ことの両方を満たし、その理由を契約に書くこと。
   - C4 に、フィクスチャで確かめる条件を加える。(a) W の探索の1日目が 403（範囲外の文言）、2日目に行がある → W は2日目で成功。(b) 1日目が 210 → 次の日へ。(c) コード別の取得が 210 → `noPriceData` に数え、`failed` には数えない。(d) 無効なキーの文言の 403 → 要求1回で失敗（今の C4-6 を具体化）。
   - 第8章の「公式に記載が無い2点」に、403（契約の範囲外）と 210 の可能性を書き足す。

2. **小数1桁の丸めを、「上場X年以内」の判定と食い違わない規則に直す（第2章の6、第6章、C1-4、C2-3、C3-1）**
   - 今の「切り捨て」は、契約自身の目的（表示 5.0年 なのに実際は 5 年超、を作らない）と逆の結果になる（論点3）。
   - 次のどちらかにし、根拠を正しく書き直す。
     - (a) **小数1桁に切り上げる**。1桁の閾値 X に対して「表示 ≤ X ⇔ 実際 ≤ X」が成り立ち、Sprint 6 が表示の値で絞り込んでも仕様どおりになる。例は 2023-09-24 → 3.0、2023-09-25 → 3.0（2.997…）、2023-09-23 → 3.1、4年364日 → 5.0、5年1日 → 5.1、2016-09-27 → 2026-09-24 → 10.0（9.99…）のように変わる。
     - (b) 別の規則にする場合は、「Sprint 6 の絞り込みがどの値を使うか」と「表示と絞り込みの結果が食い違わないこと」を契約に明記する。
   - ビュー（または関数）には、丸める前の値（またはそれを出せる項目）も返し、Sprint 6 の並べ替えと絞り込みに使えるようにすることを推奨する。
   - C1-4、C2-3、C3-1 の期待値を、選んだ規則に合わせて直す。テストは 5.0 の境界の前後（ちょうど5年、5年＋1日、5年−1日）を必ず含める。

3. **「Standard で取り込んだ行は N = 10」という記述を直す（第2章の6、第4章のカードの例、C10-4）**
   - W は「実行日の10年前の翌日」以降なので、取り込んだ当日の基準日から W までは10年未満になる。取り込み直後の N は **9** で、基準日が W＋10年に達したとき（最大で約2週間後）に 10 になる。第6章の投入例（N=9）とは合っているが、第2章の6の記述と矛盾している。
   - 記述を正しく直すこと。C10-4 に期待する N を書くなら、「取り込み直後は 9、その後 10」と書く。第4章のカードの例「（10年超）」も、例だとわかる書き方にする。
   - 「9年超」の表示を避けたい場合（実際は約10年のデータがあるため）は、N の定義を変える方法もある。ただし、その場合は仕様の「N年超」が正しい（実際にN年を超えている）ことを保つこと。

## 改善提案（推奨。合否には影響しない）

- R1: ログアウトの GET（`/auth/signout`）は、`request.nextUrl.origin`（既定のホスト名）でリダイレクト先を作っている。`127.0.0.1` で開いた場合、許可の取り消し後に `localhost` のログイン画面へ移る可能性がある。M1 と同じ理由なので、リダイレクト先を相対パス、または同じ判定から作るホストにそろえることを推奨する。C9-2 では、ログアウト後の `/login` のホストが `127.0.0.1` のままであることも確かめてほしい。
- R2: 第2章の4（初出日の限界）に、**銘柄コードの再利用**を加える。上場廃止の後に同じコードが別の会社に割り当てられると、`code=X&from=W` に前の会社の行が混ざり、初出日が古くなる（または W の一覧に出て「データ期間開始以前から上場」になる）。補正は不要だが、推定の限界として書いておく。
- R3: 取引日カレンダー API（`/v2/markets/calendar`、`hol_div` で営業日を絞れる）を使えば、S 以降の最初の営業日を1回の要求で求められる。休場日の探索が要らなくなる。必須ではない。使う場合も、期間外の応答の扱い（必須修正1）は必要。
- R4: Sprint 11 で上場廃止を扱い、`stocks` の行を削除する場合、`on delete cascade` で初出日も消える。その後、同じコードで再び取り込むと、初出日が作り直される（AC4.4 に反する）。第9章に一言残しておくとよい。
- R5: 基準日は、株価の取り込みが失敗し続けると古いままになり、年数が実際より短く表示される。仕様の「データが古いときの警告」（Sprint 11）で扱う旨を第9章に書いておくとよい。
- R6: 初回の完了後も、毎日の実行で W の探索（`date=` の一覧、数千行）を行う。対象（未確定の銘柄）が0件なら探索しない、という第5章の4の順序は正しい。ただし、「株価データなし」の銘柄が1つでも残っていると、毎日探索することになる。問題は無いが、`details.apiCalls` で見えるようにしておくとよい（今の設計どおり）。
- R7: `GET /api/stocks` の `estimated_listing_years` は、JSON の数値で `3`（3.0）になる。画面と API で表示の桁がそろうよう、API の説明（CLAUDE.md）に「小数1桁の数値」と書いておくとよい。

## 新たな指摘（軽微。承認の条件にはしない）
- N1: 「計算は `numeric` で行う」とある。C3-1 の Vitest でアプリ側の表示用の関数を使う場合は、切り上げを `Math.ceil((d / L) * 10)` のように浮動小数点で行わないこと。整数で `Math.ceil(10 * d / L)` のように計算しないと、境界（端数がちょうど 0.1 の倍数）で DB の結果と1桁ずれうる。画面と API は DB の値を表示するだけにするのが最も安全。C3-2（アプリと DB の一致）で確かめる。
