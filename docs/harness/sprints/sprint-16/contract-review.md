# Sprint 16 契約レビュー

## 判定: 修正依頼

全体としてよくできている。仕様の F16（AC16.1〜AC16.12）をすべて完了条件に対応させており、各条件は E2E・API・DB・単体テストで合否を判定できる。ユーザーの決定（「事業の内容」の最初の段落を原文のまま表示するだけ）からの範囲の拡大は見当たらない。AI 要約・全文・2段落目以降・事業系統図・円グラフ・文による検索は、第8章でやらないことに明記されている。抽出の失敗の分類（`conflicting_sections`・`paragraph_too_long`・`continuation_not_supported`）、性能の上限、取り込み状況の「記載なし／読み取れなかった」の内訳は、仕様の状態表示（AC16.5・AC16.9）を支える最小限の補足と判断した。過剰な拡大とはみなさない。

ただし、受け入れ基準の網羅が1点欠けている。ほかに、契約の中の矛盾が1点、件数の定義のあいまいさが1点ある。いずれも小さな修正で済む。

## 修正必須

### R1: AC16.12「訂正報告書に区画が無く元の有報を使う場合」をフィクスチャで確かめるテストが無い
- AC16.12 は、事業の内容の読み取りと最初の段落の取り出しの自動テストについて、フィクスチャに「訂正報告書に区画が無く元の有報を使う場合」を含めるよう求めている。
- 契約の C7-1 は、DB に行を直接入れて書類の選び方を確かめるだけで、ZIP（フィクスチャ）からの読み取りを通らない。C6 は単一の書類の抽出、C8 は訂正を含まない。
- 修正: C8 に1項目を足す。`synthetic.ts` で組み立てた次の2通の ZIP を、書類取得 API の差し替えで返す。
  - 元の有報（事業の内容の区画あり）
  - 訂正有報（親はその有報。大株主・役員などはあるが `DescriptionOfBusinessTextBlock` が無い）
- 取り込みを実行した後、次を確かめる。
  - 訂正の行は `section_not_found`、元の有報の行は `ok`
  - `business_description_detail` が元の有報の段落を返し、`fallback = true`、飛ばした書類は訂正
  - 大株主・役員の区画（`annual_report_sections_for`）の選択は従来どおり

### R2: 「取り込み待ち」の件数の扱いが第2章の5と第2章の8・C5-4 で矛盾している
- 第2章の5 の末尾には「取り込み状況の『取り込み待ち』に、事業の内容の分が含まれる。これは正しい振る舞いとする」とある。
- 一方、第2章の8 と C5-4 は「既存のキーと値は変えない」としている。既存の「取り込み待ちの書類」（`annual-report-pending-count`）は `pendingDocumentCount` で、大株主・役員の区画の pending だけを数える（`20261007000000` の `annual_reports_summary`）。
- このままでは、導入直後に既存のタイルが 0 件、新しい注記が約 3,900 件になる。どちらが正しいのか、評価で判定できない。
- 修正: どちらにするかを1つに決めて、契約に書く。推奨は「既存のタイルの値は変えず、事業の内容の待ちは新しいタイルの注記（`business-description-pending-count`）だけで示す」。その場合は第2章の5 の該当の文を直す。
  - 区画の説明文（「取り込み待ちが残るときは『今すぐ取り込み』を続けて押す…」）が、事業の内容の待ちにも当てはまることがわかる文にする。
  - 「未取得の残り」の注記（Sprint 12 の `remaining_count`）に事業の内容の分が含まれる点は、今の記述のままでよい。

### R3: 事業の内容の「取り込み待ちの有報」の数に、上場廃止の銘柄の書類を含めないことを明記し、確かめる
- `pendingDocumentCount`（第2章の8）は「区画の状態が pending の書類の数（重複なし）」とだけ書かれている。上場中に限るかどうかが、文面から読み取れない。
- `edinet_ingestion_state` は上場廃止の銘柄を対象から除く（第2章の5、Sprint 12）。上場廃止の銘柄の pending の書類を数えると、取り込みを何回続けても 0 にならない。AC16.9（数は上場中の銘柄だけで数える）にも反する。
- 修正:
  - 第2章の8 に「`pendingDocumentCount` も上場中の銘柄の書類だけを数える（既存の `pendingDocumentCount` と同じ `listed` で絞る）」と明記する。
  - C5 に1項目を足す。例: 9R012（上場廃止）の事業の内容の行を消して pending にし、リロードしても `business-description-pending-count` が増えないことを確かめる（psql の操作と期待値を書く）。

## 改善提案（承認の条件ではない）
- C6-2 か C6-3 に、仕様の見出しの例「＜当社グループの事業＞」「【事業系統図】」を、そのまま見出しの行として加える。どちらも句点が無く 40 文字以下なので、規則で飛ばされることを例で固定できる。
- 第2章の6 の pending の文言の書式「{種類} （{書類ID}）」に、余分な半角空白がある。例文「有価証券報告書（S16TEST51）」と合わせる。仕様の「有報（書類ID）」を種類の名前（有価証券報告書・訂正有価証券報告書）にするのは、より具体的な表示なので妥当と判断する。
- AC16.8 の「導入の前後で変わらない」のうち、マイグレーションそのものが既存の行を変えないことは、C8 では確かめられない（C8 は導入後の取り込みを確かめる）。self-review に、マイグレーションに既存のテーブルへの DML（update・delete・insert）が無いことを書いてほしい。評価者も、マイグレーションのファイルで確かめる。
- 第2章の4(b) の「HTML の空白の連続は U+0020 1つ」は、ブラウザの表示に合わせた解釈として妥当。原文の HTML のソースの改行が和文の途中にあると、表示に半角空白が入る。実データの抜粋でそうなるかを self-review に書いてほしい（なるなら、和文の文字に挟まれた空白の扱いを報告する）。

## 第2章の論点への見解
1. 実 API が使えないための方針: Sprint 8・9 と同じで妥当。閲覧サイトから実データの抜粋を最低1通取ることを必須にしている点がよい。
2. target を分けず、同じ ZIP の3つ目の処理にする: 妥当。届出書で行を作らないことも仕様（有報だけ）に合っている。
3. 選び方を `annual_report_sections_for` の大株主の列と同じにし、既存の関数を変えない: 妥当。新しい訂正が未処理の間は取り込み待ちを表示し、古い事業年度に戻らない（C3-5）。これは仕様の「大株主・役員の区画と同じ規則」に沿っている。
4. 最初の段落の具体化: 仕様の定義 1〜5 に沿っている。表・図の代替テキストを採らないこと、`&amp;` を文字にすることも妥当。
5〜9. 保存・表示・API・取り込み状況・性能: R2・R3 を除いて妥当。
10. コミットの手順: 並行作業の保護として妥当。評価では、コミットにスケルトンの変更が含まれず、作業ツリーに残っていることを確かめる。
