### R2. Sprint 8 の数と文言の変更がリグレッションを隠さないようにする

  - 新しい区画の「取り込み待ち」は**主要な経営指標等が未処理の書類だけ**を数える。

### R3. `edinet_documents` の削除（連鎖）での再計算を、テストの対象に入れる

第2章の8の表は、`edinet_documents` の delete を再計算の対象にしている。後片付け（`business-results-cleanup.sql`）もこの経路に頼っている。ところが、C4-8 のテストの列挙には delete が無い（取り下げ・不開示・`edinet_filers`・`stocks` の追加・抽出の行の削除だけ）。

書類の行を消すと、外部キーの連鎖で `business_results_extractions`・`business_results_periods` が消える。そのとき、期の行のトリガーが書類から銘柄を引こうとしても、書類の行はもう無い。したがって、再計算できるのは `edinet_documents` 側のトリガー（OLD の `sec_code`・`edinet_code` を使う）だけになる。発火の順番（連鎖の削除 → 文単位のトリガー）によっては、消える前の期で再計算されるおそれがある。

C4-8 に次の2つのケースを明記すること。
- 「`edinet_documents` の行を削除すると、同じ文の中で、その書類の期を使っていた銘柄の指標が再計算される（期が無くなった後の値になる）」
- 証券コードの無い届出書を削除したときも、`edinet_filers` 経由で結び付いた銘柄が再計算される

### R4. 金融業の「経常収益」を読むこと、「経常利益」を売上高として読まないことを、テストで確かめる

ユーザーの決定により、金融業は特別扱いしない。したがって、銀行・保険の書類でも売上高として「経常収益」を読む必要がある。ところが、第2章の5の表では「銀行・保険などの経常収益の要素」の要素名が決まっていない。C7-1 のフィクスチャにも、銀行の形が無い。

`jpcrp_cor` には、「経常収益」と「経常利益」という英語名の紛らわしい要素がある（どちらも `OrdinaryIncome…` 系の名前）。これを取り違えると、利益を売上高として CAGR に入れることになり、しかも静かに間違う。

C7-1 に次を加えること。
- 経常収益と経常利益の両方が記載された書類（銀行の形。実データが取れなければ資料に沿って組み立てる）では、売上高が経常収益の要素から読まれる。`revenue_element` にその要素名が入る。
- 経常利益の要素（`…OrdinaryIncomeLoss…SummaryOfBusinessResults` の類）だけの書類は、売上高として読まれない。

要素の定数の一覧には、「読まない要素」の注記も書くこと。

## 論点ごとの判断（承認する点）

- **S1（期の開始日）**: 書類一覧の `periodStart` を使わず、事実のコンテキストの期間から取り、決められない期は保存しない。この方針は正しい。12か月を仮定して補うと変則決算を見落とす、という理由付けも妥当である。`endDate` の表し方を実データで確かめ、テストで固定する（C7-1）ことも適切。
- **出典の優先順位**: 期（終了日）ごとに、`source_priority` → 提出日時 → 書類ID の順で1行を選ぶ。EDINET には項目ごとの補いを適用せず、書類IDと値の出どころを一致させる。この方針は仕様の「最も新しく提出された書類の値」と整合する。決算短信の期は Sprint 5 のまま。
- **トリガーでの再計算**: 変更の種類ごとの対象の表（第2章の8）は漏れが少ない。`stocks` の upsert で既存の銘柄を再計算しないことの確認（C4-8）もよい。
  - `save_edinet_document_list` の upsert は、既存の行が変わらなければ更新しない（`where … is distinct from`。Sprint 8）。そのため、直近7日の一覧の取り直しで再計算が毎日走ることは無い。
  - R3 の delete の確認だけを加えること。
- **キー未設定での検証方針**: 次の方針は、仕様の検証方針に合っている。
  - 閲覧サイトから実在の書類を取得するのを必ず試み、取得できた書類の抜粋をフィクスチャにする。取得できなかった形は資料に沿って組み立て、そう明記する。
  - アプリの本体にサンプルを置かない（C12-7）。
  - キーありの件数を合否の条件にしない。
- **1つの target で2つの処理**: 同じ ZIP を2回取らない、という理由は妥当である。導入時に1回だけ取り直すこと（C6-4）も明示されている。
- **補完の印は CAGR が算出された銘柄だけ**: AC15.3 の「CAGR の算出に EDINET から補った期を含む銘柄」の解釈として正しい。
- **注記の差し替え**（C9）と m2・m3 の取り込み（C10）は、完了条件が具体的で判定できる。

## 改善提案（修正依頼ではないが、検討してほしい）

1. **売上高の要素の優先と決算短信の一致**: 小売業などは「売上高」と「営業収益」の両方を記載する。決算短信（J-Quants の `Sales`）が営業収益を採っている会社で、EDINET の期は `NetSales…`（売上高）を先に読むと、CAGR の分母と分子で定義がずれる。上場から日の浅い会社では少ないと思われるが、既知の制限として CLAUDE.md に書くとよい。
2. **直近通期が EDINET の期の営業利益率**: 日本基準の「主要な経営指標等の推移」には、ふつう営業利益の行が無い。そのため、決算短信がまだ無い銘柄（上場直後）では、営業利益率が「算出不可（営業利益の開示なし）」になる。表示の「開示なし」は、実際の事情（書類の表に記載なし）と少し違う。カードの出典の補足（第4章）に加えて、理由の文言を「記載なし（書類の主要な経営指標等に営業利益の行がありません）」に寄せると、誤解が減る。
3. **届出書の取得量**: 「銘柄に結び付く届出書をすべて対象」にすると、上場会社の新株予約権・公募増資の届出書（参照方式が多い）も取得することになる。取得の順番で補完の効く書類を先にするので実害は小さい。ただし、初回の所要の見積もり（CLAUDE.md）に、届出書の件数も入れるとよい。
4. **「補」の印の分かりやすさ**: 目に見えるのは1文字の「補」である。`aria-label` と `title` に「補完あり」があるので AC15.3 は満たせる。ただし、初めて見た人には意味が伝わりにくい。デザインの評価で見る。

## 実装時の注意（承認の条件ではないが、評価で見る）

1. **営業利益率の理由の文言は、表示の層で出し分ける。** 「営業利益の記載なし」は、FY0 の出典が EDINET のときの表示である。`financial_metrics_from_periods` の理由のコード（`operating_profit_not_disclosed`）を出典によって変えると、「算出は出典に依存しない」（C4-9）が崩れる。コードはそのままにし、画面が `financial_periods` の FY0 の `source` を見て文言を選ぶこと。スクリーニングの一覧の理由の表示も同じ規則にそろえる。
2. **取り直しの間の本文の停止。** `edinet_list_fetched_dates` を全部消すと、導入後の約3回の実行では、一覧を取り終えるまで本文（大株主・役員を含む）に進まない。これは意図どおりだが、取り込み状況の画面で「一覧の取り直し中」と分かるようにしておくとよい（`details.stoppedReason` などに理由が残ること）。
3. **トリガーの発火の順番。** 外部キーの連鎖の削除は、PostgreSQL では親の文の after の行トリガーとして動く。文単位の after トリガーより先に終わるはずだが、C4-8 のテストで実際の値を確かめること（契約のとおり）。評価では、後片付けの後の `financial_metrics` と、S9TEST12 の削除での表示を psql で確かめる。
4. **C12-2 の「`details` の値」**は変えてよい範囲が広い。評価では、`details` の変更が届出書と主要な経営指標等の項目の追加に限られ、Sprint 8 の既存のキー（`listDatesFetched`・`documentsListed`・`stoppedReason`・`failedDocuments` など）の意味が変わっていないかを差分で見る。
5. **ダッシュボードの表示**は定数1か所から出す。評価では、「有報」の文字がアプリの target の表示に残っていないか（Sprint 8 の区画の見出しなど、書類の種類としての「有報」は除く）を、全画面で見る。
