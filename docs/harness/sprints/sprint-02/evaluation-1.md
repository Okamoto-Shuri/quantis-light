### B1: dev サーバーをしばらく動かすと、B2' の `Performance.measure` 例外が再発する（C7-1、C7-2 が未達）
- 重要度: Major（完了条件の未達。dev 限定で、保護された内容は表示されない）
- 再現手順（`pnpm dev`。契約の C7-1 と同じ）:
  1. `pnpm dev` を起動し、しばらく操作する。今回は、起動から約5〜15分後、ほかの画面の操作を何度か行った後に再現した。
  2. owner でログインし、`/nope` を開く。
  3. 「ダッシュボードに戻る」を押し、ヘッダーの製品名を押す。
  4. ログアウトし、「戻る」を2回押してから「進む」を押す。
  5. C7-2 の経路（`/nope` → 取り込み状況 → 設定 → ログアウト → 戻る×3 → 進む×2）でも同じ例外が出る。
- 期待結果: `pageerror` が0件。
- 実際の結果: `Uncaught TypeError: Failed to execute 'measure' on 'Performance': '​MissingPage' cannot have a negative time stamp.` が出る。画面は `/login?next=...` で、保護された内容は表示されない。
- 根拠（別々の dev サーバー3つで観測した）:
  - **サーバー1**（約10分動かした後）: 私のスクリプトで、経路 A と B を各3回試し、**6回中6回**で例外が出た。続けてプロジェクト自身の `pnpm exec playwright test e2e/shell.spec.ts -g "B2'"` を実行すると、**2件とも失敗**した（DB を空にしてから再実行しても、2件とも失敗）。

    ```
    - Array []
    + Array [
    +   "pageerror: Failed to execute 'measure' on 'Performance': '​MissingPage' cannot have a negative time stamp.",
    + ]
    > 224 |     expect(problems).toEqual([]);
    ```
  - **サーバー2**:
    - 起動直後と、各画面の検証を行った直後は、0/6 だった。E2E も成功した。
    - 約13分後からは 4/6、6/6、6/6 と、続けて再現した。
    - node_modules へのファイルの追加が原因ではないことは、サーバー3で切り分けた。
  - **サーバー3**: 起動直後から 90 秒ごとに6回試行した。結果は `0, 0, 5, 0, 0, 0` で、起動から7分後に6回中5回出た。
  - **prod**（`pnpm start`）: 6/6 で0件。
  - 起動したばかりの dev サーバーで実行する E2E（`pnpm test:e2e`）は成功する。自己評価の「E2E で pageerror 0件」は、この条件でだけ成り立っている。
- 考察と修正の方向:
  - 保護画面の中で描画する構成に変えても、発生元のコンポーネントの名前が `NotFound` から `MissingPage`（`notFound()` を投げる catch-all のページ）に変わっただけで、例外そのものは残っています。
  - 起動直後の dev サーバーでは出ず、しばらく動かすと出ます。そのため、「修正前の構成に戻すとテストが失敗する」ことを確認しただけでは、解消した証拠になりません。
  - 次のことを勧めます。
    - 長く動かした dev サーバー（または `performance.timeOrigin` がずれる条件）で、再現を確かめる。
    - React や Next.js の、開発時のパフォーマンス計測（Server Components の track）の側で、原因を特定する。
    - `notFound()` を投げない構成（catch-all で 404 の本文を直接描画し、ステータスだけ 404 にする、など）を検討する。
  - アプリ側の変更で解消できない場合は、C7-5 に従って、調査結果と代わりの扱いを契約の改訂として提示してください。
  - E2E は、起動直後のサーバーでは例外を検出できません。この性質も、改訂に明記してください。
- 関連: CLAUDE.md の「404」の項は、構成を変えたことで例外が解消したように読めます。B1 の結論に合わせて直してください。

## 改善提案（合格判定には影響しないが推奨）
- 設定画面のテーマのラジオで、Tab でフォーカスした直後の最初の矢印キーは、フォーカスを動かすだけで選択を変えません（2回目からは選択が変わります）。Radix の既定の動作とみられ、Space で選択できるので、実害は小さいです。ヘッダーのメニューはキーボードで問題なく操作できます。
- 375px の取り込み状況は、1件ごとにカードが縦に長いです。50件あると、ページがかなり長くなります（約 6,500px）。後続スプリントで履歴の詳細画面を作るときに、1件をもっと短く表示する方法（開始日時・対象・結果の1行表示など）を検討してください。
- 集計エラーのとき、dev ではサーバーのログ（`[dashboard] 集計の取得に失敗しました`）がブラウザのコンソールにも転送され、エラーとして表示されます。意図的に障害を起こしたときだけの現象で、prod では出ないので、問題はありません。
