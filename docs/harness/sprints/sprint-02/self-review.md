# Sprint 02 自己評価（ラウンド 2: 修正R1）

evaluation-1.md の B1（dev サーバーを長く動かすと、B2' の `Performance.measure` 例外が `'MissingPage'` として再発する）に対応した。ラウンド1の自己評価の「E2E が不具合を検出できる」は、起動直後のサーバーでしか成り立っていなかった。評価の指摘どおりである。

## 原因の調査
- 例外を投げているのは、React 19.2 の開発用ビルドの RSC クライアント（`react-server-dom-turbopack-client.browser.development.js` の `flushComponentPerformance`）。
  - エラーになったサーバーコンポーネント（`notFound()` や `redirect()` を投げたもの）を "Errored" として記録するとき、`performance.measure(name, { start: max(0, start), end })` を呼ぶ。開始時刻は 0 未満を 0 に丸めるが、**終了時刻は丸めない**。
  - 正常なコンポーネントの記録には `0 < endTime` のガードがあるが、エラーの記録には無い。
  - メッセージの名前の前の空白は、エラーの記録を表すゼロ幅スペース（`"​" + name`）である。`'​MissingPage'` と一致する。
- 時刻は「サーバーの絶対時刻 − ブラウザの `performance.timeOrigin`」で換算される（`_timeOrigin = +row - performance.timeOrigin`）。したがって、終了時刻が負になるのは、サーバーの時計がブラウザより遅れていて、コンポーネントがブラウザのナビゲーション開始より前に描画されたように見えるときである。
- 確定的な再現: ブラウザの `performance.timeOrigin` を 5 秒進める（＝サーバーの時計が遅れている状態）init script を入れると、**起動直後の dev サーバーでも**、修正前のコード（769a38c）で `/nope` を直接開いた1回目に `'MissingPage' cannot have a negative time stamp` が出た。戻る・進むは必須ではなかった。init script が無ければ出ない。
- 時計のずれの実測: 別の Node プロセスで `performance.timeOrigin + performance.now() − Date.now()` を 24 分記録した。値は +0.9ms から −8.3ms まで単調に減った（約 −0.35ms/分）。Node の時刻は、起動時の壁時計と単調時計から求めるため、壁時計から徐々に遅れる。これが「長く動かすと出る」の説明として最も有力な仮説である。
- 同じ種類の問題の別の経路: 許可を取り消した後にナビゲーションでクライアント遷移すると、ページの `requireAllowedUser()` が投げる `redirect()` で、`'ImportsPage'` について同じ例外が出た（時計のずれを再現した状態。修正前のコードでも同じ）。`notFound()` だけの問題ではない。

## 対策（2層）
1. **404 を、何も投げずに描画する**
   - `(app)/[...missing]`（`notFound()` を投げる）と `(app)/not-found.tsx` を削除した。
   - 一致しない URL は `src/app/global-not-found.tsx`（`experimental.globalNotFound`）で描画する。
   - global-not-found はルートレイアウトを通らないため、次のようにした。
     - `<html>`、テーマ、フッターは `src/app/app-document.tsx` に切り出して共有した。
     - 認証（`requireAllowedUser()`）とアプリの枠は、このファイルの中で行う。
     - HTTP ステータスは 404 のまま。
   - global-not-found の中では、next/link のクライアント遷移で画面が切り替わらない（URL だけ変わり、404 の表示が残る）ことを見つけた。そこで `AppLink`（`src/components/shell/app-link.tsx`）を用意した。global-not-found の中では `<a>`（文書遷移）、それ以外では next/link になる。対象はナビゲーション、製品名、「ダッシュボードに戻る」。
2. **開発時だけ、`performance.measure` に渡る負の時刻を 0 に丸める**
   - 実装は `src/lib/dev/measure-guard.ts`。`src/instrumentation-client.ts` から、`NODE_ENV === "development"` のときだけ入れる。
   - React が開始時刻に行っている丸めを、終了時刻にも行うだけである。計測の記録以外には影響しない。本番の React はこの計測をしないので入れない。
   - これで、`redirect()` や、今後のページ（銘柄詳細など）の `notFound()` も対象になる。
   - 404 は、対策1だけで例外が出ないことを確認している（下記）。対策2に頼っていない。

  - 404 画面の中のリンク（ナビゲーション2つ、製品名、戻る）で実際に移動できる（新規。C7-7）

## 長時間稼働した dev での確認（試行回数と結果）
- 修正後のコード（:3000）と修正前のコード（769a38c を git worktree で :3001）の dev サーバーを同時に起動し、約 31 分動かした。
- 1つの Chromium で、90 秒ごとに評価者の手順を実行した（経路 A＝C7-1、経路 B＝C7-2。時計のずれの再現は無し）。
- 16 回 × 2 経路 × 2 サーバー ＝ 64 回。
- 結果:
  - **修正後: 32 回中 0 回**。この計測の時点の構成は対策1だけ。対策2を入れた後は、起動直後のサーバーで E2E を実行しており、長時間の再計測はしていない。
  - **修正前: 32 回中 0 回**。
  - 正直に書くと、評価者の環境で起きた自然な再発は、私の環境では 28 分以内には再現しなかった。上記の時計のずれは 24 分で −8ms で、ナビゲーション開始からサーバーの描画までの時間より小さかったためと考えている。
  - そのため、「修正後は長時間でも出ない」ことの主な根拠は、時計のずれを 60 秒ぶん再現した E2E（修正前は必ず失敗し、修正後は成功する）である。ずれの大きさに関係なく、404 の描画には、エラーの記録の対象になるコンポーネントがもう無い。
- 評価者には、評価者の環境で長く動かした dev サーバーでの再確認をお願いしたい（契約 C7-6）。
