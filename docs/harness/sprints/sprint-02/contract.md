# Sprint 02 契約: F2 アプリシェルとダッシュボード

## 1. 対象機能

F2 アプリシェルとダッシュボード。ログイン後の全画面に共通のヘッダー、ナビゲーション、テーマ切り替え、モバイル用メニューを用意する。ダッシュボードには、保存済みデータから集計したデータの鮮度と件数を表示する。データが無いときは空状態を表示する。

あわせて、Sprint 1 の評価（`sprint-01/evaluation-2.md`）で持ち越しになった次の2点に対応する。
- B2': dev で「404 → ダッシュボード → ログアウト → 戻る×2 → 進む」の経路をたどると、`Performance.measure` の例外が出る。これを解消し、E2E に戻る・進むの経路を追加する。
- CLAUDE.md に「テーブルは必ずマイグレーションで作成する」と明記する。

### 仕様書の受け入れ基準（引用）

- AC2.1 ログイン後、ナビゲーションから各画面に移動できる（まだ実装されていない画面は「準備中」ではなく、ナビゲーションに出さない）。
- AC2.2 ダッシュボードに、最終取り込みの完了日時、保存済みの銘柄数、財務指標を算出できた銘柄数、条件④を判定できた銘柄数が表示される。いずれも保存済みデータから集計した実際の値である。
- AC2.3 データが1件も無いときは、ダッシュボードに「まだデータが取り込まれていません」という空状態と、取り込み状況画面へのリンクが表示される。ダミーの数値は表示されない。
- AC2.4 ライト／ダークのテーマを切り替えられ、リロードしても選択が保持される。
- AC2.5 横幅 375px の画面でもナビゲーションが使え（ハンバーガーメニューなど）、表示が崩れない。

## 2. 仕様上の論点と、このスプリントでの解釈

仕様を変えずに、次のように解釈する。評価者は、この解釈が妥当かも判断してほしい。

1. **AC2.3 の「取り込み状況画面へのリンク」と、AC2.1 の「未実装の画面はナビゲーションに出さない」**
   取り込み状況画面そのものは F3（Sprint 3）の機能だが、Sprint 2 でリンク先が無いと AC2.3 を満たせない。そこで Sprint 2 では、取り込み状況画面を「実行履歴の閲覧」だけに絞って実装する。
   - 実行履歴は DB の実テーブル（後述の `public.ingestion_runs`）から読む。「準備中」の表示やダミーの行は出さない。
   - 取り込みを実行する仕組みはまだ無いので、通常は「実行履歴はまだありません」という空状態になる。評価者が DB に行を投入すれば、その行が表示される。
   - データソースの設定状態、「今すぐ取り込み」ボタン、Cron は Sprint 3 で実装する。これらの領域は Sprint 2 では描画しない（「準備中」のプレースホルダも置かない）。
2. **AC2.2 の集計元のテーブル**
   財務指標（F5）と条件④の判定（F9）の取り込みは後続スプリントの機能だが、集計対象を DB に用意しておかないと、AC2.2 の「実際の値」を評価者が確かめられない。そこで Sprint 2 では、ダッシュボードの集計に必要な最小限の列だけを持つテーブルを、マイグレーションで作る（第6章）。後続スプリントでは、マイグレーションで列を追加して拡張する。アプリはこれらのテーブルに行を書き込まない（Sprint 2 では書き込み経路が無い）。
3. **「最終取り込みの完了日時」の定義**
   結果が「成功」または「一部失敗」で終わった実行のうち、`finished_at` が最も新しいもの（対象の種別は問わない）。「失敗」の実行は、データを更新していないので含めない。ただし、利用者が失敗に気づけるよう、直近の実行（開始日時が最も新しいもの）の結果を別に表示する。どの対象の完了を「日次取り込みの完了」とみなすかは、取り込みの種類が増える Sprint 3 以降で見直す。
4. **「財務指標を算出できた銘柄数」の定義**
   売上CAGR と営業利益率の、少なくとも一方を算出できた銘柄数。内訳として、売上CAGR を算出できた銘柄数と、営業利益率を算出できた銘柄数も表示する。
5. **「条件④を判定できた銘柄数」の定義**
   判定の状態が「判定済み」（判定不能以外）の銘柄数。判定結果の4区分（該当・非該当など）は、閾値に依存するため Sprint 9 で扱う。
6. **「データが1件も無い」の定義**
   保存済みの銘柄数（`public.stocks` の行数）が 0。このときは件数のカードの代わりに空状態を表示する。銘柄が1件以上あり、財務指標などが 0 件のときは、0 を実際の値として表示する（空状態にはしない）。

## 5. 設計の要点（評価者が確認に使う範囲）

- **テーマ**: 選択肢は「ライト」「ダーク」「OS に合わせる」の3つ。既定は「OS に合わせる」。選択は Cookie `theme`（値は `light`／`dark`／`system`、`Path=/`、有効期限1年、`SameSite=Lax`）に保存する。サーバーがこの Cookie を読んで `<html data-theme="...">` を出力するため、リロード時に配色がちらつかない。Cookie はログアウトで消さないので、ログイン画面にも同じテーマが適用される。ユーザーごとの DB への保存はしない（端末ごとの設定）。
- **テーマの切り替え導線**: ヘッダーのテーマボタン（アイコン。押すと3択のメニュー）と、設定画面の3択。どちらで変えても同じ Cookie を更新する。
- **ナビゲーション**: 幅 768px 以上では、ヘッダーの製品名の右に横並びで表示する。768px 未満では、ヘッダー左端のメニューボタン（`aria-label="メニューを開く"`）で開くドロワーに表示する。現在の画面の項目には `aria-current="page"` を付け、見た目でも区別する。ドロワーは、項目を選ぶ、Esc を押す、外側を押す、のいずれかで閉じる。
- **ダッシュボードの集計**: DB 関数 `public.dashboard_summary()`（`security invoker`。RLS が効く）が、1回の問い合わせで全件数と日時を返す。画面（サーバーコンポーネント）も API も、ログインしたユーザーのセッションでこの関数を呼ぶ。サービスロールは使わない。関数の実行権限は `authenticated` にだけ与える（anon には与えない）。
- **ダッシュボードの API**: `GET /api/dashboard`。`requireApiUser()` で保護し、`jsonNoStore` で返す。未ログインは 401、許可リスト外は 403。
- **取り込み状況の API**: 追加しない（画面はサーバーコンポーネントで、ユーザーのセッションから直接読む）。一覧の API は Sprint 3 で必要になったときに追加する。
- **日時の表示**: すべて日本時間の `YYYY-MM-DD HH:mm`（既存の `formatDateTimeJst`）。ダッシュボードの最終取り込みには、相対表記も並べる（リクエスト時点を基準にサーバーで計算）。相対表記の規則は次のとおり（経過時間は切り捨て）。
  | 経過時間（基準時刻 − 対象時刻） | 表示 |
  |---|---|
  | 0 未満（未来。時計のずれなど）、または 60 秒未満 | 「たった今」 |
  | 60 秒以上 60 分未満 | 「N分前」 |
  | 60 分以上 24 時間未満 | 「N時間前」 |
  | 24 時間以上 | 「N日前」 |

  この規則は Vitest で、境界値（未来、59秒、60秒、59分59秒、60分、23時間59分、24時間）を含めて確認する。
- **数値の表示**: 件数は3桁区切り（`1,234`）、等幅数字で右揃え。比率は「保存済み銘柄数に対する割合」を小数点以下1桁の % で添える（例 `2 / 3 銘柄（66.7%）`）。
- **集計に失敗したとき**: ダッシュボードは「ダッシュボードの集計を取得できませんでした」というエラー表示にする。0 件や空状態として表示しない（障害をデータ無しと誤認させない）。
- **B2' の対策**: 存在しない URL の 404 画面を、保護画面のルートグループの中で描画する構成に改める（async のサーバーコンポーネントをルートの `not-found` として描画しない）。具体的な構成は実装時に決めるが、完了条件（C6）で結果を確認する。404 の HTTP ステータスと、「アプリの枠の中に日本語の 404 を表示する」という Sprint 1 の振る舞いは変えない。

## 6. データの保存形式（評価者の直接投入用）

Sprint 2 のマイグレーション（`supabase/migrations/2026092500xxxx_*.sql`）で、次の3テーブルを追加する。3つとも `public.stocks` と同じ方針にする。RLS を有効にし、anon の権限は無し。`authenticated` のうち許可リストに登録されたユーザーだけが select でき、書き込みは service_role のみ。

### `public.ingestion_runs`（取り込みの実行履歴）

| 列 | 型 | 制約・意味 |
|---|---|---|
| `id` | `bigint` | 自動採番の主キー |
| `target` | `text` | `stock_master`（銘柄マスタ）／`daily_quotes`（株価）／`financials`（財務）／`edinet_reports`（有報）のいずれか |
| `trigger` | `text` | `cron`（定期実行）／`manual`（手動）のいずれか |
| `status` | `text` | `running`（実行中）／`succeeded`（成功）／`partial`（一部失敗）／`failed`（失敗）のいずれか |
| `started_at` | `timestamptz` | 必須。既定値 `now()` |
| `finished_at` | `timestamptz` | `status = 'running'` のときだけ NULL、それ以外は必須。`started_at` 以降 |
| `processed_count` | `integer` | 0 以上。既定値 0 |
| `error_message` | `text` | 任意 |

画面の表示名: 対象は「銘柄マスタ」「株価」「財務」「有報」、起動は「定期実行」「手動」、結果は「実行中」「成功」「一部失敗」「失敗」。

### `public.financial_metrics`（銘柄ごとの財務指標。Sprint 5 で列を追加する）

| 列 | 型 | 制約・意味 |
|---|---|---|
| `code` | `text` | 主キー。`public.stocks(code)` への外部キー（銘柄の削除で連鎖削除） |
| `revenue_cagr` | `numeric` | 売上CAGR（比率。41.4% なら `0.414`）。算出不可なら NULL |
| `revenue_cagr_unavailable_reason` | `text` | 算出不可の理由。`revenue_cagr` と、どちらか一方だけが NULL でない |
| `operating_margin` | `numeric` | 営業利益率（比率）。算出不可なら NULL |
| `operating_margin_unavailable_reason` | `text` | 算出不可の理由。`operating_margin` と、どちらか一方だけが NULL でない |
| `calculated_at` | `timestamptz` | 必須。既定値 `now()` |

### `public.ownership_judgments`（銘柄ごとの条件④の判定。Sprint 9 で列を追加する）

| 列 | 型 | 制約・意味 |
|---|---|---|
| `code` | `text` | 主キー。`public.stocks(code)` への外部キー（連鎖削除） |
| `status` | `text` | `determined`（判定済み）／`undeterminable`（判定不能）のいずれか |
| `judged_at` | `timestamptz` | 必須。既定値 `now()` |

### 投入例（`postgres` ユーザーで実行。RLS を迂回する）

次の投入後の期待値は、完了条件 C3-3 に書く。実行履歴の日時は、評価時点より確実に過去になるよう `now()` からの相対で指定する。画面に表示されるべき日本時間の値は、投入後に次の SQL で求める。

```sql
select id, status,
       to_char(started_at  at time zone 'Asia/Tokyo', 'YYYY-MM-DD HH24:MI') as started_jst,
       to_char(finished_at at time zone 'Asia/Tokyo', 'YYYY-MM-DD HH24:MI') as finished_jst
  from public.ingestion_runs order by started_at desc;
```

```bash
psql 'postgresql://postgres:postgres@127.0.0.1:54322/postgres' <<'SQL'
```

## 7. テスト可能な完了条件

前提: 第3章の手順で起動し、`owner@quantis.local` でログイン済み。DB は `pnpm db:reset && pnpm seed:users` 直後（市場データと実行履歴は0件）から始める。特記の無い限り、`pnpm dev` と `pnpm build && pnpm start` の両方で満たすこと。

### C1. ナビゲーション（AC2.1）と設定画面
1. 幅 1280px でログインすると、ヘッダーに製品名と、ナビゲーション「ダッシュボード」「取り込み状況」「設定」がこの順で表示される。「スクリーニング」「ウォッチリスト」の項目や、「準備中」「近日公開」などの文言はどこにも無い。
2. 各項目を押すと、それぞれ `/`、`/imports`、`/settings` に遷移し、各画面の見出し（「ダッシュボード」「取り込み状況」「設定」）が表示される。押した項目に `aria-current="page"` が付き、ほかの2項目には付かない。
3. 各画面をリロードしたり、URL を直接開いたりしても、同じ項目が現在の画面として表示される。
4. ブラウザのタブのタイトルが、画面ごとに「ダッシュボード | Quantis Light」「取り込み状況 | Quantis Light」「設定 | Quantis Light」になる。
5. ナビゲーションの項目はキーボードだけで操作できる（Tab で移動し、フォーカスが見え、Enter で遷移する）。
6. 未ログインで `/imports`、`/settings` を開くと `/login?next=%2Fimports` などにリダイレクトされる（`curl -sI` で 307）。`/screening`、`/watchlist` はログイン後に開くと 404 画面になる。
7. アカウントメニュー（メールアドレス、ログアウト）は Sprint 1 と同じように使える。
8. 設定画面には「テーマ」と「アカウント」の2つの区画がある。「アカウント」には、実際のセッションの値として、ログイン中のメールアドレス（`owner@quantis.local`）、利用許可の状態（「許可リストに登録済み」）、最終ログイン日時（`auth.users.last_sign_in_at` を日本時間で表示したもの）が表示される。ログインし直すと、最終ログイン日時が更新される。

### C2. ダッシュボードの空状態（AC2.3）
1. DB に銘柄が0件の状態で `/` を開くと、「まだデータが取り込まれていません」という見出しと、短い説明と、「取り込み状況を見る」リンク（`/imports` へ）が表示される。
2. 空状態のとき、銘柄数などの件数のカードや、「0 銘柄」などの数値は表示されない。最終取り込みの日時も数値としては出さない（「未取り込み」などの文言は可）。
3. リンクを押すと `/imports` に遷移し、「実行履歴はまだありません」という空状態が表示される。
4. 実行履歴が0件のときは、空状態の中に「直近の実行」の欄を出さない。
5. 実行履歴が「失敗」の1行だけある状態（`ingestion_runs` に `status='failed'` の行を1行投入）で `/` を開くと、空状態のまま、直近の実行が「失敗」だったこと、その日時、エラーメッセージが表示される。

### C3. ダッシュボードの件数と鮮度（AC2.2）
1. 第6章の投入例のうち `public.stocks` の3行だけを投入してリロードすると、空状態が消え、次の4つが表示される。
   - 最終取り込み: 「記録なし」（成功した実行が無いため。日時は出さない）
   - 直近の実行: 「実行履歴なし」（実行履歴が0件のため）
   - 保存済みの銘柄数: `3`
   - 財務指標を算出できた銘柄数: `0 / 3 銘柄（0.0%）`。内訳の売上CAGR `0`、営業利益率 `0`
   - 条件④を判定できた銘柄数: `0 / 3 銘柄（0.0%）`
2. 数値の値だけを変えたダミー表示でないことの確認: `public.stocks` に1行追加（例 `99904`）してリロードすると、銘柄数が `4` になり、比率の分母も 4 になる。確認後、その行を削除する。
3. 第6章の投入例をすべて投入してリロードすると、次のとおり表示される。
   - 最終取り込みの完了日時: 成功の行の `finished_jst`（第6章の SQL で求めた値）と、相対表記「2日前」。対象「銘柄マスタ」
   - 直近の実行: 「失敗」、開始日時は失敗の行の `started_jst`、エラーメッセージ「J-Quants の API キーが設定されていません」
   - 保存済みの銘柄数: `3`
   - 財務指標を算出できた銘柄数: `2 / 3 銘柄（66.7%）`。内訳は売上CAGR `1`、営業利益率 `2`
   - 条件④を判定できた銘柄数: `1 / 3 銘柄（33.3%）`
4. `update public.ingestion_runs set status = 'partial' where status = 'failed';` を実行してリロードすると、最終取り込みの完了日時が一部失敗にした行の `finished_jst` になり、相対表記が「4時間前」になる（一部失敗も完了として数える）。
5. 実行中の行を、既存のどの行よりも新しい開始日時で追加（`insert into public.ingestion_runs (target, trigger, status, started_at) values ('financials', 'manual', 'running', now());`）してリロードすると、直近の実行に「実行中」（対象「財務」）と表示される。最終取り込みの完了日時は C3-4 のまま変わらない。
6. 件数は3桁区切りで表示される（例: `stocks` に 1,000 行以上を `generate_series` で投入すると `1,000` 以上の区切り付きになる。確認後に削除）。
7. API: ログイン済みのブラウザの Cookie で `GET /api/dashboard` を呼ぶと、200 で次の形の JSON が返り、値が画面と一致する。キー名はこの例のとおりで確定とする。`lastCompletedRun` と `latestRun` は、該当する行が無ければ `null`。日時は ISO 8601 の文字列。
   ```json
   { "data": {
       "stockCount": 3,
       "financialMetrics": { "anyCount": 2, "revenueCagrCount": 1, "operatingMarginCount": 2 },
       "ownershipDeterminedCount": 1,
       "lastCompletedRun": { "target": "stock_master", "status": "succeeded", "finishedAt": "2026-09-22T09:38:00+00:00" },
       "latestRun": { "target": "stock_master", "status": "failed", "startedAt": "...", "finishedAt": "...", "errorMessage": "J-Quants の API キーが設定されていません" }
   } }
   ```
   応答に `Cache-Control: no-store` が付く。未ログインで呼ぶと 401、許可リスト外（C8 と同じ手順で取り消したユーザー）なら 403 で、件数を含まない。
8. RLS の経路で集計していることの確認: 公開キーだけで `POST http://127.0.0.1:54321/rest/v1/rpc/dashboard_summary` を呼ぶと、権限エラー（401 または 42501 など）になり、件数を返さない。新しい3テーブルを公開キーだけで `GET /rest/v1/<テーブル>` しても、行は返らない（エラーまたは `[]`）。
9. 集計が失敗したときのエラー表示を、実際の画面で確認する。
   - postgres で `revoke execute on function public.dashboard_summary() from authenticated;` を実行して `/` をリロードすると、「ダッシュボードの集計を取得できませんでした」と表示される。件数のカードも空状態も表示されない。ヘッダー、ナビゲーション、フッターは通常どおり表示され、ほかの画面にも移動できる。
   - このとき `GET /api/dashboard`（ログイン済み）は 500 で `{"error":"internal_error"}` を返し、件数を含まない。
   - 確認後、`grant execute on function public.dashboard_summary() to authenticated;` で戻す。
   - 同じ振る舞いを Vitest の単体テストでも確認する（集計関数がエラーを返したとき、エラーの状態になり、0 件としては扱わない）。
