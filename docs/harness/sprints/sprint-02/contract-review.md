# Sprint 02 契約レビュー

## 判定: 修正依頼

方針（第2章の解釈、先行して作るテーブル、B2' の扱い）は妥当です。ただし、第6章の投入 SQL に未来の日時が含まれています。そのため、C3-4 と C3-5 が、書かれたとおりには検証できません（下記 R1）。R1 と R2 を直せば承認します。R3〜R5 も同時に直すことを勧めます。

## 第2章の解釈について

### 論点1（取り込み状況の画面を、閲覧専用で先に作る）: 妥当
- AC2.3 は、取り込み状況の画面へのリンクを必須にしています。リンク先が 404 や「準備中」だと、AC2.1 と AC2.3 のどちらかに反します。実データ（`ingestion_runs`）を読む閲覧専用の画面は「準備中」ではありません。本物の機能を一部だけ先に出すものなので、AC2.1 の趣旨にも合っています。
- 実装するのは、AC3.3 のうち表示の部分だけです。AC3.1、3.2、3.4、3.5、3.7（データソースの状態、今すぐ取り込み、Cron、二重実行の防止）は Sprint 3 に残しています。プレースホルダも置かないので、先回りしすぎてはいません。
- ナビゲーションに「取り込み状況」を出すのも妥当です。実データで動く画面だからです。

### 論点2（集計元の3テーブルを、最小限の列で先に作る）: 妥当（注意点あり）
- テーブルが無いと、AC2.2 の「保存済みデータから集計した実際の値」を検証できません。列は、集計に必要なもの（値と算出不可の理由、判定の状態）だけです。書き込む経路も作らないので、F5 や F9 の中身を先に作っていることにはなりません。
- 注意点（今回の修正は不要。Sprint 9 の契約で扱ってほしい）: `ownership_judgments.status`（determined／undeterminable）は、Sprint 9 で追加される判定結果の4区分と情報が重なります。Sprint 9 では、「判定不能」を表す値を2か所に持たないようにしてください（`status` を結果から導出する、制約で整合させる、など）。ダッシュボードの「判定できた銘柄数」の定義も、それに合わせて更新してください。
- `financial_metrics` の、値と理由の「どちらか一方だけが NULL でない」という制約は、AC5.3 と AC5.4（算出不可には理由を付ける）に合っています。

### 論点3〜6（各件数と「データが無い」の定義）: 妥当
- 「成功」と「一部失敗」だけを完了として数え、失敗は別に表示するという扱いは、ユーザーストーリー（古いデータで判断しない）に合っています。
- 「財務指標を算出できた」を「少なくとも一方」と定義し、内訳も表示するので、利用者が誤解しません。
- 空状態の判定を銘柄数 0 にし、銘柄がある場合の 0 件は実際の値として出すという区別は、AC2.3 の「ダミーの数値は表示されない」と矛盾しません。

## 修正依頼

### R1（必須）: 投入 SQL の日時が未来なので、C3-4 と C3-5 を書かれたとおりに検証できない
- 現在は 2026-09-24 03:24 UTC（12:24 JST）です。第6章の失敗の行は `started_at = 2026-09-24 12:00 UTC`、`finished_at = 12:01 UTC` で、今日の評価時点ではまだ来ていない時刻です。
- C3-5 は、実行中の行を `started_at = now()`（既定値）で追加します。この行の開始日時は失敗の行より古くなります。そのため、開始日時が最も新しい行は失敗の行のままで、「直近の実行に『実行中』と表示される」という期待値になりません（21:00 JST までに評価すると、正しく実装しても不合格になります）。
- C3-4 で一部失敗にした行は、`finished_at` が未来なので、相対表記が「◯時間後」や負の値になりえます。期待値が定まりません。
- 修正案（どちらでも可）:
  - 投入例の日時を、評価日より確実に前にする（例: 2026-09-20 と 2026-09-21）。そのうえで C3-3 と C3-4 の期待値（JST の表記）を直す。
  - または、日時を `now() - interval '...'` で相対的に指定し、期待値を「投入した時刻を JST で表示したもの」とする。
- あわせて、C3-5 の実行中の行には `started_at` を明示し、既存のどの行よりも新しい時刻にしてください。
- 相対表記の対象が未来の時刻（時計のずれ）のときの表示も決めてください（例:「たった今」に丸める）。Vitest で確認できる形にしてください。

### R2（必須）: C5-9 のコントラストの基準を数値にする
- 「低すぎない」では合否を判定できません。「本文と見出しは WCAG AA の 4.5:1 以上、補足の小さい文字（muted）も 4.5:1 以上、大きい文字は 3:1 以上」のように、閾値を書いてください。評価者は、計算した色（computed style）からコントラスト比を算出して確認します。

### R3（推奨）: 設定画面の「アカウント情報」に完了条件が無い
- 第4章で、設定画面に「アカウント情報」を表示するとしていますが、C 条件がありません。「ログイン中のメールアドレス（実際のセッションの値）が表示される」などを C1 か C5 に加えてください。何を表示するかを決めておかないと、見せかけの項目になるおそれがあります。

### R4（推奨）: 実行履歴が0件のときの「直近の実行」の表示を決める
- C3-1（銘柄3件、実行履歴0件）と C2-1 で、「直近の実行」の欄を出さないのか、「実行履歴なし」と出すのかが書かれていません。どちらかに決めて、期待値に書いてください。

### R5（推奨）: 集計が失敗したときの表示を、実際の画面でも確かめられるようにする
- C3-9 は Vitest だけで確認します。評価者は、例えば `revoke execute on function public.dashboard_summary() from authenticated;` を postgres で実行すれば、実際の画面でエラー表示を再現できます。確認後は grant で戻します。この手順と期待値（「ダッシュボードの集計を取得できませんでした」、件数も空状態も出ない、`/api/dashboard` は 5xx でエラーの JSON）を C3-9 に加えてください。

## そのほかの確認結果（修正は不要）
- AC2.1〜2.5 は、それぞれ C1、C3、C2 と C4、C5、C6 に対応しています。どれも UI、API、DB のいずれかで判定できます。
- 第6章の SQL の値は、既存の `stocks` の制約（`code` は4〜5文字の英数字、`company_name` は必須）と、提案されている制約（`finished_at` と `status` の整合、理由の XOR）の両方を満たしています。C3-3 の期待値（21:05 JST、66.7%、33.3%）の計算は正しいです（R1 の日時の問題を除く）。
- C3-6 で `generate_series` を使って銘柄を投入するときは、`code` の制約（`^[0-9A-Z]{4,5}$`）に合う値（例: `'8' || lpad(g::text, 4, '0')`）と `company_name` が必要です。評価者の側で対応するので、修正は任意です。
- C3-7 のキー名は「実装で確定させる」となっています。例の JSON のキー名をそのまま正式なものにすると、曖昧さが無くなります（推奨）。
- B2'（C7）は、E2E で戻る・進むの経路を検査するところまで含めて、Sprint 1 の評価の提案を満たしています。原因がフレームワーク側にあって解消できなかった場合でも、C7-1 は不合格のまま扱います。そのときは、契約を改訂して扱いを明示してください。
- AC1.8 のフッターは、新しい画面（`/imports`、`/settings`）にも表示されることを、C8-1 の抜き取り確認で見ます。
