## B1 の再確認（前回ラウンドの修正必須バグ）

### 長時間稼働した dev での対照実験
- 同じマシンで、修正後（:3000）と修正前（769a38c を一時的な git worktree に置いて :3001）の dev サーバーを同時に起動した。worktree は評価後に削除した。
- 約2分ごとに、C7-1 の経路 A と C7-2 の経路 B を各3回、両方のサーバーに対して実行した。時計のずれの再現は使っていない。

| 時刻（起動からの経過） | 修正後 | 修正前 |
|---|---|---|
| 15:05〜15:26（約5〜26分） | 10 回とも 0/6 | 10 回とも 0/6 |
| 15:28（約28分） | 0/6 | 1/6 |
| 15:31 | 0/6 | 2/6 |
| 15:33〜15:38 | 0/6（4 回） | 5/6（4 回） |
| 15:39〜15:40 | 0/6（2 回） | 6/6（2 回） |
| **合計** | **108 回中 0 回** | **108 回中 36 回** |

- 修正前で出た例外は、ラウンド 1 と同じ `'​MissingPage' cannot have a negative time stamp` だった。
- 修正前は約28分後から自然に再発したので、この環境は長時間稼働の再現条件を満たしている。そのうえで、修正後は一度も出なかった。
- 長く動かした修正後のサーバーで、開発時の対策（measure の丸め）を無効にした状態でも、6回中0回だった。無効にする方法は、`performance.measure` を書き換えできないプロパティとして固定する init script で、対策を入れられなかったという警告が出ることも確認した。404 の修正（global-not-found）だけで解消していると判断する。
- 許可を取り消した後のクライアント遷移（redirect の経路）は、長く動かした修正後と修正前の両方で0件だった。この経路は、時計のずれの再現でだけ例外になる（修正前の E2E で `'ImportsPage'`）。

### 時計のずれの再現
- 私のスクリプトで、`performance.timeOrigin` を 60 秒進めて試した。修正前は 6/6 で例外が出て、修正後は 0/6 だった。修正後で対策を無効にした状態でも 0/6 だった。
- 私の環境で自然に出た例外と、再現で出た例外は、コンポーネント名もメッセージも同じだった。再現の方法は妥当である。

### global-not-found と AppLink の副作用の確認
- **HTTP ステータス**: 8つのパス（`/nope`、`/foo/bar`、`/screening`、`/stocks/72030`、`/login/zzz`、`/auth/zzz`、`/imports/zzz`、`/settings/x`）はすべて 404 だった。タイトルは「ページが見つかりません | Quantis Light」で、アプリの枠（ヘッダー、ナビゲーション3項目、アカウント）とフッターが表示される（dev と prod）。
- **テーマ**: Cookie `theme=dark` で 404 を開くと、`data-theme="dark"` になる。404 の中のテーマメニューでライトに変えると、リロード後も保持される。
- **認証**: 未ログインの 404 のパスは proxy が 307 で `/login?next=` に送る。許可を取り消した状態で `/nope` を開くと、`/login?reason=revoked` に移って Cookie が破棄される。global-not-found の中の `redirect()` も正しく動く。404 の画面からのログアウトも正常。
- **AppLink**: 404 の中では `<a>`（文書遷移）、それ以外の画面では next/link のクライアント遷移のまま。ナビゲーション、テーマ、ダッシュボードの動作は変わっていない。
- **本番への混入**: prod のビルドで `performance.measure` は書き換えられておらず、クライアントの JS にも対策のコードや文言は含まれない。本番で出るコンソールのメッセージは、404 のドキュメントの読み込みログだけ。

## 改善提案（合格判定には影響しないが推奨）

### N1（Minor、Sprint 1 からの振る舞い）: 許可を取り消した後にナビゲーションで移動すると、取り消しの理由が表示されない
- 再現手順:
  1. owner でログインしてダッシュボードを開く。
  2. `admin_disallow_email` で許可を取り消す。
  3. ヘッダーの「取り込み状況」を押す。
- 実際の結果: `/login` に着くが、`?reason=revoked` は付かず、「利用許可が取り消されました」も出ない。認証の Cookie は0件になり、保護された内容は表示されない。
- 完了条件への影響: 無し。Sprint 1 の C6-7 と Sprint 2 の C8-1 は、どちらも「URL を開いた場合」の振る舞いを定めている。URL を開いた場合は、どの画面でも `/login?reason=revoked` になることを確認した。修正前のコードでも同じ振る舞いだった。
- 評価: Sprint 2 でナビゲーションができたため、最も自然な操作でこの経路を通るようになった。コンプライアンス（データを返さない）は守られているが、利用者はなぜログアウトしたのか分からない。後続スプリントで、ナビゲーション経由でも理由を表示するよう直してほしい。

### N2（Minor）: 存在しない配下のパスの 404 で、ナビゲーションの項目が現在の画面として強調される
- 再現: `/imports/zzz` を開くと、404 の画面なのに「取り込み状況」に `aria-current="page"` と下線が付く。`/settings/x` も同様。
- 原因: `isNavItemActive` が前方一致で判定しているため。後続スプリントで配下の画面（詳細など）ができると正しい動作になる。ただし 404 の画面では、項目を強調しないほうが誤解が少ない。
