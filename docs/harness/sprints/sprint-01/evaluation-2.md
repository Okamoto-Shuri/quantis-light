## B1 と B2 の再確認

### B1: 解消
- 評価1の再現手順（ログイン → 404 のパスを直接開く → 「ダッシュボードに戻る」 → ログアウト → 戻る）を、`/foo`、`/nope`、`/stocks/72030` の3パスで試した。dev では3回、prod では2回繰り返した。「戻る」の後、250ms ごとに 2.5 秒間観測し、さらに「戻る」「進む」「進む」と続けた。メールアドレスは一度も表示されなかった。
- 「戻る」の時のドキュメントの取得は `307 /foo → 200 /login` で、HTTP キャッシュからではなくサーバーから取り直している（修正前は、キャッシュから `404 /nope` を表示していた）。
- 追加で試したパターンもすべて問題なかった（dev と prod）。
  - ダッシュボードをリロードした後、別の画面からログアウトして「戻る」を2回押す。
  - 別タブでログアウトした後に、元のタブで「戻る」「進む」「リロード」を行う。元のタブに表示済みの画面が残るのは、ブラウザの仕様上避けられない。
  - 許可を取り消した後に「戻る」を押す。
- ログアウトの所要時間は 180〜245ms で、Clear-Site-Data による遅延は見られない。

### B2: 一部が残っている（B2'）
- 404 のパスを直接開いたときの例外と script タグの警告は、解消した（dev と prod の両方でコンソールエラーは 0 件）。
- ただし、次の B2' が残っている。

### B2'（Minor、dev 限定）: ログアウト後に「戻る」「進む」で 404 の履歴を通ると、`NotFound` で Performance.measure の例外が出る
- 重要度: Minor（`pnpm dev` だけで起き、`pnpm start` では出ない。保護された内容は表示されず、どの完了条件にも該当しない）
- 再現手順（dev。3回中3回再現した）:
  1. owner でログインする
  2. `/nope` を開く
  3. 「ダッシュボードに戻る」を押す
  4. ヘッダーの製品名を押す
  5. ログアウトする
  6. 「戻る」を2回押し、その後「進む」を押す
- 期待結果: 未処理の例外が出ない
- 実際の結果: 2回目の「戻る」と「進む」のたびに、`Uncaught TypeError: Failed to execute 'measure' on 'Performance': '​NotFound' cannot have a negative time stamp.` が出る。画面は `/login` で、開発オーバーレイに「1 Issue」と表示される
- 根拠: Playwright の `pageerror`。prod で同じ手順を2回試したところ、0 件だった
- メモ: 前回の `UnknownPage` と同じ種類の例外（React の開発用のパフォーマンス計測が、async のサーバーコンポーネントで起こすもの）で、コンポーネント名が変わっただけとみられる。フレームワーク側の問題の可能性が高いが、E2E の「404 で例外が出ない」テストは、直接開く経路しか見ていない。

## 改訂3の振る舞いの妥当性と副作用
| 項目 | 結果 | 確認内容 |
|---|---|---|
| Clear-Site-Data `"cache"` | 妥当 | `POST` の 204 と、破棄を伴う `GET` の 303 に付いている。許可ユーザーの `GET` には付かない。localhost は安全なコンテキストなので効く。本番の https も同じ |
| `POST /auth/signout` の CSRF | 妥当 | Origin が無い要求と `https://evil.example` からの要求は 403。同一オリジンからは 204 |
| `GET /auth/signout` | 妥当 | 許可ユーザーが外部からのリンクで開いても、セッションは維持され `/` または `next` に戻る。外部 URL の `next` は `/` に丸められる。未ログインの場合は `/login` に送られる。障害中はセッションを保持したまま `/login` に送られる |
| Auth 障害時の 503 | 妥当 | 503 はセッションを持つ要求だけで、未ログインは 401 のまま。AC1.6（未ログインは 401 または 403）に矛盾しない。データは含まれない |
| Send Email Hook | 妥当（副作用は軽微） | owner と intruder への OTP と recover は 403、Mailpit は 0 件。パスワードでのログイン、add-user、seed は正常。パスワードリセットもできなくなるが、スコープ外（契約第7章）で、運用は `--reset-password` で代わりになる |
| default privileges | 妥当 | postgres が public に作ったテーブルと関数に、anon と authenticated の権限が付かないことを、ロールバックする一時オブジェクトで確認した。`create extension pg_trgm` で作られる拡張の関数は、従来どおり authenticated と anon が実行できる（拡張には副作用が無い） |

## 改善提案（合格判定には影響しないが推奨）
- B2' を解消するか、少なくとも E2E の「404 で例外が出ない」テストに、戻る・進むの経路を加える。
- `POST /auth/v1/recover` は、アカウントが存在するアドレスでは 403（フックの拒否）、存在しないアドレスでは 200 を返す。そのため、公開キーでアカウントの有無を判別できる。ラウンド 1 の OTP（200 と 422）でも同様だったので新しい問題ではないが、本番では Auth の回数制限に頼ることになる。
- `pg_default_acl` を見ると、`supabase_admin` が public に作るオブジェクトには、今も anon と authenticated に権限が付く既定の設定が残っている。マイグレーションは postgres で実行されるので実害は無く、E2E の権限の検査が後から検出する。ただし、Studio などから supabase_admin として作成した場合は抜け道になる。CLAUDE.md に「テーブルはマイグレーションで作る」と明記することを勧める。
- 同じタブで開いたままの保護画面は、別タブでログアウトしても表示されたまま残る（ブラウザの仕様）。気になる場合は、今後 `BroadcastChannel` などで他のタブに通知することを検討してほしい。
