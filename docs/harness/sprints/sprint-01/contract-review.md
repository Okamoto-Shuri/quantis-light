## 判定: 修正依頼

契約の骨格はよくできている。AC1.1〜AC1.8 はすべて完了条件 C1〜C8 に対応しており、各手順は Playwright・curl・psql で実行できる。スコープも適切で、`public.stocks` と `GET /api/stocks` を先に作るのは AC1.6 と AC1.7 を実データの経路で検証するために必要な土台であり、先回り実装にはあたらない。評価環境には Node v22.15.0、pnpm、Docker（`/Applications/Docker.app`、`/usr/local/bin/docker`）、psql 17 がそろっており、第3章の起動手順はこの Mac で実行できる。

## 修正必須

### R1. `next` パラメーター検証の抜け道（オープンリダイレクト）
- 第4章のルールは「`/` で始まり `//` で始まらない」。このルールだと `/\example.com` が通る。ブラウザは `\` を `/` に正規化するため、`/\example.com` は `//example.com` と同じ意味になり、外部に遷移する。
- 修正内容: ルールを「`/` で始まる」「2文字目が `/` でも `\` でもない」「制御文字（タブ、改行など）を含まない」に強める。または、`new URL(next, 'http://localhost')` でパースし、origin が変わらないことを確かめる方式にする。
- C2-4 と、Vitest の単体テスト（C9-3）に次のケースを追加する: `/\example.com`、`%2F%5Cexample.com`、`/%09/example.com`、`https:example.com`、`javascript:alert(1)`。いずれも `/` に遷移すること。

### R2. 運用コマンドに完了条件が無い
第2章で `pnpm seed:users` と `pnpm auth:add-user` を成果物として約束している。特に `auth:add-user` は、仕様上ユーザーを追加する唯一の手段である。それなのに、どちらを検証する C 項目も無い。次の項目を追加してほしい（例として C10）。
1. `pnpm auth:add-user --email New.User@Quantis.local --password <p>` を実行すると、`private.allowed_emails` に小文字の `new.user@quantis.local` が入り、そのユーザーで画面からログインできる。
2. 同じコマンドをもう一度実行しても、エラー終了や重複行にならない（冪等である。既存ユーザーのパスワードを更新するのか、そのままにするのかも明記する）。
3. 既存アカウントの `intruder@quantis.local` に `auth:add-user` を実行すると許可リストに追加され、ログインできるようになる。これで、フック（Custom Access Token Hook）が許可リストを実行時に参照していることを確かめる。確認後に許可リストから行を削除すると、再びログインが拒否される。
4. 引数が欠けているとき、メール形式が不正なときは、使い方を表示して 0 以外の終了コードで終わる。
5. `NEXT_PUBLIC_SUPABASE_URL=https://example.supabase.co pnpm seed:users`（または契約が定める変数名で）を実行すると、URL を拒否して終了し、何も作らない。

### R3. 異常系の振る舞いが決まっていない（レート制限・Auth 停止）
- ローカルの Supabase Auth には、サインインの回数制限がある（`[auth.rate_limit]` の既定値は IP ごとに 5 分で 30 回程度）。評価での手動ログインと `pnpm test:e2e` を合わせると、上限に届くおそれが十分にある。その場合に画面が落ちたり、英語の生のエラーが出たりしても、今の契約では判定の基準が無い。
- 修正内容:
  1. 次の 2 つのケースで画面に出すメッセージを契約に明記し、完了条件に加える。どちらもクラッシュや英語の生エラー、未処理例外にしない。
     - 回数制限（429）: 例「ログインの試行回数が上限に達しました。しばらくしてから再度お試しください」
     - Supabase Auth に到達できない: 例「認証サーバーに接続できません」
  2. 確認手順も書く。例: `pnpm db:stop` の後にログインを押すと、上記のメッセージが表示され、Next.js のエラー画面にはならない。
  3. 評価と E2E が回数制限で不安定にならないように、`supabase/config.toml` のローカル用の上限値をどうするかを明記する（上限を上げるなら、その理由も書く）。

### R4. ログイン中に許可リストから外されたユーザーの扱い
- 仕様のコンプライアンス要件は「市場データは、ログイン済みで**許可された**ユーザーにしか表示・返却しない」である。今の設計では、画面の保護は `getUser` の確認だけである。そのため、ログイン中に許可リストから外されたユーザーは、アクセストークンの有効期限（既定 1 時間）までは画面を見続けられる。データは RLS で守られるはずだが、この点を確かめる完了条件が無い。
- 修正内容: 次の条件を追加する。「owner でログインした状態で、psql から `private.allowed_emails` の owner 行を削除する。その直後に `/api/stocks` を開くと、401/403 または `{"data":[]}` が返り、検証用の銘柄は含まれない。」あわせて、保護画面の振る舞いも明記する。サーバー側で許可リストも確認して `/login` に戻すのか、トークンの期限切れまで表示を許すのかを決める。前者が望ましい。確認後は行を元に戻す。

### R5. Auth と REST の直接経路の網羅が不足
C4-4 と C7 に次を追加する。
1. 匿名サインインの無効化: `curl -X POST .../auth/v1/signup -H "apikey: $ANON" -H 'Content-Type: application/json' -d '{}'` を呼ぶとエラーになり、`auth.users` に `is_anonymous = true` の行が作られない。`config.toml` で `enable_anonymous_sign_ins = false` であることも明記する。フックは、メールが null のトークン要求も拒否する。
2. OTP（マジックリンク）経由: `POST /auth/v1/otp` に `{"email":"stranger@example.com"}` を送っても、ユーザーは作られない。
3. private スキーマは PostgREST に公開しない: `curl .../rest/v1/allowed_emails -H "apikey: $ANON" -H 'Accept-Profile: private'` はスキーマ拒否のエラーになる。今の C7-2 は public スキーマしか見ていない。
4. 許可リストの確認手段: ログインのサーバーアクションが許可リストを確認する手段（RPC 関数など）を public に作る場合、`anon` と `authenticated` は実行できないようにする。そうしないと、公開キーで `/rest/v1/rpc/...` を呼ぶだけで、許可リストに入っているかを外部から判定できてしまう。完了条件: 公開キーで該当の RPC を呼ぶと、権限エラーになる。
5. （推奨）`POST /graphql/v1` に公開キーで `stocks` を問い合わせても、行が返らない。

### R6. 画面保護を middleware だけに頼らないことの確認
- 第4章には「保護された画面では、サーバー側でセッションを検証する」と書かれている。しかし、middleware を通らなかった場合にもそれが効くことを確かめる手順が無い。
- 修正内容: C1 に次を追加する。
  - `curl -sI http://localhost:3000/ -H 'x-middleware-subrequest: middleware:middleware:middleware:middleware:middleware'` の結果が、ヘッダーなしの場合と同じくリダイレクトになる（過去の Next.js middleware 回避の手口に対する確認）。
  - matcher が静的アセットを拡張子で除外している場合は、`/stocks/72030.png` や `/api/stocks.json` のようなパスが保護画面や銘柄データを返さないことを確認する。
  - `/api/stocks` のルートハンドラー自身もセッションを検証し、未ログインなら 401 を返す（middleware が無くても 401 になる）。この点を、ルートハンドラーの単体テストか設計記述で担保する。

## 修正推奨（任意。反映すると評価が確実になる）
- **メールアドレスの大文字小文字**: C2 に「`OWNER@Quantis.Local` と入力してもログインできる」を加える。許可リストは小文字で正規化すると決めているので、入力側の正規化も検証しておく。
- **ログアウト後の「戻る」**: Next.js App Router は、戻る・進むの操作ではクライアント側のルーターキャッシュ（RSC ペイロード）を再利用する。そのため、`Cache-Control: no-store` だけでは、ダッシュボードが再表示されるおそれがある。ログアウト後の遷移はフルリロード（`window.location.assign('/login')` など）にするか、`router.refresh()` と組み合わせることを勧める。C5-2 は、ソフトナビゲーションでダッシュボードへ行った後にログアウトし、「戻る」を2回押す手順でも確認する。
- **ダークモードの確認方法**: C9-5 の「OS をダークモードにする」は評価環境で再現しにくい。Playwright の `colorScheme: 'dark'`（エミュレーション）で確認すると明記し、E2E テストにもスクリーンショットかアサーションを1つ入れてほしい。
- **E2E テストの後片付け**: `pnpm test:e2e` が `public.stocks` に検証用の行を投入する場合は、終了時に削除することを明記する（C9-6 の「0 件」と矛盾させないため）。
- **C4-4 の期待レスポンス**: 許可リスト外ユーザーのパスワードログインについて、フックが拒否したときのステータスとエラー本文の例（例: `"error_code": "..."`、`access_token` を含まない）を載せておくと、判定がぶれない。

### N1. 許可の取り消し（C6-7）と、ログイン済みで `/login` を開いたときのリダイレクト（C2-6）が矛盾し、リダイレクトがループするおそれがある
- 第4章では、保護画面の共通レイアウト（サーバーコンポーネント）が「サインアウトさせて `/login?reason=revoked` に戻す」としている。しかし、Next.js のサーバーコンポーネントは Cookie を書き換えられない（`cookies().set` は Server Action、Route Handler、middleware の中でしか使えない）。そのため、レイアウトの中で `signOut()` を呼んでも、セッション Cookie は残る。
- Cookie が残ったまま `/login` を開くと、C2-6 の「ログイン済みなら `/` にリダイレクト」が働く。すると、次の遷移が無限に続く。
  `/` → `/login?reason=revoked` → `/` → …
  さらに、取り消し時に使うアクセストークンは期限内なので、`getUser` は成功し続ける。
- 修正内容: 次の3点を契約に明記する。
  1. セッションの破棄を、Cookie を書き換えられる場所で行う。例: レイアウトは `/auth/signout?reason=revoked` のような Route Handler にリダイレクトし、そこで `signOut()` と Cookie の削除を行ってから `/login?reason=revoked` へ遷移する。middleware で許可リストも確認する方式でもよい。
  2. C2-6 の「ログイン済みなら `/` へ」は、**許可リストに入っている**ユーザーだけに適用する。
  3. C6-7 に確認手順を追加する。
     - 取り消し後に `/` を開いた後、ブラウザの Cookie に `sb-...-auth-token` が残っていない。
     - 取り消し後のセッション Cookie を付けて `curl -sIL --max-redirs 5 http://localhost:3000/` を実行すると、ループせずに `/login?reason=revoked`（200）で止まる。

### N3. C2-4 の `/%09/example.com` の期待結果があいまい

## 注意事項（修正は任意。評価ではこの観点で確認する）
- `is_email_allowed` の権限について: Postgres は、関数の実行権限を既定で `PUBLIC` に与える。そのため、`anon` と `authenticated` から `revoke` するだけでは、`PUBLIC` 経由で実行できてしまう。`revoke execute ... from public, anon, authenticated` のように `PUBLIC` からも外す必要がある。C7-5 の `has_function_privilege` で検出するので、実装時に注意すること。
- C10-1 のパスワード `New-User-Pass-2026!` は、zsh の対話シェルでは `!` が履歴展開される。例示はシングルクォートで囲む（`--password 'New-User-Pass-2026!'`）とよい。
- C4-4 の「HTTP 403」は、フックが返す `http_code` を Auth サーバーがそのまま返すことを前提にしている。実装時に、ローカルの Supabase で実際のステータスを確かめること。403 以外になる場合は、契約の期待値を実測値に合わせる。「`access_token` を含まない」ことは必須のままとする。
