# Sprint 05 契約: F5 財務データの取り込みと指標の算出

## 1. 対象機能

F5 財務データの取り込みと指標の算出。J-Quants の財務情報（決算短信のサマリー、`/v2/fins/summary`）から、**通期の決算短信（実績）**の売上高と営業利益を取り込んで保存する。保存した通期実績から、銘柄ごとに次の2つを DB の1か所で算出して保存する。
- 売上CAGR（成長4年分）: 直近5期の通期実績から (FY0 / FY-4)^(1/4) − 1
- 営業利益率: 直近通期の営業利益 ÷ 売上高

算出できない場合は、理由のコードを保存する。取り込みの対象に「財務（`financials`）」を加え、Sprint 3・4 の取り込み基盤（実行履歴、二重実行の防止、応答の無くなった実行の後片付け）の上で動かす。起動経路は、手動（取り込み状況の画面）と Cron の2つ。Cron は財務専用のエンドポイントを別の時刻に動かす（第2章の11）。

保存した指標は、次の3か所で確認できる。
- 取り込み状況の画面の新しい区画「財務指標（売上CAGR・営業利益率）」
- 銘柄コードで確認するカード
- `GET /api/stocks` と新しい `GET /api/financials?code=`

ダッシュボードの「財務指標を算出できた銘柄数」（Sprint 2）は、このスプリントで保存する値から実際に集計される。スクリーニング（Sprint 6）と銘柄詳細（Sprint 7）は、ここで保存する指標の列と、通期実績のビューをそのまま使う。

あわせて、Sprint 4 の評価（`sprint-04/evaluation-1.md`）の改善提案を次のように扱う。
- **m4（性能）**: 指標を読み出しのたびに計算せず、**計算済みの値を普通の列として保存し、索引を付ける**（第2章の12）。Sprint 6 の全件の絞り込み・並べ替えは、関数を行ごとに評価しない。性能の完了条件を C12 に置く。`stock_listing_ages` ビュー自体の改善は、Sprint 6 で扱う（第9章）。
- **m1・m2・m3**: 取り込み状況の画面の「銘柄コードで確認」に手を入れるので、あわせて直す（第4章、C14）。
- **m5**: 注記のみ。対応しない。

### 仕様書の受け入れ基準（引用）

- AC5.1 データベースに通期売上 100 → 150 → 200 → 300 → 400（FY-4 → FY0）の銘柄を投入すると、売上CAGR は 41.4%（小数点以下1桁。(400/100)^(1/4) − 1）と表示される。
- AC5.2 直近通期の売上 1,000、営業利益 120 の銘柄の営業利益率は 12.0% と表示される。
- AC5.3 通期実績が4期分しかない銘柄は、CAGR が「算出不可（通期実績が5期未満）」と表示される。
- AC5.4 FY-4 の売上が0以下の銘柄、直近5期に変則決算を含む銘柄、営業利益が開示されていない銘柄は、それぞれ理由付きの「算出不可」になる。
- AC5.5 四半期決算や業績予想の値は、CAGR と営業利益率の算出に使われない（通期実績の値とのみ一致する）。
- AC5.6 （キーあり環境）取り込み後、財務指標を算出できた銘柄数がダッシュボードに反映される。
- AC5.7 算出ロジックには、上記のケースをすべて含む自動テストがあり、そのテストが通る。
- AC5.8 通期実績が6期分以上ある銘柄では、直近5期だけが CAGR の算出に使われる（6期前の値を変えても CAGR は変わらない）。

用語定義（仕様書「用語と算出ルール」より）:
- 直近4期の売上CAGR（成長4年分）: 直近の通期決算（実績）を含む連続した5つの通期売上高（FY0, FY-1, FY-2, FY-3, FY-4）から、CAGR = (FY0 / FY-4)^(1/4) − 1 で算出する。次の場合は「算出不可」とし、理由を表示する。
  - 直近5期の通期実績がそろわない場合
  - FY-4 の売上が0以下の場合
  - 5期のうちに、決算期変更による変則決算（12か月でない期間）を含む場合

  業績予想の値は使わない。
- 直近通期の営業利益率: 直近の通期実績の営業利益 ÷ 売上高。営業利益が開示されていない場合（一部の IFRS 企業など）は「算出不可（営業利益の開示なし）」とする。

## 2. 仕様上の論点と、このスプリントでの解釈

仕様を変えずに、次のように解釈する。評価者は、この解釈が妥当かも判断してほしい。
- 根拠は J-Quants の公式ドキュメント。いずれも 2026-09-24 に確認した。
  - 財務情報: https://jpx-jquants.com/ja/spec/fin-summary
  - 開示書類種別: https://jpx-jquants.com/ja/spec/fin-summary/typeofdocument
  - データ格納期間: https://jpx-jquants.com/ja/spec/data-spec
  - レートリミット: https://jpx-jquants.com/ja/spec/rate-limits
  - 更新タイミング: https://jpx-jquants.com/ja/spec/data-update

1. **使う API**
   - J-Quants API V2 の財務情報 `GET https://api.jquants.com/v2/fins/summary` を、Sprint 3・4 と同じ `x-api-key` ヘッダーで呼ぶ。
   - `code` か `date`（開示日）の少なくとも一方が必須。`code` だけなら「その銘柄の全期間分」、`date` だけなら「全上場銘柄の、その開示日の分」が返る。
   - 応答は `{"data":[...], "pagination_key": "..."}` の形。`pagination_key` があれば次のページを取る。
   - `cursor`（差分の取得）は Premium プランだけなので使わない。
   - 公式の記載で、実装に効くのは次の点。
     - **すべての項目が JSON の文字列**（数値も `"100529000000"` のような文字列）。
     - **値の無い項目は `null` ではなく空文字列 `""`**。
     - 単位の換算や丸めは J-Quants 側でしていない。
   - 使う項目は次のとおり。ほかの項目（配当、予想、BS、CF など）は読まない・保存しない。
     - `DiscDate`（開示日）、`DiscTime`（開示時刻）、`Code`、`DiscNo`（開示番号）、`DocType`（開示書類種別）
     - `CurPerType`（当会計期間の種類。`1Q, 2Q, 3Q, 4Q, 5Q, FY`）
     - `CurFYSt`・`CurFYEn`（当事業年度の開始日・終了日）
     - `Sales`（売上高）、`OP`（営業利益）、`NCSales`・`NCOP`（非連結。第2章の3でだけ使う）
   - 財務諸表（BS/PL/CF）`/v2/fins/details` は、公式のデータ格納期間の表で Premium プランだけなので使わない。

2. **「通期実績」の特定（AC5.5）**
   - 通期実績として扱うのは、次の3つをすべて満たす行だけ。
     - `DocType` が `FYFinancialStatements_` で始まる（決算短信。公式の開示書類種別の一覧の `FYFinancialStatements_Consolidated_JP`、`_Consolidated_IFRS`、`_NonConsolidated_JP` など）
     - `DocType` が `FYFinancialStatements_Consolidated_REIT` でない（REIT の決算期は通常6か月。そもそも `stocks` は内国株券だけなので対象外）
     - `CurPerType` が `FY`
   - 次の行は保存も算出もしない。**四半期決算と業績予想の値は、保存する経路が無い**。
     - 四半期決算短信（`1Q〜3QFinancialStatements_*`）
     - その他四半期決算短信（`OtherPeriodFinancialStatements_*`。変則決算の第5四半期など）
     - 業績予想の修正（`EarnForecastRevision`、`DividendForecastRevision` など）
   - 通期の決算短信の行にも、予想の項目（`FSales`、`FOP`、`NxFSales`、`NxFOP` など）がある。使うのは実績の `Sales`・`OP` だけ。
   - DB の通期実績のテーブルには、`document_type` が `FYFinancialStatements_` で始まる行しか入らない制約を付ける（第6章）。評価者が四半期の行を投入しようとしても拒否される。

3. **会計基準と連結・単体**
   - `DocType` の2番目の区切りが連結（`Consolidated`）か非連結（`NonConsolidated`）、3番目が会計基準を表す。
     - 会計基準: `JP` 日本基準、`US` 米国基準、`IFRS`、`JMIS`、`Foreign` 外国株
   - DB では、`document_type` から「連結か」と「会計基準」を生成列として導く。
   - 公式の留意点「項目名は日本基準が基準。IFRS・米国基準には経常利益の概念が無く空欄」のとおり、会計基準で項目名は変わらない。
     - 売上高は `Sales`、営業利益は `OP` を使う。
     - IFRS の企業で営業利益を開示していない場合は `OP` が空文字になり、営業利益率は「算出不可（営業利益の開示なし）」になる。
     - 米国基準でも同じ。
   - **使う値**:
     - 連結の短信: `Sales`・`OP`
     - 非連結の短信: `Sales`・`OP` を使い、空文字のときだけ `NCSales`・`NCOP` を使う。**判定は項目ごと**に行う（R3。`Sales` に値があり `OP` が空なら、売上高は `Sales`、営業利益は `NCOP`）。どちらを使ったかは保存しない（値だけを保存する）
     - 非連結の会社の値がどちらの項目に入るかは公式に記載が無い。キーのある環境で確かめる（第8章）。
   - **連結と単体、会計基準が5期の中で変わる場合**（子会社を持って連結に移った、日本基準から IFRS に移った、など）は、算出不可にしない。
     - 仕様が挙げる算出不可の理由に無く、上場から日の浅い成長企業ではよくある（除外すると条件①の対象から大きく漏れる）ため。
     - かわりに、指標に「基準の混在」の印（`revenue_cagr_mixed_basis`）を保存し、カードに「連結と単体、または会計基準が異なる期を含みます」と注記する。
     - 営業利益率は FY0 の1期だけで算出するので、混在は起きない。

4. **同じ期の複数の開示（訂正）**
   - 公式の記載は次のとおり。
     - 「訂正開示には新しい開示番号（`DiscNo`）が割り振られ、既存レコードは上書きされない」
     - 「訂正であることを示すフラグは無い。同一銘柄の同一会計期間のレコードを開示日時順に並べて確認する」
     - 「開示番号は開示順序を保証しない。順序の判定には `DiscDate`・`DiscTime` を使う」
   - そこで、同じ銘柄・同じ事業年度の終了日（`CurFYEn`）の通期の開示は、すべて別の行として保存する（主キーは 銘柄コード＋開示番号）。
   - 算出には、事業年度ごとに**開示日時が最も新しい1行**を使う。並べる順は次のとおり。
     1. 開示日（新しい順）
     2. 開示時刻（新しい順。空は最も古い扱い）
     3. 開示番号（大きい順）
   - 同じ開示番号の行を再び受け取ったとき（J-Quants 側のデータ修正など）は、値が変わっていれば上書きする。
   - **訂正の開示で一部の項目が空欄になる場合がある**（キーありの実データで確認。例: 最初の開示に営業利益があり、訂正の開示の営業利益が空）。そこで、売上高と営業利益は**項目ごとに、同じ出典・同じ期の開示のうち値のある最新のもの**を使う（第8章の R2 の対応。`financial_periods` で行う）。

5. **期の連続と変則決算**
   - 公式の記載は「本APIには決算期変更を直接示す項目はありません」。そこで、決算期変更は通期の開示の事業年度の長さから判定する。
   - **12か月の期**: 事業年度の日数（`CurFYEn − CurFYSt + 1`）が **358 日以上 371 日以下**の期を、12か月の期とする。
     - 暦の12か月（365・366 日）と、52・53 週決算（364・371 日）が入る。
     - 1か月の決算期変更（11か月 ≒ 334 日、13か月 ≒ 396 日）は入らない。
     - これ以外の期を**変則決算**とする。例: 3月決算から12月決算への変更で 2022-04-01〜2022-12-31（275 日）。
   - **連続**: 新しい期の開始日の前日が、1つ古い期の終了日と一致すること。一致しない（間が空いている、重なっている）場合は、そこで途切れているとする。
   - FY0 は、その銘柄の通期実績のうち、事業年度の終了日が最も新しい期（決算の実績。予想は第2章の2のとおり入らない）。FY-1〜FY-4 は、FY0 から連続してさかのぼった期。

6. **売上CAGR の算出と、算出不可の理由（優先順位つき）**
   - FY0 から連続する期を最大5期（FY0〜FY-4）までさかのぼる（途切れたらそこで止める）。この5期（以下「対象の期」）だけを使う。
     - 6期以上あっても、FY-5 より古い期は使わない（AC5.8）。
   - 次の順に判定し、最初に当てはまったものを理由として保存する（理由は1つだけ）。

     | 順 | 条件 | 理由コード | 表示 |
     |---|---|---|---|
     | 1 | 対象の期に変則決算がある（FY0 自身を含む） | `irregular_period` | 算出不可（直近5期に変則決算を含む） |
     | 2 | 対象の期が5期未満で、途切れた先に古い期が無い | `insufficient_periods` | 算出不可（通期実績が5期未満） |
     | 3 | 対象の期が5期未満で、途切れた先に古い期がある（間の期が欠けている、または期が重なっている） | `non_consecutive_periods` | 算出不可（直近5期の通期実績が連続していない） |
     | 4 | 対象の5期のどれかで、売上高が空（開示なし） | `revenue_not_disclosed` | 算出不可（売上高の開示がない期がある） |
     | 5 | FY-4 の売上高が0以下 | `base_revenue_not_positive` | 算出不可（FY-4 の売上高が0以下） |
     | 6 | FY0 の売上高が負 | `latest_revenue_negative` | 算出不可（直近期の売上高がマイナス） |
     | — | 上のどれでもない | （値を保存） | `41.4%` など |

   - 仕様の3つの理由（そろわない、FY-4 が0以下、変則）に加えて、4と6を置く。
     - 4: 5期のうちに売上高の無い期がある。仕様の「5期の通期売上高がそろわない」の一種。銀行など、売上高ではなく経常収益を開示する業種が当たる。
     - 6: 負の比の4乗根が定義できない。
     - 3: 「そろわない」の中で、欠けた期があることを区別する。
   - 3つの理由の順（変則 → 期数 → 値）は、「期の並びの問題」を「値の問題」より先に伝えるため。
   - FY0 の売上高が 0 のときは、CAGR は −100.0% になる（定義どおり計算できるので、算出不可にしない）。
   - 値は `(FY0 / FY-4)^(1/4) − 1` を DB の `numeric` で計算し、**小数点以下10桁に丸めて**比率で保存する（例: 0.4142135624）。
     - 丸める理由: `numeric` のべき乗は近似値なので、ちょうど 20% の比（2.0736）が 0.19999… にならないようにする。
     - 実測: `power(2.0736::numeric, 0.25)` は `1.2000000000000000`。

7. **営業利益率の算出**
   - FY0 の1期だけで算出する。次の順に判定する。

     | 順 | 条件 | 理由コード | 表示 |
     |---|---|---|---|
     | 1 | FY0 の営業利益が空（開示なし） | `operating_profit_not_disclosed` | 算出不可（営業利益の開示なし） |
     | 2 | FY0 の売上高が空 | `revenue_not_disclosed` | 算出不可（売上高の開示なし） |
     | 3 | FY0 の売上高が0以下 | `revenue_not_positive` | 算出不可（売上高が0以下） |
     | — | 上のどれでもない | （値を保存） | `12.0%` など |

   - 値は `営業利益 / 売上高` を小数点以下10桁に丸めて、比率で保存する。営業赤字は負の値のまま（算出不可にしない）。
   - FY0 が変則決算でも、営業利益率は算出する（仕様は変則決算を CAGR の理由にだけ挙げている）。カードの通期実績の表で、その期に「変則決算」の印が付く。

8. **表示の丸め（Sprint 4 の考え方と同じ）**
   - 表示は**百分率の小数点以下1桁に切り捨て**（負の方向へ。`floor`）にする。例: 0.4142135624 → `41.4%`、0.12 → `12.0%`、0.1999999 → `19.9%`、−0.0123 → `-1.3%`。
   - 理由: 小数点以下1桁までの閾値 X% に対して、「表示の値 ≥ X」と「保存した値 ≥ X」が必ず一致する。
     - 条件①・②は「以上」の判定。四捨五入だと、19.96% が「20.0%」と表示されるのに「20%以上」を満たさない、という食い違いが起きる。
     - Sprint 4 の上場年数は「以内」の判定なので、切り上げにした。
   - **Sprint 6 の絞り込みと並べ替えは、保存した値（`revenue_cagr`、`operating_margin`）で行う**。表示用の値は DB の生成列で作る（`*_display_pct`）。アプリでは丸めない。
   - 期の表示は `YYYY/MM期`（事業年度の終了日の年月。例: `2025/03期`）。CAGR の期間は `2021/03期 → 2025/03期（4年）` の形（仕様 AC7.3 の例に合わせる）。
   - 金額は **百万円**の単位で、3桁区切りの整数（四捨五入）で表示し、見出しに単位を書く。J-Quants の値は円単位とみなす（公式に単位の記載は無い。キーのある環境で確かめる。第8章）。比率の指標は単位に依存しない。

9. **取得できる期間と、取り込みの方法**
   - 公式のデータ格納期間は、Standard プランで財務情報が「10年前まで」。
   - 必要なのは FY-4 の開示まで。FY0 の開示は、遅くとも約1年3か月前（決算の3か月後が期限）。FY-4 はその4年前なので、約5年3か月前になる。
   - そこで、取り込む開示日の範囲（以下「取得範囲」）を**実行日（日本時間）の6年前の日から実行日まで**とする（定数。環境変数にはしない）。
     - 6年にする理由: 5年3か月に余裕を持たせる。また、多くの銘柄で6期目も入り、AC5.8 を実データでも確かめられる。
     - プランの10年の内側なので、期間外の応答は起きない。
   - **開示日（`date=`）ごとに全銘柄を取得する**。
     - 銘柄ごと（`code=`）に取ると、全銘柄で約 3,800 回かかる。
     - 開示日ごとなら、6年分の営業日で約 1,470 回で済み、毎日の差分も1〜数回で済む。
     - 公式のベストプラクティス「日付のみの指定で全銘柄のデータを取得」とも合う。
     - **要求する開示日は、東証の営業日だけにする（R1）**。実行のはじめに、J-Quants の取引カレンダー `GET /v2/markets/calendar?from=<取得範囲の開始日>&to=<実行日>`（公式: https://jpx-jquants.com/ja/spec/mkt-cal 。Standard で使える。応答は `Date` と `HolDiv`）を1回（ページ送りを含む）取る。休日区分 `HolDiv` が `1`（営業日）か `2`（東証半日立会日）の日を営業日とし、`0`（非営業日）と `3`（非営業日・祝日取引あり）は要求しない。TDnet の適時開示は東証の営業日に行われるため。
     - 取引カレンダーの取得に失敗したとき（キーの無効・欠如の 403、401、429 はその実行を打ち切る。それ以外の失敗と形式の違い）は、土日を除いた平日で代用し、`details.calendar = "weekdays_fallback"` を記録する（その実行に限る）。この場合、平日の祝日の `date=` には行0件の 200 が返ると想定する（キーのある環境で確かめる。第8章）。
   - **取得済みの開示日の記録**: 開示日ごとに、全ページの取得と保存が済んだら「取得済み」を DB に記録する。保存と記録は1つのトランザクションで行う。
   - **処理する開示日の順番**:
     1. 直近7日（実行日の6日前〜実行日）の営業日（取得済みでも毎回取り直す）
     2. 取得範囲のうち、まだ取得していない営業日。新しい順
   - 1 で直近を取り直す理由:
     - 公式の更新タイミングは「18:00頃（速報）、24:30頃（確報）」「反映までに時間を要する場合がある」。
     - 夜の実行で取った当日の速報を、翌日以降に確報で取り直す。
   - 2 を新しい順にする理由: 直近の通期実績（営業利益率）が早くそろう。
   - `DiscDate`（開示日）が要求した日と違う行があっても、そのまま保存する（開示日は保存した値で扱う）。
   - **初回の取り込みにかかる時間**: 約 1,470 回で、1回の実行（約190回。第2章の10）では終わらない。
     - Cron なら約9日、手動で続けて押せば約9回で取得範囲を埋める。
     - 取得範囲を埋めるまでは、古い期がまだ無いので、多くの銘柄が「通期実績が5期未満」になる。
     - これを誤解させないよう、最後に終わった財務の実行の `datesRemaining` が1以上の間は、区画とカードに「開示日の取得が完了していないため、『通期実績が5期未満』には取り込み途中の銘柄が含まれます（取得済み N / M 日）」と表示する。
   - 一括ダウンロード（`/v2/bulk/*`）は、キーが無いとファイルの形式（圧縮、CSV の列）を確かめられないため、このスプリントでは使わない（第9章）。

10. **呼び出し回数と時間の制限（一部完了と再開）**
    - 公式のレートリミットでは、`/fins/summary` は**プランにかかわらず 1 分あたり 60 回**の専用枠。429 には `Retry-After` が付かない。
    - 財務の取り込みでは、要求の間隔を **1,100 ミリ秒以上**あける（1 分あたり 55 回以下）。間隔は**前の要求の開始から次の要求の開始まで**で測る（R6。公式の制限は1分あたりの要求の数なので、応答を待った時間も間隔に含めてよい）。取引カレンダーの要求も同じ間隔で数える。
    - 時間は Sprint 4 と同じく、実行（Cron ではルート）の開始から **210 秒**を過ぎたら新しい要求を始めない。1回の要求のタイムアウトは 30 秒で、`maxDuration = 300` に収まる。
    - 1回の実行で約 190 回の要求になる。取り込みきれなかった開示日は、取得済みの記録が無いので、次の実行で自然に続きから処理する。
    - 429 を受けたら、その実行を打ち切る（待ってからの再試行は Sprint 11）。
    - 開示日ごとの取得の失敗（500、210、形式の違いなど）が **5 回続いたら**、その実行を打ち切る（`stoppedReason: "consecutive_failures"`）。プランの範囲外などで毎回失敗する場合に、190 回の要求を無駄にしないため。

11. **Cron と手動**
    - 手動取り込みの対象の選択に「財務（決算短信）」を加える。
    - **Cron は財務専用のエンドポイント `GET /api/cron/financials` を、毎日 22:00（日本時間。`0 13 * * *`）に動かす**。`vercel.json` の `crons` に2つ目を加える。
      - `/api/cron/daily`（20:00。銘柄マスタ → 株価）に3つ目の対象として足すと、株価の初回の取り込み（210 秒を使い切る）と時間を取り合い、財務がまったく進まない日が続く。
      - 別の関数の呼び出しにすれば、それぞれが 300 秒を使える。
      - Vercel の Hobby プランでは、Cron の起動時刻が指定の時間帯（1時間）の中でずれることがある。20:00 の実行（最大で 20:59 開始、5分以内に終わる）と重ならないよう、2時間あける。
      - 重なった場合は、Sprint 3 の二重実行の防止で 409 になり、その日の財務は動かない（翌日に続きから処理する）。
    - 22:00 は財務情報の速報（18:00頃）の後。確報（24:30頃）は、翌日の実行で直近7日を取り直すときに入る。
    - `/api/cron/financials` の認証、`HEAD` の 405、409 の扱いは `/api/cron/daily` と同じにする。認証の処理は共通にする。

12. **保存の形式と性能（m4）**
    - 通期の開示を保存するテーブル（`financial_statements`）と、事業年度ごとに最新の開示を1行にするビュー（`financial_periods`）を置く。
    - 指標は `financial_metrics`（Sprint 2 で作った表）に**普通の列として計算済みの値を保存**し、索引を付ける。
    - **計算は DB の1か所（関数）で行い、`financial_statements` を変更すると、同じトランザクションの中でトリガーが、変更された銘柄の指標を計算し直す。**
      - 取り込みでも、評価者の直接投入・更新・削除でも、同じ経路で指標が更新される。
      - AC5.8 の「6期前の値を変える」も、`update` するだけで確かめられる。
      - アプリ（TypeScript）では指標を計算しない。DB の値を表示するだけ。
    - Sprint 6 の絞り込み（`revenue_cagr >= 0.2 and operating_margin >= 0.1` など）と並べ替えは、索引のある列を読むだけになる。行ごとの関数の評価は無い。
    - `financial_metrics` の行は、通期実績が1件以上ある銘柄にだけ作る。通期実績の無い銘柄は行が無く、「財務データ未取り込み」と表示する。
    - 通期実績をすべて削除すると、その銘柄の行も消える。

13. **上場から日の浅い銘柄（仕様上の限界）**
    - J-Quants の財務情報は決算短信のデータなので、上場前の期の通期実績は無い。上場後の最初の決算短信も、その期の1期分だけ。
    - そのため、上場後の通期決算が5回に満たない銘柄は、必ず「算出不可（通期実績が5期未満）」になる。上場からおおむね4年未満の銘柄が当たる。
    - 条件①と条件③（上場5年以内）を両方満たせるのは、上場後およそ4〜5年の銘柄になる。これは仕様の定義から来る性質で、補正はしない。
    - 契約レビューの U1 を受けて、ユーザーは「EDINET で上場前の期を補う」を選んだ（仕様の改訂2、F15。新しい Sprint 9）。Sprint 5 では決算短信の値だけで算出し、上の振る舞いは想定どおり（仕様の F5 の補足）。Sprint 6〜8 の間の注記は AC6.12 で扱う。

14. **出典に依存しない保存形式と算出（仕様の改訂2）**
    - 仕様の改訂2は、「算出の定義は各期の値の出典に依存しない」「出典の優先順位は 決算短信 → 有価証券報告書 → 有価証券届出書」「EDINET の書類は決算短信に無い期を補うだけ」と定めた。Sprint 9 で EDINET の期が加わっても、算出の関数を変えずに済むよう、次の3層に分ける。
      1. **出典ごとの保存**: 決算短信は `financial_statements`（第6章）。Sprint 9 は、EDINET の書類の期を別のテーブルに保存する（このスプリントでは作らない）。
      2. **期の選択（`financial_periods` ビュー）**: 出典ごとの候補を1つにまとめ（Sprint 5 の候補は決算短信だけ）、銘柄・事業年度の終了日ごとに1行を選ぶ。選ぶ順は、出典の優先順位（`source_priority`。決算短信 = 1、有報 = 2、届出書 = 3）→ 同じ出典の中で新しい書類（決算短信は第2章の4の順）。各行は、出典（`source`。このスプリントでは `"tdnet_summary"`＝決算短信）、出典の書類の識別子（`source_document_id`。決算短信は開示番号）と日付（`source_document_date`）を持つ。Sprint 9 は、このビューに候補を1つ足すだけで済む（ビューの置き換えのマイグレーション）。
      3. **算出（純粋な関数）**: 算出の核は、期の配列（事業年度の開始日・終了日、売上高、営業利益、連結か、会計基準）だけを受け取って指標を返す、データを読まない関数にする（`financial_metrics_from_periods(jsonb)`）。出典の列は受け取らない（渡しても無視する）。再計算の関数は、`financial_periods` から銘柄ごとの期を集めて、この関数を呼び、`financial_metrics` に保存する。Sprint 9 は、EDINET のテーブルにも同じ再計算の関数を呼ぶトリガーを付ける。
    - 期の連続・変則決算・理由の優先順位・丸めは、出典を問わず同じ規則（第2章の5〜8）。出典が加わって変わるのは「そろう期の数」だけ（仕様のとおり）。
    - 「基準の混在」の印（`revenue_cagr_mixed_basis`）は、出典ではなく「連結か」と「会計基準」だけで決める。出典の混在（「補完あり」の印、AC15.3）は Sprint 9 で、`financial_periods` の `source` から作る。
    - カードの通期実績の表には、期ごとの出典（「決算短信」）の列を置く（仕様の改訂2の「出典は詳細の表では期ごとに小さなラベル」に合わせる。このスプリントでは常に「決算短信」）。

## 5. 取り込み処理の振る舞い（財務 `financials`）

1. **開始**: Sprint 3 と同じ DB 関数で、実行を `target = 'financials'`、`status = 'running'` で記録する（二重実行の防止と後片付けも同じ）。
2. **キーの確認**: `JQUANTS_API_KEY` が未設定なら、外部 API を呼ばずに「失敗」、処理件数 0、「J-Quants の API キーが設定されていません」。
3. **銘柄マスタの確認**: `public.stocks` が0件なら、外部 API を呼ばずに「失敗」、「銘柄マスタが未取り込みのため、財務情報を取り込めません。先に銘柄マスタを取り込んでください」。
4. **対象の開示日**: 取引カレンダーを取得し、第2章の9の順番で営業日の一覧を作る（実行日は日本時間）。
5. **開示日ごとの取得**
   - `GET /v2/fins/summary?date=YYYY-MM-DD` を、ページ送りを含めてすべて取得する。
   - 応答の扱い（公式の response-status と Sprint 4 の分類に基づく）:

     | 応答 | 扱い |
     |---|---|
     | 200（全ページ） | 通期実績の行を保存し、その開示日を取得済みにする（行0件でも取得済み） |
     | 403 で、本文の `message` がキーの無効・欠如（Sprint 4 と同じ文言） | **すぐに打ち切る**。Sprint 3 の 403 の文言 |
     | 401、429 | すぐに打ち切る。Sprint 3 の文言 |
     | 上記以外の 403、400、210、500 など、接続できない、形式の違い（`data` が配列でない、JSON でない） | その開示日だけ失敗に数える（取得済みにしない）。次の開示日へ進む。5回続いたら打ち切る |

   - 2ページ目以降で失敗したら、その開示日は何も保存しない（途中のページだけを保存しない）。
6. **行の選別と検証**（第2章の2・3）
   - 全行で `Code` と `DocType` が文字列であることを確かめる。欠けていれば、その開示日の形式の違い。
   - `DocType` が `FYFinancialStatements_`（REIT を除く）で始まる行だけを、通期実績の候補にする。
   - 候補の行は次の値を検証する。
     - `DiscNo`: 空でない
     - `DiscDate`: `YYYY-MM-DD`
     - `DiscTime`: 空か `HH:MM` か `HH:MM:SS`
     - `CurPerType`: `FY`
     - `CurFYSt`・`CurFYEn`: `YYYY-MM-DD` で、終了日 > 開始日
     - `Sales`・`OP`（と `NCSales`・`NCOP`）: 空文字か、`^-?\d+(\.\d+)?$`
   - 検証に通らない行は保存せず、`invalidRows` に数える（その開示日のほかの行は保存し、開示日は取得済みにする）。
   - `Code` が `public.stocks` に無い行は保存せず、`skippedUnknownCode` に数える。
   - `stocks` に無いコードの開示を後で取り直すのは、直近7日の取り直しだけ。銘柄マスタは同じ日の 20:00 に更新されるので、通常は起きない。
7. **保存**
   - 開示日ごとに、DB 関数（service_role のみ）で、1つのトランザクションとして次を行う。
     1. 通期実績の行を追加する（同じ 銘柄コード＋開示番号 の行は、値が違うときだけ上書きする）
     2. その開示日を取得済みにする（受け取った行数を記録する）
     3. 実行の `processed_count` に、追加した行数と上書きした行数の和を足す
   - 実行がすでに「実行中」でなければ（後片付けで「失敗」にされていたら）、保存せずに処理をやめる。
   - 保存のトリガーが、変更のあった銘柄の指標を計算し直す（第2章の12）。
8. **要求の間隔と時間**: 前の要求の開始から 1,100 ミリ秒以上あける。開始から 210 秒を過ぎたら、新しい要求を始めない（第2章の10）。
9. **終了**
   - `processed_count` は、この実行で追加・上書きした通期実績の行数。
   - 結果とエラーメッセージは次のとおり。

     | 状況 | 結果 | エラーメッセージ |
     |---|---|---|
     | 対象の開示日をすべて取得した | 成功 | なし |
     | 時間内に処理しきれなかった | 一部失敗 | `時間内に処理しきれなかったため、残り 1,380 日分の開示日は次回の取り込みで処理します` |
     | 取得に失敗した開示日があった | 一部失敗（取得できた開示日が0なら失敗） | `3 日分の開示日で財務情報を取得できませんでした。次回の取り込みで再試行します` |
     | 取得の失敗が5回続いて打ち切った | 取得できた開示日が1日以上なら一部失敗、0なら失敗 | `財務情報の取得に5回続けて失敗したため中断しました（最後の応答は HTTP 500）` |
     | 形式の違う行があった | 一部失敗 | `2 件の開示は形式が想定と異なるため保存しませんでした` |
     | 429 で打ち切った | 取得できた開示日が1日以上なら一部失敗、0なら失敗 | Sprint 3 の 429 の文言。一部失敗なら、続けて `残り N 日分の開示日は次回の取り込みで処理します` |
     | 401、またはキーの無効・欠如の 403 で打ち切った | 同上 | Sprint 3 の文言 |
     | 保存に失敗した | 同上 | `財務情報の保存に失敗しました` |
     | 予期しない例外 | 失敗 | Sprint 3 と同じ（「実行中」のまま残さない。保存済みの件数は残す） |

   - 複数に当てはまるときは、上の順に「。」でつなぐ。
   - エラーメッセージ、`details`、ログに、キーの値と応答の本文（財務の値、`message` の文字列）を含めない。
10. **`details`**（市場データそのものは入れない）:
    ```json
    {
      "windowStart": "2020-09-24", "windowEnd": "2026-09-24", "calendar": "jquants",
      "datesInWindow": 1469, "datesFetchedBefore": 0,
      "datesFetched": 185, "datesFailed": 0, "datesRemaining": 1381,
      "recentDates": 5,
      "rowsReceived": 12034, "annualRows": 1201, "savedStatements": 1180,
      "skippedUnknownCode": 21, "invalidRows": 0,
      "apiCalls": 190, "stoppedReason": null,
      "lastFailedStatus": null
    }
    ```
    - `calendar`: `"jquants"`（取引カレンダーの営業日）か `"weekdays_fallback"`（平日で代用）
    - `datesInWindow`: 取得範囲の営業日数
    - `datesFetchedBefore`: 開始時点で取得済みだった営業日数
    - `datesFetched`・`datesFailed`: この実行で取得できた日数・失敗した日数（直近の取り直しを含む）
    - `datesRemaining`: 終了時点で、取得範囲に残る未取得の営業日数
    - `recentDates`: 直近7日の取り直しの日数
    - `stoppedReason`: `null`、`"time_budget"`、`"rate_limited"`、`"unauthorized"`、`"consecutive_failures"`、`"save_failed"` のいずれか

### C5. 財務の取り込みの結合テスト（`pnpm test:db`。fetch と時計だけを差し替え、ネットワークに出ない）
フィクスチャは J-Quants V2 の `fins/summary` の公式の項目名を持つ形にする。
- すべて文字列で、空は `""`。
- 公式のサンプルの全項目を含む行を最低1つ入れる。
- コードは `99990`〜`99999` にする。
- テストの最後に、作った `stocks`、`financial_statements`、`financial_fetched_dates`、`ingestion_runs` の行を削除する。
1. **初回**: 銘柄マスタに 99991〜99994 がある状態で、実行日を 2026-09-24（木）に固定する。
   - 取得範囲は 2020-09-24〜2026-09-24。最初の要求は取引カレンダー（`/v2/markets/calendar?from=2020-09-24&to=2026-09-24`）。フィクスチャのカレンダーで 09-21（月）と 09-23（水）を非営業日（`HolDiv: "0"`）、09-19（土）を `"3"` にすると、続く財務の要求は直近7日の営業日の 09-24、09-22、09-18 の3回で、土日・祝日（09-19〜09-21、09-23）は要求しない。
   - ある日の応答は2ページ（`pagination_key`）で、次の行を含む。
     - 99991 の通期（連結・日本基準）
     - 99992 の通期（非連結で、`Sales` が空、`NCSales` に値）
     - 99993 の四半期
     - 業績予想の修正
     - 銘柄マスタに無い `13010` の通期
     - `CurFYEn` が壊れた通期の行
   - 結果:
     - 99991 は `Sales`・`OP` の値、99992 は `NCSales`・`NCOP` の値で保存される。
     - 四半期・予想の修正・`13010`・壊れた行は保存されない（`skippedUnknownCode = 1`、`invalidRows = 1`）。
     - その日は取得済みになる。
     - 実行は「一部失敗」で、エラーは「1 件の開示は形式が想定と異なるため保存しませんでした」。
     - `processed_count` は保存した行数と一致する。
     - `financial_metrics` が計算されている。
   - 各要求に `x-api-key` が付き、URL は `…/v2/fins/summary?date=YYYY-MM-DD`（2ページ目は `&pagination_key=`）。
2. **続きから（時間切れ）**: 時計を差し替え、途中で 210 秒を超えたことにすると、それ以降の要求は無い。
   - 実行は「一部失敗」で、エラーは「時間内に処理しきれなかったため、残り N 日分の開示日は次回の取り込みで処理します」。`stoppedReason = "time_budget"`。
   - 次の実行では、直近7日の営業日を取り直したあと、取得済みの開示日を飛ばして、未取得の日から新しい順に要求する。
   - 取得範囲をすべて取得済みにすると「成功」になる。以降の実行の要求は、取引カレンダーと直近7日の営業日の分だけ。
3. **取り直しと上書き**: 直近7日の取り直しで、同じ開示番号の行の `Sales` が変わっていれば上書きされ、指標も計算し直される。値が同じなら `processed_count` に数えない。
4. **キー未設定**: fetch は呼ばれず、「失敗」「J-Quants の API キーが設定されていません」。
5. **銘柄マスタが0件**: fetch は呼ばれず、「失敗」「銘柄マスタが未取り込みのため、財務情報を取り込めません。先に銘柄マスタを取り込んでください」。
6. **403・401・429**
   - 最初の要求が 403 で、本文がキーの無効（`The incoming api key is invalid or expired.`）またはキーの欠如（`The api key is required.`）の場合: **要求はちょうど1回**で「失敗」、Sprint 3 の 403 の文言。
   - キー以外の本文の 403: その日だけ失敗に数えて次へ。
   - 途中の 429: そこで打ち切り、保存済みは残り、「一部失敗」。
   - 401: 打ち切り。
   - どの場合も、エラーメッセージ・`details`・ログに本文の文字列が含まれない。
7. **開示日ごとの失敗と連続失敗**
   - 1日だけ 500 → その日は取得済みにならず、次の実行で再び要求される。エラーは「1 日分の開示日で財務情報を取得できませんでした。次回の取り込みで再試行します」。
   - 2ページ目だけ 500 → 1ページ目の行も保存されない。
   - 210 と 400 も、その日だけの失敗になる。
   - 5回続けて失敗 → 要求はちょうど5回で打ち切り、`stoppedReason = "consecutive_failures"`、取得できた日が0なので「失敗」。
8. **形式の違い**: `data` が配列でない、JSON でない → その日の失敗。`Code` の欠けた行がある → その日の失敗。
9. **要求の間隔**: 時計を差し替え、連続する要求の**開始時刻の差**がどれも 1,100 ミリ秒以上であることを確かめる。応答に 1,500 ミリ秒かかる場合は、待ちを入れずに次の要求を始める（開始から開始で測る。R6）。
10. **後片付けされた実行**: 実行の途中で、その行を DB で `failed` に変えると、それ以降の保存は行われない。行は `failed` のまま上書きされない。
11. **保存の単位**: 開示日の途中で例外を投げさせても、それまでに保存した開示日の行・取得済みの記録・`processed_count` は残る。例外を投げた開示日の行と記録は、どちらも残らない（1つのトランザクション）。
12. **取引カレンダー（R1）**: カレンダーが 500・形式の違いなら、平日で代用して続け（`details.calendar = "weekdays_fallback"`）、結果に影響しない。カレンダーがキーの無効の 403 なら、要求はちょうど1回で「失敗」。`HolDiv` が `0`・`3` の日は要求しない。

  - 非連結の決算短信（`FYFinancialStatements_NonConsolidated_*`）の値が、`Sales`・`OP` と `NCSales`・`NCOP` のどちらに入るか（両方に対応する）。

  - 銀行・証券・保険など、売上高ではなく経常収益や営業収益を開示する会社で、`Sales` に何が入るか。
    - 空なら「売上高の開示がない期がある」「売上高の開示なし」になる。
