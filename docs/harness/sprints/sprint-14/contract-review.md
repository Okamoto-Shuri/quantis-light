## 修正必須

### R1: 上限に達したユーザーが登録済みの銘柄を追加すると、冪等にならず 409 になる

- 第2章の1の設計は次の組み合わせです。
  - 「insert で 500 件あれば拒否する（BEFORE INSERT のトリガー）」
  - 「追加は `insert … on conflict do nothing` で冪等」
- PostgreSQL は、BEFORE INSERT の行トリガーを、ON CONFLICT の重複の確認より**先に**実行します。評価者が一時テーブルで確かめました。
  - 1行ある表に、件数で拒否するトリガーを付ける。
  - `insert … values (1) on conflict do nothing` を実行すると、`ERROR: limit` になる。
- その結果、次のことが起きます。
  - 500 件のユーザーが登録済みの銘柄に `PUT /api/watchlist/<code>` を送ると、200 ではなく 409 `watchlist_limit` になる。
  - 499 件のときに同じ銘柄の追加を2つ同時に送ると、片方が 409 になる。
  - どちらも第2章の1の「冪等」と第4章の PUT の「既に登録済みなら 200」に反します。
- 直し方（どちらでも可。契約にどちらかを書く）:
  - トリガーが、同じ (`user_id`, `code`) の行が既にあれば上限の確認を飛ばす（ロックを取った後に確かめる）。
  - または、API が先に存在を確かめる。ただし、直接の insert（PostgREST）でも冪等にするなら、トリガーで対処する方がよいです。
- 完了条件への追加:
  - C1-8: 500 件のとき、登録済みの銘柄への `PUT` は 200 で、行は変わらない。
  - C7-1: 499 件のユーザーで同じ銘柄の insert を2つ並行に行うと、両方とも成功して1行になる。

### R2: 記録の失敗が、日次の取り込みそのものを止める

- 記録は `start_ingestion_run` と同じトランザクションで作ります（第2章の5）。そのため、`capture_screening_snapshot` が例外を投げると、`start_ingestion_run` も失敗します。例外の原因の例は次のとおりです。
  - 将来のスキーマの変更
  - 記録の制約違反
  - タイムアウト
- すると `/api/cron/daily` は 500 になり、銘柄マスタと株価の取り込みが**行われません**。
  - Sprint 12（日次取り込みの信頼性）で守った経路が、表示用の機能に依存することになります。
  - C7-1 は「開始が失敗したら記録も残らない」側しか確かめていません。
- 直し方（推奨）:
  - 記録の呼び出しを、`start_ingestion_run` の中の例外を捕まえるブロック（セーブポイント）で包む。
  - 失敗しても実行は開始し、`ingestion_runs.details` に記録の失敗を残す（例 `snapshot: "failed"`。エラー文は決まった文言だけ）。
  - このとき、比較には前回の記録がそのまま使われます。`changes-cycle` が古い日付を示すので、利用者を誤らせません。
- 完了条件への追加（C7-1、`pnpm test:db`）:
  - トランザクションの中で記録を強制的に失敗させても、`start_ingestion_run('stock_master','cron')` は `started: true` を返し、実行の行ができる。
  - 失敗のさせ方の例: `screening_snapshot_stocks` に一時的に満たせない check 制約を付ける。
- もし「記録できないなら取り込みも止める」を選ぶなら、その理由を契約に書いてください。その場合は、ユーザーの判断事項にするのが適切です。

### R3: 判定の式を1か所に置く条件（C7-2）を、今の書き方では満たせない

- `screen_stocks` は、`included` のほかに除外の件数も出しています。
  - 除外の件数は `excl_unavailable`・`excl_undet`（評価者が今の定義で確認）。
  - これらは「算出不可で除外」「判定不能で除外」を、状態から式で求めています（`ok_a`・`ok_b`）。
  - `included` の列を足しただけでは、この式が `screen_stocks` に残ります。
- ウォッチリストの `data-kind` は、状態と「含める」の設定から求めることになります。「条件①・条件③」と、妨げている条件を並べるからです。
  - 対象: `included`／`unmet`／`unavailable`／`filters`／`delisted`
  - この対応を TypeScript で作ると、C7-2 の「TypeScript に判定の式が無い」に反します。
- 変化の理由の「妨げる」（第2章の9）も同じ定義です。
- 直し方:
  - `screening_evaluate` が、`included` に加えて除外の分類を返すと、契約に書く。分類は次のとおり。
    - 除外の種類（`delisted`／`filters`／`unmet`／`unavailable`／`null`）
    - 妨げている条件の配列。例 `blocking: ['cagr','years']` と、それぞれが unmet か unavailable か。
  - この分類を、次のすべてが使う。
    - `screen_stocks` の件数
    - ウォッチリストの `data-kind`
    - `screening_changes` の理由
  - 分類の優先順位を決める。例: 上場廃止 → 絞り込み → 満たさない → 算出不可・判定不能。
  - 「満たさない」と「判定不能」が同時にあるときの `data-kind` と文言も決める（今は未定義）。
- 記録の側の判定は、「銘柄ごとの入力の行」を今の表か記録の表から作る。その後の状態の CASE 式は1つだけにする（入力の CTE を切り替える形）。これを C7-2 の確認の観点として明記してください。
  - 記録用に CASE 式を複製すると、2つ目の実装になります。

### R4: 記録の保持（最新 7 回）が、テストの外の記録を消す。後片付けの約束（C7-1・C11-5）と矛盾する

- `capture_screening_snapshot` は、記録するたびに最新 7 回を残して古いものを消します。
  - C3-4・C7-1 の `pnpm test:db` は、8 回記録します。
  - その結果、DB に元からあった記録（開発中の DB の、定期実行の記録）がすべて消えます。
  - その後、テストは自分の記録を消すので、比較の基準が無くなります。
- 「テストが作った行だけを消す」（C7-1、C11-5）が、記録の関数そのものの動作で破られます。
- さらに、`screening_changes` は全体の「最新の記録」を使います。そのため、DB に記録があると、テストの期待値が揺れます。
- 直し方（どちらか）:
  - 記録を作る `pnpm test:db` の前提に「記録が0件の DB（`db:reset` 直後）」を加える。既存の株価・財務のテストと同じ書き方です。あわせて、CLAUDE.md の `pnpm test:db` の行に書き、テストの冒頭で0件を確かめて、そうでなければ失敗させる。
  - または、記録を作るテストを、すべて巻き戻すトランザクションの中で行う。
- E2E の前提（記録0件）は第6章と C11-4 に書かれているので問題ありません。

## 観点ごとの確認結果

### watchlist_items の RLS・トリガー・権限・上限（Sprint 11・13 と同水準か）

- 次は、Sprint 11 の R1・R2・注意1、Sprint 13 のレビューの指摘と同じ水準です。
  - RLS（本人かつ許可ユーザー、`(select …)` の形。with check も同じ）
  - authenticated のテーブル権限は select／insert／update／delete ちょうど。anon なし
  - トリガーの動き:
    - `user_id` は NULL のときだけ補う
    - `user_id`・`code` の変更を拒否する
    - `created_at` を固定する
    - `updated_at` はメモの変更時だけ更新する
    - メモは前後の空白を除き、空なら NULL にする
  - check 制約
  - ユーザーごとの advisory lock（プリセットとは別のキー）
  - トリガー関数の EXECUTE を付けないこと
- `user_id` の変更を拒否するので、行を他人に移して上限をすり抜けることはできません。
- 上限の数え方は security invoker のトリガーで、RLS で見える自分の行だけを数えます。これは正しいです。
- 欠けているのは R1（冪等との衝突）だけです。
- `code` の参照は削除で連鎖しますが、上場廃止では `stocks` の行を消しません。この点は Sprint 11 のレビューの注意と整合しています。

### スナップショット（判定の入力）を、定期実行の開始時に同じトランザクションで記録する設計

- 記録する列を、今の `screening_evaluate` の定義と照らし合わせました（評価者が DB から取得）。
  - 条件①: `financial_metrics.revenue_cagr`
  - 条件②: `financial_metrics.operating_margin`
  - 条件③: `stock_listing_dates` の `first_price_date`・`data_start_date`、基準日
  - 条件④: `ownership_judgments.status`・`president_is_top_holder`・`owner_total_pct` を `owner_result_of` に渡す
  - 絞り込み: `market_code`・`sector33_code`、`delisted_on`
- 契約の第2章の5の列は、これと過不足なく一致します。
  - 行が無いこと（`stock_listing_dates` や `financial_metrics` の行が無い）を NULL で表せば、「算出不可」も再現できます。
- 結果ではなく入力を残す方針は正しいです。この方針なら「両側に同じ条件」と「両側に今の補正」を実現でき、閾値やプリセットを変えても比べ直せます。
- 記録の側の判定に、**記録の基準日**を使うこと（C4-10 の境界の例）も正しく押さえています。基準日が進んだだけで上場年数が 5.0 年を超えた銘柄が「外れた」に並ぶのは、データによる本当の変化です。
- 仕様の「毎日新たに該当した銘柄と外れた銘柄」「毎朝、今日新しく条件に入った銘柄」との対応:
  - 朝に見ると、前夜の 20:00・22:00・0:00 の変化がまとめて見えます。利用者の話にそのまま合います。
  - 「今回」を今のデータにするので、NEW とダッシュボードが必ず一致します。これも利点です。
  - 20:00 を過ぎると一覧は新しい周期に入れ替わり、途中の状態になります。`changes-running-note` と `changes-incomplete-note` で示すので、許容できます。
- 状況ごとの扱い:
  - 部分完了・失敗は、注記の条件（記録の後に始まった実行だけ、後の成功で打ち消す）が明確です。
  - 実行中・409（記録しない）も明確です。
  - 上場廃止（`delisted` だけ）、上場廃止から戻った（`relisted`）、新規（`new_stock`）も明確です。
  - 空の記録（`empty_snapshot`）の扱いも、全銘柄が「新規」に並ぶのを避けていて妥当です。
- 定期実行が1日飛んだとき（Hobby のずれや障害）は、2日分の変化になります。`changes-cycle` の日付で分かるので問題ありません。
- 最新 7 回の保持は、比較に1回しか使わないので、履歴画面（第8章でやらないこと）への備えとして妥当です。4,000 銘柄 × 7 回でも小さい量です。R4 のテストとの関係だけ直してください。
- 同じトランザクションで記録する点:
  - 利点: 取り込みが書き始める前の状態を確実に取れます。二重実行（409）のときに記録しないことも保証できます。
  - 問題: 記録の失敗が取り込みを止めます（R2）。

### 「該当」の式を screening_evaluate にまとめるリファクタリング

- 今は、`screen_stocks` と `stock_detail` の2か所に同じ式があります（評価者がソースで確認。今は同値）。
  - `screen_stocks`: 「unmet が無い」かつ「含める設定と ok_a・ok_b」
  - `stock_detail`: 同じ式
- 1か所にまとめること自体のリスクは低いです。
- リスクが残るのは次の2つです。
  - R3 の除外の件数
  - 記録の側の判定を別の CASE 式で書いてしまうこと
- C7-1 の網羅（含める2つの真偽、オフの組み合わせ、市場・業種、上場廃止）で3つの集合が一致することを確かめます。これで、リファクタリングの回帰は十分に検出できます。
- 加えて、「記録を今と同じ値で作った直後は変化0件」も確かめます。これで、記録の側の判定も同じ式を通ることが検証できます。
- 既存の E2E（Sprint 6・7・10〜13）がそのまま通ることが、最終的な確認になります。

### 条件の使い分け

- ダッシュボード・ウォッチリストは既定の条件で判定します。
- NEW は表示中の条件で判定します。
- API は既定のプリセットを当てず、標準の条件で判定します。
- これは Sprint 13 の「画面を開いたときだけ既定を当て、API には当てない」と一貫しています。
- 条件の解決を1つの関数にして4か所で共有するのも適切です。
- 「スクリーニングで開く」のクエリで開けば、NEW とダッシュボードの一覧が一致します（C4-5 で判定できます）。
- 無効・正規形でないプリセットの注記で、Sprint 13 の m3 も解消します。

### ユーザーに確認中の2点についての意見

1. **基準の記録を、定期実行の開始時だけにする**（契約の案）について、評価者は**契約の案に賛成**です。
   - 手動の実行でも記録する案の欠点:
     - 朝に手動で取り込むと、前夜の変化の一覧がその時点で消えます。
     - EDINET の初回の取り込みでは「今すぐ取り込み」を何十回も押します。そのたびに基準が入れ替わり、変化がほとんど見えなくなります。
     - これは利用者の話「毎朝、今日新しく条件に入った銘柄」を損ないます。
   - 契約の案の欠点:
     - 定期実行が動かない環境では、ずっと「比較できません」になります。例: ローカル、Cron を止めた本番。
     - 手動の実行だけで運用する利用者は、この機能を使えません。
     - これは空状態の文言で説明されているので、許容できます。
   - 将来、必要になれば「基準を今にする」の手動の操作を別に足せます。
2. **手動補正を、比べる両側に今の補正として当てる**（契約の案）についても、評価者は**契約の案に賛成**です。
   - 記録の時点の補正を残す案の欠点:
     - 利用者のデータ（ユーザーごと・RLS）を、市場データの記録（全ユーザー共通、service_role で作成）に混ぜることになります。
     - 権限の設計が複雑になります（記録の中の補正に、ユーザーごとの RLS が要る）。
     - 自分の操作が「新たに該当」に混ざり、一覧の目的（取り込みによる変化を知る）が薄れます。
   - 契約の案の欠点:
     - 補正を付けていた銘柄では、その間の自動判定の変化が一覧に出ません。
     - 補正を外した日に結果から消えても、「外れた」に並びません。
     - どちらも利用者自身の操作の結果です。Sprint 11 の「補正後に自動判定が更新されました」の知らせもあるので、許容できます。

### R2: セーブポイントと、`start_ingestion_run` の既存の仕組み

- 二重実行の防止: 記録の呼び出しは、実行の行の insert（部分一意索引）に成功した**後**に行います。その呼び出しを、内側の例外ブロック（サブトランザクション）で包みます。
  - 記録が失敗して巻き戻るのは、内側のブロックだけです。`running` の行と一意索引の効果は残ります。
  - 記録の間（最大で約 1 秒）に別の開始の要求が来ても、その insert は一意索引で待ちます。そして、こちらの確定の後に unique_violation になり、409 になります。これは今の振る舞いと同じです。
- 応答の無い実行の後片付け: 後片付けの update は、外側のトランザクションで記録より前に行います。内側のブロックが巻き戻っても、後片付けは残ります。
  - 409 のときは記録を呼ばないので、後片付けとの順序の問題もありません。
- 以上から、矛盾はありません。実装への注意（修正は不要）は次の2つです。
  - `exception when others` は、`query_canceled`（statement_timeout によるキャンセル）を捕まえません。記録がタイムアウトすると、開始ごと失敗します。C8-1 の 1,000ms 以内の性能で、実害は小さいです。
  - `details` への書き込み（`captured`／`failed`）は、内側のブロックの外（または例外の処理の中）で行ってください。巻き戻りで消えないようにするためです。そのうえで R5 の保持が必要です。
