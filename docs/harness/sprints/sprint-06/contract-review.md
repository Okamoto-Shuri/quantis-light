# Sprint 06 契約レビュー

## 判定: 修正依頼

契約の設計（m4 の方式、算出不可の扱い、金融業の扱い、URL、性能の目標）は、仕様と整合していて妥当です。ただし、完了条件 C3 の期待値が、契約の第5章の投入データと第2章の3の規則から導かれる結果と矛盾しています（R1）。このままでは、正しく実装しても C3 は不合格になります。逆に C3 に合わせて実装すると、AC6.4 に反した絞り込みになります。R1〜R3 を直せば承認します。

## 修正必須

### R1: C3-1・C3-2 の期待件数が誤っている（オフにした条件の「算出不可」の銘柄が数えられていない）
第2章の3は「オフの条件は、状態にかかわらず絞り込みに使わない（AC6.4）」と定めています。この規則を第5章のデータに当てはめると、次の結果になります。
- **C3-1（条件②をオフ）**: 追加されるのは `99993` だけではありません。`99997`（銀行型。①25.0% 満たす・② 算出不可・③3.0年 満たす）も、②がオフになるとオンの条件をすべて満たします。そのため、正しくは **4件**（`99990`、`99991`、`99993`、`99997`）です。契約では「3件」になっています。
- **C3-2（条件③をオフ、②はオン）**: `99994`・`99995` に加えて、`99999`（①21.0%・②11.0%・③ 未確定）も入ります。そのため、正しくは **5件**（`99990`、`99991`、`99994`、`99995`、`99999`）です。契約では「4件」になっています。
- 対応: C3-1・C3-2 の件数と銘柄を直してください。C10-1 の自動テストと C14-3 の E2E の期待値も合わせてください。また、「オフにした条件が算出不可の銘柄は、オフにすると表示される」ことを C3 に1項目加えてください。これは AC6.4 と AC6.5 の組み合わせで最も間違えやすい点です（例: ②をオフにすると、既定の「算出不可を含めない」のままで `99997` が現れる。そのとき `99997` の②の印は `off`）。
- ほかの期待値（C1-3、C2-1〜C2-4、C4-1・C4-2・C4-6、C5-3 の4つの並び、C7-1・C7-3・C7-4、C8-4、C9-1）は、手で計算して一致を確かめました。

### R2: C11（性能）の測定条件と合否の基準を明確にする
- **ロールの指定**: `screen_stocks` は security invoker なので、`postgres`（スーパーユーザー）で測ると RLS が効かず、実際の経路の性能になりません。C11-2・C11-3 は、**許可リストに登録された authenticated ユーザーとして**測ると明記してください（PostgREST の RPC か、`set local role authenticated` と `request.jwt.claims` の設定）。
- **合否の基準**: 「値は開発機での目安」とあるため、100ms を超えたときに不合格なのかが読み取れません。次のどちらかに決めてください。
  - (a) `pnpm test:db` の中で、100ms を超えたら失敗させる（初回の1回はウォームアップとして除く。5回の中央値）。
  - (b) 評価者が同じ条件で測り、100ms を超えたら C11 は不合格とする。
- C11-3（`pg_stat_user_functions` の増分）は、統計の反映が遅れるため、読む前に `pg_stat_force_next_flush()`（PG15 以降）を呼ぶか、トランザクションを分ける必要があります。手順に書いておいてください。`listing_years_between` を SQL 関数に書き換えてインライン化した場合は、この方法では数えられません。その場合は、`explain (analyze)` で関数スキャンの行数を見るなど、代わりの方法を併記してください。
- 4,000 銘柄の性能テストは、CLAUDE.md にある結合テストの前提（テスト以外の銘柄行が無い DB）とぶつからないようにしてください。ほかの `*.db.test.ts` と並行して動かないこと、終了後に 0 件へ戻ることを書いておいてください（C11-5 に含めてよい）。

### R3: URL・API のパラメータとして受け付ける形を明記する
C6-4・C9-3 と C10-4 で、合否を判定できる形にするため、次を第2章の6に書いてください。
- 閾値の文字列の文法（例: `^-?\d{1,4}(\.\d)?$`）。次の値を有効とするか無効とするか: `+20`、`.5`、`20.`、`20.0`、`-0`、`1e1`、`Infinity`、全角数字、前後の空白。
- 同じパラメータの重複（`?cagr=10&cagr=20`）と、カンマ区切りの値の重複（`market=0111,0111`、`off=cagr,cagr`）の扱い。拒否するのか、重複を除くのか。C10-4 は「重複」を検証すると言っていますが、期待する振る舞いが書かれていません。
- 一部だけが不正な場合（`off=cagr,foo`、`market=0111,9999`）に、項目全体を既定にするのか、正しい値だけを残すのか。
- `sector` の「未知の値」の定義。33業種の固定の一覧に無いコードを未知とするのか、DB に銘柄が無いコードも未知とするのか。後者を有効とする場合、業種の選択肢（DB にある業種だけ）に名前が無いので、チップに何を表示するか。
- `unavailable=exclude` を明示したとき、および未知のパラメータ（`?foo=1`）の扱い（無視するか。API は 400 にするか）。
- 画面の入力欄に不正な値が残ったまま別の条件（スイッチなど）を操作したとき、URL にはその閾値の直前の有効な値を書き、入力欄のエラー表示は残す、など。

## 確認した論点（問題なし）

### 金融業を除外しない（ユーザーの決定）
守られています。業種による除外やフィルタは作りません（第1章、C4-4、C7-4）。銀行型の `99997` は、CAGR を算出し（25.0%、満たす）、営業利益率は「算出不可（営業利益の開示なし）」として扱います。既定では条件②が算出不可なので除外され、「算出不可を含める」で表示されます。スイッチの説明文にも銀行の注記があります。Sprint 5 評価の P1（業種による注記の検討）には、説明文で最低限答えています。

### m4 の対策（条件③を初出日の下限日と比べる方式）
- 単調性の前提は成り立ちます。ローカル DB の実物の `listing_years_between` で、次の範囲を全件確かめました（読み取り専用のクエリ。約10.3億の組み合わせ）。
  - 基準日 R: 2023-01-01〜2029-12-31 の全日（うるう年の 2024・2028 を含む）
  - 初出日 F: R の11年前〜R の全日
  - 閾値 Z: 0.1〜10.0 の 0.1 刻み
- 結果（違反はどちらも 0 件）:
  - F について `exact_years` は非増加だった（F が新しいほど年数が大きくなる箇所は無い）。
  - 「`F >= min{F : exact <= Z}`」⇔「`exact <= Z`」⇔「`rounded_up_years <= Z`」が一致した。
- 「表示 ≤ Z ⇔ 正確 ≤ Z」は、表示が `n + ceil(10d/L)/10` で正確な値の小数1桁の切り上げと等しく、Z が小数1桁なので成り立ちます。`d/L` が k/10 と異なるときの差は 1/(10L) 以上あります。numeric の除算の精度では誤判定しません。
- 財務の「表示 ≥ X ⇔ 保存 ≥ X/100」は、生成列が `floor(v*1000)/10` で、Z と同じ理由で成り立ちます（負の値も floor で正しい）。
- C10-3 は、うるう日を含む基準日で境界を網羅するテストで、ジェネレーター側でも確かめる形になっていて十分です。
- 軽微（修正は任意）: 第2章の3の `unmet` の理由の「Z ≤ 10 のどの閾値でも満たさないことが確定しているため」は、厳密には正しくありません。データ期間の開始日が R の約10年前の翌日のとき、その直前に上場した銘柄の真の年数は 10 未満のこともありえます。ただし、「データ期間開始以前から上場は満たさない」は仕様の用語定義そのものなので、振る舞いは正しいです。理由の文を「仕様の定義により」に直すとよいでしょう。

### 算出不可の扱い
仕様と整合しています。
- 仕様は AC6.5 で「算出不可を含めるかを選べる。既定では除外」とだけ定めています。「含める」スイッチ1つで、含めるときも `unmet` は除外する、という解釈は自然です。
- データ期間開始以前を `unavailable` ではなく `unmet` にするのは、仕様の用語定義（「上場X年以内の条件は満たさない」）に従っています。「含める」をオンにしても表示されない点（C4-2）も、それと一致します。
- 初出日が未確定・財務データなし・基準日なしを `unavailable` に入れるのも、AC6.5 の意図に沿っています。
- AC6.13 は C4-3 で検証できます。

### 条件③の閾値の上限 10.0 年
妥当です。
- 保存済みの初出日は更新しません（AC4.4）。そのため、年月が経つと「年数の分かる銘柄」の正確な年数が 10 を超えることがあります（例: 3年前に確定した行）。上限が 10 でも、それらは正しく `unmet` になります。
- 上場から日の浅い銘柄を探すという仕様の意図からも、上限で困ることはありません。
- 上限を上げると、データ期間開始以前の銘柄の扱いがあいまいになります。10.0 はその点でも安全です。

### そのほか
- AC6.1〜AC6.13 のすべてに、対応する完了条件があります。スコープの削減はありません。AC6.12 は、1280×800 と 375×812 の両方で、表示領域の中にあることを確かめる形になっています（C1-5）。
- 画面では不正な URL の値を既定に置き換え、API では 400 にします。この違いは明記されていて判定できます。
- 並べ替えの規則（値の無い行は常に最後、同じ値はコード順、上場年数の3群の順）も判定できます。期待される並びは、第5章のデータで手計算と一致しました。

## 実装時の注意（合否の条件ではない。評価で気づいたら指摘する）
1. **NFKC で直らないマイナス記号**: NFKC は全角のハイフンマイナス（U+FF0D）を `-` に直しますが、数学記号のマイナス（U+2212 `−`）や長音記号（`ー`）は直しません。日本語入力で負の閾値を打つと、これらが入ることがあります。入力欄でこれらを `-` とみなすか、エラーの文言で分かるようにしてください。エラーの文言の例「−100〜1000」自体が U+2212 を使っている点にも注意してください。
2. **`?sector=0050` のような DB に無い業種**: 業種の一覧に銘柄数 0 の行を加えるのは、URL で選ばれているときだけにしてください。C7-2 の「投入した銘柄の業種だけが並ぶ」を崩さないためです。
3. **テスト用のコードの接頭辞**: 性能テスト（`8Z…`/`7Z…`）、E2E（`9999x`・`9Z…`）、既存の結合テスト（`9999x`）で、後片付けの条件が互いの行を消さないようにしてください。特に、E2E と `test:db` を続けて実行したときのことを考えてください。
4. **スライダーのキー操作**: スライダーをキーで操作するたびに URL を書き換えるので、矢印キーを押し続けると `router.replace` が連続します。前の要求の取り消しか、最後の結果だけを描画する処理を入れてください（C2-6 と C14-5 のコンソールのエラー、表示のちらつきに関わります）。
