## 指示された確認事項

### self-review に書かれた、契約との違いの妥当性
1. **C11-4 の呼び出し回数（条件③がオンのとき、二分探索の12回が加わる）: 妥当と判断する。**
   - 契約の C11-4 の測定条件は「3条件オフ・4,000件・推定上場年数で並べ替え」です。この条件では条件③がオフなので、`listing_first_date_cutoff` は呼ばれません。テストは `calls <= 100` を満たしており、契約の文言どおりに達成しています。
   - 条件③がオンのときに加わる約12回は、二分探索の回数です。探索範囲は (ceil(Z)+1) 年分の日数なので、およそ log2(4,000) になり、銘柄数によらず一定です。m4 の意図（行ごとの評価をしない）に沿っています。テストでも `cutoffCalls < 20` と `withYears - cutoffCalls <= 100` を確かめています。
2. **性能テストのコード P0000〜P3999: 妥当と判断する。**
   - `stocks.code` の制約 `^[0-9A-Z]{4,5}$` を満たします。
   - J-Quants の実際のコードは数字で始まるため（`130A0` のような新しい形式も先頭は数字）、`like 'P%'` の後片付けが実データを消すことはありません。E2E（`9999x`・`9Z…`）と既存の結合テスト（`9999x`）の接頭辞とも重なりません。
   - ただし、CLAUDE.md の `pnpm test:db` の説明は「作った行（銘柄コード 9999x）は後片付けされる」のままです。`9Z…`・`P…` も後片付けされることを追記してください（任意）。

### ユーザーの決定「金融業は除外しない」: 守られている
- `screen_stocks` と `params.ts` に、業種による除外はありません。業種の条件は、利用者が選んだ `sector` だけです。
- 業種の選択肢に「銀行業 1」が並びます。3条件オフ・業種「銀行業」で `99997` の1件が表示されます。
- 既定の設定（「算出不可を含める」がオフ）では、`99997` は条件②が算出不可のため除外され、「算出不可・未確定のため除外: 4 件」に数えられます。
  - 「含めて表示」を押すと、CAGR 25.0%（満たす）と「算出不可（営業利益の開示なし）」の表示で現れます。
  - 条件②をオフにすると、「算出不可を含める」がオフのままでも現れます（印は ② off）。
- スイッチの説明文に「銀行など営業利益を開示しない会社は、営業利益率が算出不可になります。」があります。

## 軽微な問題（合否には影響しないが、次のスプリントまでに直すことを推奨）

### m1: 「既定の条件に戻す」を押しても、入力欄の不正な値とエラーの表示が残ることがある
- 重要度: Minor
- 再現手順:
  1. `/screening?cagr=15&off=margin&market=0113&unavailable=include&sort=years&order=asc` を開く。
  2. 上場年数の入力欄に `zz` を入力する（エラーが出る。確定済みの値は 5 のまま）。
  3. 「既定の条件に戻す」を押す。
- 期待結果: すべての入力欄が既定値（20・10・5）になり、エラーの表示が消える。
- 実際の結果: URL と結果は既定の条件になる。しかし、上場年数の欄は `zz` のままで、`aria-invalid="true"` とエラーの文言が残る。
- 根拠: 操作の後の入力欄は `['20:null', '10:null', 'zz:true']`。原因は、`ThresholdField` が「外から値が変わったとき」だけ入力欄を合わせていることです。確定済みの値が既定と同じ（5）だと、値が変わらないので入力欄が更新されません。「既定に戻す」は明示的に入力を捨てる操作なので、C6-5 の「利用者の入力を消さない」には当たりません。

### m2: 1280px で、算出不可の文言と「データ期間開始以前」が1文字だけ次の行に送られる
- 重要度: Minor（デザイン）
- 「財務データな／し」「データ期間開始以／前」「算出不可（営業利益の開示／なし）」のように、最後の1〜2文字だけが次の行に落ちます（列の幅は 6.5rem・7rem）。読めますが、密度の高い表としては粗く見えます。列の幅を少し広げるか、`text-balance`、または短い表記（「財務なし」など）にして `title` で補うことを検討してください。

### m3: 右揃えの列で、並べ替えの矢印が見出しの文字から離れて、セルの左端に出る
- 重要度: Minor（デザイン）
- 売上CAGR・営業利益率・推定上場年数の見出しで、`↓`／`↕` のアイコンが文字と離れてセルの左上に浮きます（`flex-row-reverse` と `justify-start` の組み合わせのため）。どの列の矢印なのかが一瞬分かりにくくなります。

### m4: 1280×800 では、条件パネルの下半分（市場区分・業種・既定に戻す）がパネルの中のスクロールの先にある
- 重要度: Minor（UX）
- 結果が少ないとページ自体がスクロールしないため、パネルは `max-h` で「算出不可を含める」の説明の途中で切れます。市場区分と業種の絞り込みは、パネルの中をスクロールしないと見えません。スクロールバーも目立たないので、初めて使う人は市場区分・業種の絞り込みがあることに気づきにくいです。
- 改善案: 説明文を短くする（あるいは折りたたむ）、パネルの下端にフェードを付ける、市場区分と業種をパネルの上の方に移す、など。

### m5: 条件の印の `title` とスクリーンリーダー用の文字が、確定前の閾値を示すことがある
- 重要度: Minor
- `StatusMark` は、閾値にクライアントの `current`（スライダーを動かしている間の値や、更新待ちの値）を使います。取り直しが終わるまでの間は、「条件① 売上CAGR（≥30%）: 満たす」のように、新しい閾値と古い判定の組み合わせが読み上げられます。結果（`result.conditions` に相当する、サーバーが判定に使った閾値）から作ることを推奨します。

## コード品質の所見
- 検証（`params.ts`）を画面と API で共有していて、違いは不正な値の扱いだけです。閾値は十進の文字列のまま numeric に渡しています。`screen_stocks` は1回の SQL で、件数・除外の件数・ページ・表示用の年数を求めます。条件④を足しやすい形になっています。
- 連続した操作の扱い（`queued`・`pushed`・`seenKey`）は、次の操作をすべて試しましたが、条件が古い値に戻ることはありませんでした。
  - 入力の直後のスイッチ操作
  - 待ち時間の途中の並べ替え
  - スイッチの7連打
  - 矢印キーの連打
  - 450ms 間隔の1文字ずつの入力
- ただし、この状態の管理はやや込み入っています。Sprint 7 以降で手を入れるときは、E2E で守られていることを前提にしてください。
- 独自のデータ（4,000 銘柄）でも、ビューを使った独自の問い合わせと件数が一致しました。単調性を前提にした下限日の方式が正しく働いています。
