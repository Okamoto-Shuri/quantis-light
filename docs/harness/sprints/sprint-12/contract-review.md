### R3: stale の `partial` は、後片付けの時刻を `finished_at` にしている。これが鮮度の「最終更新」として数えられてしまう
- 今の `start_ingestion_run`（`20260926000000_ingestion_stock_master.sql`）は、後片付けの行に `finished_at = now()` を入れる。この now() は、**次の実行が始まった時刻**になる。
- 第2章の4は、`partial` の最新の `finished_at` を「データが最後に更新された日時」としている。そのため、実際の保存が月曜なのに後片付けが金曜だと、最終更新は金曜になる。
  - その結果、警告が出るべき期間に出なかったり、表示の日時が誤ったりする。
  - 毎回強制終了される状態が続くと、実際の保存の時刻とは関係なく、後片付けのたびに鮮度が新しくなる。
- 直し方（どれかを契約に書き、C4 か test:db に検査を1つ足す）:

- 検査の例: 開始 3 日前・`processed_count = 120` の `running` を置いて後片付けを走らせる。その行だけでは警告が消えない（または、最終更新が最後に保存した時刻になる）ことを確かめる。

### R4: 時計に依存して既存 E2E の状態が変わる件を、ジェネレーター自身も確かめること

- 第2章の4の見た目の制約（1280 で2行、`role="status"` を使わない、リンク名の制約）は妥当。ただ、375×812 の `screening.spec.ts:84`（注記の `toBeInViewport`）は、警告の高さの影響を最も受けやすい。契約は 375px での警告の高さを縛っていない。
- 直し方:

  - 375px での警告の高さの上限（例: 1行目の折り返しを含めて4行以内）も書く。
- 評価者は、境の前後どちらの時刻に評価しても両方の状態を確かめる。
- 補足: C4 のほかの検査は、どれも `now()` からの相対で行を入れるか `p_now` を渡すので、決定的である。境の近く（47 時間 59 分）でも、描画までの数秒の余裕があるので揺れない。

### R5: 全画面で呼ぶ `data_freshness()` が失敗したときの振る舞いが未定義
- 警告は `ProtectedShell`（404 を含むすべての保護画面）で毎回 DB を呼ぶ。この呼び出しが失敗したとき（関数のエラー、一時的な DB の障害）に、**全画面が 500 やエラー境界になる**のか、警告を出さずに描画するのかが書かれていない。

- 直し方: 「鮮度の取得に失敗したときは、警告を出さずにページを描画し（サーバーのログに残す）、ほかの機能を妨げない。ダッシュボードと `GET /api/dashboard` の `freshness` は失敗を示す（例: `freshness: null`、または既存の集計エラーの表示）」のように決め、単体テストか E2E で1つ確かめる。

## 2. 依頼された論点への意見

### ★1 AC11.5 を「銘柄単位の整合＋実行中の注記」で満たす解釈
- **銘柄単位の整合（C5-1）は正しく、必要**。保存と再計算が同じトランザクションにあることは、Sprint 5・9 のトリガーの設計と合っている。「実行ごとのスナップショットを持っても、複数回に分けた取り込みでは全体はそろわない」という理由付けも妥当。
- ただし、仕様の2つの選択肢のどちらも、**文字どおりには**満たしていない。
  - 前半の「前回までの完全なデータで検索でき、途中までのデータが混ざらない」: 1回の実行の途中でも、結果の中で「更新済みの銘柄」と「未更新の銘柄」は混ざる。混ざらないのは1銘柄の中の値だけである。
  - 後半の「**どの銘柄が**更新中かが表示される」: 注記は「実行中です」と言うだけで、銘柄を特定しない。
  - さらに、注記が出るのは実行中の数分間だけ。初回の取り込みのように何日も `partial` が続く期間（残りがあり、データが途中までの状態）には何も出ない。
- 意見: 解釈として**弁護はできる**（「途中までのデータ」を「1銘柄の半端な値」と読む）。ユーザーが推奨案を選ぶなら、それに従ってよい。より仕様に近づける、費用の小さい追加案は次の2つ（どちらかでも効果がある）。
  1. 実行中の注記に「この実行で更新済み N 銘柄」を出し、結果の行に「今回更新」の小さな印を付ける。対象は、実行の開始以後に初出日・指標（`financial_metrics.calculated_at` など）・判定が変わった銘柄。「どの銘柄が」に文字どおり答えられる。
  2. 実行中でなくても、target ごとの直近の実行に残り（`remaining_count > 0`）があれば、スクリーニングに「未取得の残りがあります（株価 3,512 銘柄・財務 20 日分）」を出す。ユーザーストーリーの「何が古いままなのか」に最も効くのはこちら。
- ユーザーが推奨案（今の契約）を選んだ場合でも、C5-1 の対象の保存の関数に、次の2つを足すこと（**推奨**）。
  - `save_stock_listing_dates`（株価の 50 銘柄ごとの保存）
  - `save_edinet_document_list`（取り下げ・不開示・提出者の更新が、トリガーで期と指標を再計算する経路）
  - 今の3つ（財務・EDINET の本文・銘柄マスタ）だけでは、4つの target の保存の経路を網羅していない。

### ★2 AC11.3 の鮮度を取り込み対象ごとに判定する解釈
- **妥当で、推奨案に賛成**。全体の最新の成功で判定すると、J-Quants のキーが切れても EDINET の成功で警告が消え、仕様の目的（「何が古いままなのか」）に反する。target ごとに判定しても、仕様の文言（1行目に日時を1つ）は、最も古い日時を出すことで満たせる。
- `partial` を含めること、一度も成功していない target を除くことにも賛成（キー未設定の環境で常に警告が出るのを避ける）。ただし、R3 の stale の扱いは直すこと。
- 注意（改善提案）: `partial` を含めるので、毎日 `rate_limited` で1件だけ保存して止まる状態でも警告は出ない。その状態は実行履歴の「一部失敗」で見えるので許容できる。ただ、CLAUDE.md の鮮度の説明に「保存が1件でもあれば更新とみなす」と明記しておくとよい。

### 429・503 の待機と再試行、期限 210 秒・maxDuration 300 との関係
- **矛盾しない**。「待ちの終わりが期限を超えるなら待たない」という規則なので、新しい要求（再試行を含む）はこれまでどおり開始から 210 秒以内に始まる。1回の要求のタイムアウト（J-Quants 30 秒、EDINET の書類取得 60 秒）と保存を足しても、300 秒に収まる。これは `clock.ts` のコメントの前提と同じ。
- 最悪でも待ちの合計は 15＋30＋60＝105 秒で、期限の中に収まる。
- 改善提案（必須ではない）:
  - `Retry-After` が HTTP 日付の形や数でない値のときは、既定の 15・30・60 秒を使うと明記する。
  - EDINET は HTTP 200 の本文でステータスを返すので、ヘッダーの `Retry-After` はふつう無い前提になる。そのことを書いておく。
  - Cron の daily では、銘柄マスタで待った時間が株価の予算を減らす。これは今の「ルートの開始から数える」設計のままで問題ない。

### 上場廃止を `stocks.delisted_on` で表し、行を消さない設計
- **妥当**。Sprint 11 の補正・メモの連鎖削除を避けられ、再上場で NULL に戻す規則とも合う。`complete_stock_master_run` は今も行を消していないので、既存の振る舞いとも矛盾しない。
- 100 銘柄を超えたときの保留も妥当（一時的な欠落や、市場区分のコードの付け替えなどで大量に消えるときの保護。境界 100／101 の検査もある）。
- 改善提案（必須ではない）:
  - 本当に 101 銘柄以上が消えた場合、毎日 `partial`（`delisting_held`）が続き、手で解く手段が無い。解き方（例: 保留を一度だけ無視して反映する運用コマンド、または手順）を CLAUDE.md の既知の制限に書く。
  - `delisting_held` は、表示の規則では「一部失敗」になる。中断の理由の文言で説明されるので、これで許容できる。

### ingestion_run_failures の権限・RLS、新しい画面・API の認証
- テーブルの権限（許可ユーザーの select だけ、書き込みは service_role の関数だけ、`code` は参照にしない、`run_id` は連鎖削除）は、既存の方針と一致する。
- 既存の E2E の後片付け（`delete from public.ingestion_runs`）が、連鎖で失敗の行も消す点も整合している。
- `data_freshness`（authenticated・security invoker）、`GET /api/ingestion/runs/[id]`（`requireApiUser()`・`jsonNoStore`・401／403／400／404）、保護画面の中の 404 も妥当。
- `e2e/db-privileges.spec.ts` の更新も契約にある。
- 改善提案: `/imports/runs/[id]` を開いているときに、ナビゲーションの「取り込み状況」に `aria-current` を付けるかを明記する（銘柄詳細は付けない方針だった）。

### 完了条件の判定可能性
- C1〜C9 は、画面（data-testid と文言）・API・DB・test:db のどれかで判定でき、投入例の値も具体的である。
- C5-1 の検査は「未コミットの保存は別の接続から見えない」という、DB の分離の性質を確かめる部分が大半である。意味があるのはコミットの後の後半（保存と再計算が同じトランザクションにあること）なので、そちらを主眼にすること。
- 改善提案: 鮮度の警告を保護画面の枠（layout）に置くと、クライアント遷移（next/link）では layout が描き直されない。遷移しても直前の状態が残る（リロード・`router.refresh()` で更新される）。C4 はどれも `goto`・`reload` で確かめるので合否には影響しないが、振る舞いを CLAUDE.md に書いておくこと。

### 既存テストの変更を5種類に限った点
- 範囲を絞る方針はよい。ただし R1（表の見出しの配列）と R2（0 件の stale の文言）は、今の契約どおりに実装すると範囲の外で壊れる。これを直すこと。
- `result-message.test.ts:49`（新しい列の無い時間切れの `partial` は「一部失敗」）は、「列の無い行の期待値は変えない」と整合している。

## 実装・評価の段階で注意する点（承認の条件ではない）

1. **失敗した実行が残りの注記を消してしまう**
   - 残りの判定は「最新の終了済みの実行」の `remaining_count` を見る。
   - 例: 財務の `partial`（残り 20 日分）の後に、キーの無効などで保存 0 件の `failed`（残りが NULL）が続くと、残りがあるのに注記が消える。
   - 推奨: `failed` で `remaining_count` が NULL の実行は判定に使わず、1つ前の実行の値を使う。または、`failed` の実行にも数えられるなら残りを記録する。
   - 評価では、この場合の表示を確かめる。今の文面では、どちらの振る舞いも契約違反にはならない。
2. **1280 幅の警告の高さの書き方が2か所で違う**
   - 第2章の4は「1行目と内訳が2行以内」、C4-8 は「3行以内（1行目＋内訳2行）」と書いている。
   - 評価は C4-8（3行以内）で判定する。
3. **警告の高さを測る状態**
   - C4-8 は、C4-4 の2 target の状態で測る。
   - 4 target すべてが古い状態で 375px を超える場合は、`<details>` での折りたたみ（第2章の4）が効いているかも確かめる。
