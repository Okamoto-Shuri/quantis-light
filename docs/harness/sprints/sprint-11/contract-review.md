## 修正必須

### R1: 記録の列・日時・選択肢を、直接の書き込み（PostgREST）からも守ることを契約で保証する

契約の第2章の2は、`authenticated` にこのテーブルの select・insert・update・delete を grant します。一方で、記録（`auto_*`）を偽れないようにする手段は「保存用の関数か、トリガー。ジェネレーターが決める」となっています。**関数を選んだ場合、利用者は公開キーと自分の JWT で `PATCH /rest/v1/ownership_overrides?code=eq.9U006` を呼べば、`auto_*` を任意の値に書き換えられます**（RLS は自分の行かどうかしか見ない）。`created_at`・`updated_at` も同じです。影響は本人の表示にとどまりますが、契約自身が「偽れないよう」と書いている以上、その保証の仕組みを契約で決めてください。

次のどちらかを契約に明記してください（前者を推奨）。

- (a) BEFORE INSERT OR UPDATE のトリガーで、`auto_*` を常に `ownership_judgments` から求め直し、`created_at` は insert 時の値に固定、`updated_at` は `now()` にする。`user_id`・`code` の update は拒否する（または with check と「変更不可」のトリガーで防ぐ）。この場合、契約のどの書き込み（新規・編集・確認済み）も「記録を現在の自動判定で置き換える」ので、規則と矛盾しません。
- (b) 列単位の grant にする（insert は `code`・`verdict`・`memo` だけ、update は `verdict`・`memo` だけ）。ただし `e2e/db-privileges.spec.ts` は `information_schema.role_table_grants` だけを見ているので、列の権限（`column_privileges`）も検査するように直す必要がある。

あわせて次も契約に足してください。
- `verdict` の check 制約（`president_top`／`owner_company`／`not_matched`）。API の検証だけでは、直接の書き込みを防げません。
- authenticated に付けるテーブル権限は select・insert・update・delete だけ。TRUNCATE・REFERENCES・TRIGGER は付けない。`db-privileges.spec.ts` はそれを確認する。
- **完了条件（C4-3 か C6-1）への追加**: owner の JWT で PostgREST から直接、次を試す。
  1. `auto_owner_total_pct`・`auto_shareholders_doc_id` を偽った insert・update をしても、行の記録が現在の自動判定と同じになる（または拒否される）。
  2. `created_at` の update で値が変わらない。
  3. 自分の行の `user_id` を owner2 の id に変える update と、`code` を変える update は拒否される。
  4. `verdict = 'met'` の insert は拒否される。
  5. 空白だけのメモ、1,001 文字のメモも拒否される（DB の check 制約）。

### R2: メモの「空白」と「文字数」の定義を UI・API・DB でそろえる

- **空白の範囲**: PostgreSQL の `btrim(memo)` は、既定では半角の空白 `' '` しか除きません。一方、JS の `trim()` は改行・タブ・全角空白（U+3000）なども除きます。日本語の入力では全角空白や改行だけのメモは普通に起こりえます。今のままだと「API は拒否、DB は受理」（直接の書き込みで空メモが入る）か、その逆になりえます。除く文字の集合を契約で決めてください。例: 半角空白・タブ・改行（\n、\r）・全角空白 U+3000。できれば JS の `\s` と同じ集合にし、DB の check は明示した文字クラスの正規表現で書く（`[[:space:]]` はロケールに依存するため避ける）。
- **保存する値**: 前後の空白を除いた値を保存するのか、入力のまま保存するのかを決めてください。前者を推奨します。今の書き方では、1,000 文字の本文に末尾の改行が付いた入力を受理するかどうかが決まりません。
- **文字数**: 契約はコードポイント（`char_length`）で数えると決めていますが、JS の `String.length` は UTF-16 の単位で数えます。API の検証と画面の「N / 1,000」は `[...s].length` などコードポイントで数えることを明記してください。
- **完了条件（C1-3・C4-8）への追加**:
  1. 全角空白だけ、改行だけのメモは、画面・API・DB（直接の書き込み）のどれでも拒否される。
  2. サロゲートペアの文字（例: 「𠮷」）1,000 個のメモは保存でき、表示は「1,000 / 1,000」になる。1,001 個は拒否される。

## 論点ごとの意見

### 権限設計（ownership_overrides）と「書き込みは service_role のみ」の例外

- 方針の例外にすることは妥当です。補正は利用者のデータなので、サービスロールで書けば `user_id` の決定をアプリのコードに任せることになり、かえって危険です。RLS（`user_id = auth.uid()` かつ `current_user_is_allowed()`）と、ユーザーのセッションでの書き込みは、既存の多層防御（ガード → API → RLS）とも整合します。例外の理由をマイグレーションと CLAUDE.md に書くことにも賛成です。
- ポリシーは既存と同じく `(select auth.uid())`・`(select public.current_user_is_allowed())` の形で書くことを推奨します（行ごとの評価を避ける。C7 の性能に効きます）。
- 許可の取り消し（C4-9）: Access Token Hook は新しいトークンの発行を止めるだけで、発行済みの JWT は有効期限まで使えます。したがって、RLS の `current_user_is_allowed()` が実際の防御になります。この設計は正しく、C4-9 で確かめられます。
- 保存・確認済みの関数を security invoker にするのは妥当です（definer にしないので、`search_path` の注入の心配も小さい）。ただし R1 のとおり、関数だけでは直接の書き込みを防げません。
- 後続への注意（Sprint 12 の上場廃止）: `code` は `stocks` への参照で、削除すると連鎖します。上場廃止で `stocks` の行を消す実装にすると、利用者の補正とメモが黙って消えます。上場廃止では行を消さないことを、CLAUDE.md か第8章に一言残すことを推奨します。

### AC10.5 の通知の条件

- 記録と現在の自動判定の比較（状態・理由・社長が筆頭株主か・オーナー系合計・書類ID）を DB で行い、`judged_at`・`pending_doc_id` を比べないという規則は妥当です。「同じ内容の再計算」「取り込み待ちの書類が一覧に載っただけ」を知らせないという要件を満たし、クエリの条件（モード・閾値）にも依存しません。記録と同じ内容に戻れば知らせが消えるのも自然です。
- 書類IDが変われば、数値が同じでも知らせる、という点について。毎年の有報の取り込みで、補正したすべての銘柄に知らせが出ます。仕様の文言（「自動判定が変わった場合」）より広い解釈です。しかし、補正は特定の有報の記載に基づく判断なので、見直しを促すのは利用者の利益になると考えます。容認します。ただし、知らせの表で「変わったのは書類だけ」と分かるよう、変わった項目を強調することを推奨します（任意）。
- 実装上の注意（推奨。完了条件に足すとよい）:
  - 補正時に `ownership_judgments` の行が無い（有報未取得。9U004）場合、記録は NULL になります。比較は `is distinct from` で行ってください。
  - **AC10.5 の最も素直な筋書き**は「9U004（有報未取得）に補正を付ける → 有報が取り込まれる → 知らせ」です。これが C5 にありません。C5-2 は訂正有報、C5-6 は取り下げなので、追加を推奨します（例: 9U004 の有報と抽出・大株主・役員を投入して知らせが出る）。

### ダッシュボードの件数と並べ替えを自動判定のままにする解釈

- 妥当です。ダッシュボードの「条件④を判定できた銘柄数」（AC2.2）は、取り込みの状態を示す数です。利用者ごとに変わる値にすると、意味がぶれます。

### メモ必須の解釈

- 仕様は「理由のメモを入力して保存できる」「メモを残せる」で、必須とまでは書いていません。とはいえ、補正はスクリーニングの結果を変える唯一の人手の経路です（F14 の AC14.2）。後から理由を追えることの価値は大きいので、必須にする解釈は妥当です。★ の確認とあわせて、ユーザーに一言伝えておくと安全です。

## 実装・評価での注意（契約の修正は不要。評価ではこの解釈で判定する）

1. **insert の `user_id` の扱い**: 第2章の2は「insert では `user_id` を `auth.uid()` にし（違う値を渡せば with check で拒否）」と書いています。トリガーが `user_id` を**無条件に** `auth.uid()` で上書きすると、with check には常に自分の id が渡ります。その場合、owner2 が owner の id を指定した insert は拒否されず、owner2 の行として黙って保存されます。
   - これは C4-3 の3つ目（「`user_id` に owner の id を指定した insert は RLS で拒否される」）を満たしません。
   - トリガーは「`user_id` が NULL のときだけ `auth.uid()` を入れ、値が渡されたときはそのまま残す」にしてください。そうすれば、渡された値が違うときは with check で拒否され、`user_id` を省いた insert は自分の id で保存されるので、C4-3 と C6-4 の6の両方を満たせます。
   - 評価では C4-3 のとおり「拒否される」ことを確かめます。
2. C6-4 の「トリガーの関数を authenticated が実行できない」について: PostgreSQL は、トリガーが発火するときには関数の EXECUTE 権限を確かめません。したがって、authenticated から EXECUTE を revoke しても、トリガーは動きます。トリガー関数を security invoker にする場合、関数の中で `ownership_judgments` を読むので、RLS 上の許可ユーザーだけが書けることになり、それで問題ありません。
3. C1-3 の 1,001 文字の入力: `textarea` に `maxlength` を付けると、1,001 文字を入力できず、文言を確かめられません。付ける場合は、「1,001 文字目が入らないこと」を確かめ、API（C4-8）で 400 になることを別に確かめます。付けない場合は、契約どおり文言を確かめます。どちらの場合も、画面の上限をコードポイントで数えていることを「𠮷」で確かめます（`maxlength` は UTF-16 の単位で数えるため、「𠮷」500 個で止まってしまう。つまり `maxlength` を付けると C1-3 の「𠮷」1,000 個を保存できない）。**そのため、実際には `maxlength` は付けられない**と考えてください。
