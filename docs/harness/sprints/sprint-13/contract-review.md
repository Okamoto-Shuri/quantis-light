## 修正必須

### R1: 既定の切り替えを「対象の行が自分のものであるときだけ」行い、同時実行と POST の既定も1トランザクションにする

第2章の2は、`set_default_screening_preset(p_id)` の処理を「同じユーザーのほかの行の既定を外してから、指定した行を既定にする」と書いています。この順番のまま素直に実装すると、次の問題が起きます。

1. **他人の行・存在しない id を指定すると、自分の既定だけが消える。**
   - 関数は security invoker なので、RLS で `p_id` の行は見えず、2つ目の update は0行になります。
   - しかし1つ目の「ほかの行の既定を外す」は、自分の行に作用します。
   - 結果として、PostgREST の `rpc/set_default_screening_preset` に存在しない uuid を渡すだけで、既定が解除されます。
   - PATCH `{"isDefault": true}` を存在しない id に送った場合、API が先に行の有無を確かめなければ、404 を返しても DB は変わっています。これは C3-5 の「DB は変わらない」に反します。
2. **同時に2つの切り替えを行うと、片方が一意の違反（23505）で失敗する。**
   - READ COMMITTED では、後から来た方の「ほかの行の既定を外す」は、先の方がコミットした新しい既定の行を見ません。
   - そのため、指定した行を既定にするときに、部分一意索引に当たります。
   - API がこれを名前の重複（`duplicate_name`）と取り違えると、利用者に誤った文言が出ます。
3. **POST の `isDefault: true` が1トランザクションになっていない。**
   - 契約で1トランザクションと明記しているのは PATCH だけです。
   - POST を「insert → 切り替えの RPC」の2要求で実装すると、途中で失敗したときに「保存はされたが既定にならない」状態が残ります。

契約に次を足してください。

- 切り替えの関数は、まず `p_id` の行を `select … for update`（RLS 下）で取る。無ければ何も変えずに「見つからない」を返す（例外か、戻り値）。有れば、ほかの行の既定を外し、この行を既定にする。
- 切り替えの関数と、insert の上限の確認は、同じユーザーごとのロック（`pg_advisory_xact_lock`）を取ってから行う。こうすれば、同じユーザーの切り替えは直列になる。
- POST で `isDefault: true` のとき、insert と既定の切り替えは1トランザクションにする（関数にまとめる）。
- API は 23505 を制約の名前で区別する。名前の一意の違反は 409 `duplicate_name`。既定の部分一意索引の違反は（直列化で本来は起きないが）500 か再試行にし、`duplicate_name` にしない。
- **完了条件への追加**:
  - C3-5: 既定が「厳しめ」のときに、`PATCH /api/screening/presets/<存在しない uuid>` に `{"isDefault":true}` を送ると 404。DB の既定は「厳しめ」のまま。
  - C5-4: owner2 の JWT で `rpc/set_default_screening_preset` に owner の行の id を渡す。owner の既定は変わらず、owner2 自身の既定も変わらない。
  - C6-1: 同じユーザーで、別の行を既定にする切り替えを2つ並行に行う。どちらもエラーにならないか、エラーでも既定は常に1個になる（期待する方を契約で決める。推奨は「どちらも成功し、後の方が既定になる」）。
  - C1-7（または C4）: `POST {"isDefault": true}` で既存の既定が外れ、新しい行だけが既定になる。

### R2: `query` の check が許す文字を明示する（リダイレクトの安全性の根拠）

既定のプリセットのリダイレクト先は `/screening?<保存したクエリ>` で、保存したクエリはそのまま URL になります。第2章の2は「値は文字の種類と長さだけを見る」と書いていますが、**種類が決まっていません**。

PostgREST の直接の書き込みで、次のような値が形の検査を通ると、リダイレクトの Location の組み立てや、ほかの経路（F13 のダッシュボード、銘柄詳細のリンク）が壊れる恐れがあります。

- `%`（二重のデコード）
- `#`
- `/`・`\`
- 空白
- CR・LF（`$` の扱い）
- 非 ASCII

外部へのリダイレクトにはなりません（パスは固定）。しかし「DB は形だけ」という設計の安全性は、この文字の範囲に依存しています。

次を契約に明記してください。

- パラメータごとの値の文字クラス。例:
  - 閾値 `-?[0-9.]{1,8}`（`cagr=99999` のように範囲・文法の外でも、C2-11 のとおり受け付けられる長さにする）
  - `ownermode`・`sort` `[a-z]{1,16}`
  - `off` `[a-z,]{1,40}`
  - `market`・`sector` `[0-9,]{1,200}`
  - `order` `(asc|desc)`
- 正規表現は `^…$` で全体に当て、改行を含む値は拒否する（`\n` で `$` が通らないことをテストで確かめる）。
- **完了条件への追加（C5-5）**: 次を含む `query` は拒否される。`%2C`・`#`・`/`・半角空白・改行・全角文字、`cagr=20&cagr=30…`（重複）。
- あわせて、C2-11 の `cagr=99999` が形の検査を通ることを C6-1 で確かめる（5桁は `parseScreeningParams` の文法では無効。形の検査が文法まで見てしまうと、C2-11 を再現できない）。

### R3: プリセットの一覧の読み出しに失敗したときの表示を決める

第2章の4は、既定のプリセットの読み出しの失敗（`preset-load-error`）だけを定めています。C4-11 は authenticated の select の権限を外すので、**一覧の読み出しも同時に失敗します**。その場合のセレクター・管理・保存の振る舞いが契約にありません。

失敗を「保存したプリセットはありません」と表示すると、プロジェクトの方針（「集計の失敗は 0 件として扱わずエラー表示にする」。CLAUDE.md のダッシュボード）に反します。利用者は、プリセットが消えたと誤解します。

次を決めて、C4-11 に入れてください。

- 一覧を読めないとき、セレクターのメニューに「プリセットを読み込めませんでした」を出す（「保存したプリセットはありません」は出さない）。管理のダイアログも同じにする。
- 「標準の条件」の適用は、今までどおりできる。
- 「現在の条件を保存」の扱いを決める（無効にするか、押せるが失敗の文言を出すか）。
- `GET /api/screening/presets` の失敗は 500（`jsonNoStore`）で、空の配列を返さない。

## 論点ごとの意見

### screening_presets の RLS・トリガー・権限（Sprint 11 と同水準か）

- **同水準です（R1 を除く）。**
  - RLS の4つの操作と with check は `(select auth.uid())`・`(select current_user_is_allowed())` の形です。
  - authenticated に付けるのは select・insert・update・delete ちょうど、anon には何も付けません。
  - トリガーは `user_id` を NULL のときだけ補い、`id`・`user_id` の変更を拒否し、日時を固定します。
  - 名前と `query` を check 制約で守ります。
  - これらは Sprint 11 の契約レビューの R1・R2・注意1 をすべて満たしています。
- 他人の行: select・update・delete は RLS で0行になり、insert は with check で拒否されます（C5-4 で判定できます）。
- 上限 50 件: insert だけで数えますが、`user_id` の変更を拒否するので、行を移して上限をすり抜けることはできません。ユーザーごとの advisory lock で同時の insert も直列になります（C6-1 で判定できます）。
  - トリガーが security invoker なら、数えるのは RLS で見える自分の行だけです。これは正しい動きです。
  - `pg_advisory_xact_lock` は PUBLIC が実行でき、`alter default privileges` の影響も受けません。
- 名前の一意: 前後の空白を除いた後の (`user_id`, `name`) の一意索引で守られます。トリガーが空白を除いてから、索引と check が評価されるので、順番も正しいです。
- 既定の一意: 部分一意索引で守られます（C5-5-3）。ただし、切り替えの関数の順番と同時実行は R1 のとおり直してください。
- トリガー関数の EXECUTE を authenticated に付けない点（C6-4）: トリガーの発火には EXECUTE の権限は要らないので、問題ありません（Sprint 11 の注意2と同じ）。
- 提案（任意）: 名前に U+200B（ゼロ幅空白）など `\s` に含まれない不可視の文字だけが入ると、見えない名前ができます。仕様の範囲外なので、必須にはしません。

### 正規形のクエリ文字列で保存し、DB は形だけ・値は読み出し時に既定値＋注記とする設計

**妥当です。**

- 状態の正本は URL（AC6.7）で、プリセットは「名前の付いた URL」です。そのため、適用・既定のリダイレクト・F13 での利用のどれも、同じ `parseScreeningParams` を通ります。
- DB に範囲の2つ目の実装を作らないので、範囲や業種の一覧が将来変わっても、ずれは読み出し時の注記として表に出ます。
- 範囲外の値が入っても、害は本人の画面の注記だけです。値そのものは URL に直接書いても同じです。

ただし、安全性の根拠は形の検査の文字クラスなので、それを R2 で明記してください。

補足（任意）:
- 形は正しく、値の範囲も有効だが、正規形ではないクエリがありえます。例: 直接の書き込みで入れた `cagr=020`、`market=0113,0113`。
  - これは `invalidFields` が空なので注意の印が出ません。一方で、完全一致で比べるので「適用中」には決してなりません。
  - 「`serialize(parse(q))` から `page` を除いたものが `q` と違えば、無効と同じ扱いにする」と定義すると、利用者が理由の分からない不一致に出会いません。評価では、どちらの扱いでも、クラッシュしないことだけを確かめます。
- 同じクエリのプリセットが2つある場合と、プリセットのクエリが標準の条件と同じ場合、セレクターに何を表示するかを決めてください。推奨は「作成の古いプリセット → 標準の条件」の順です。第2章の3の「完全に一致するプリセット」が複数ありうるので、C2 で判定するために必要です。

### 「条件のパラメータが1つも無いときだけ既定のプリセットへリダイレクト」

**妥当です。ループはありません。**

- ループ: 保存したクエリは check により必ず `cagr=` で始まります。そのため、リダイレクト先は必ず条件のパラメータを持ち、再びリダイレクトすることはありません。
  - 読み出しに失敗したときは、リダイレクトせずに標準の条件で描画するので、失敗でもループしません。
  - `?utm=x` → リダイレクトで `utm` が落ちる点も、未知のパラメータを無視する既存の規則と矛盾しません。
- 戻る・進む:
  - サーバーのリダイレクトなので、履歴に残るのはリダイレクト先の URL だけです（直接の入力でも、Link のクライアント遷移でも同じ）。
  - プリセットの適用は `router.replace` なので、「戻る」はスクリーニングの前の画面に戻ります（C2-8 で判定できます）。
- ナビゲーションの戻り先・銘柄詳細（AC7.6）:
  - 詳細をスクリーニングから開いたとき、そのリンクは表示中の条件のクエリ付きです。そのため、パンくず・ヘッダーの「スクリーニング」・「戻る」は、どれも条件のパラメータのある URL になり、既定で上書きされません。
  - 条件のパラメータの無い詳細（取り込み状況の「銘柄詳細を開く」など）は、既定のプリセットで判定します。戻り先の `/screening` も同じ既定になるので、判定と戻り先が一致します。
  - 既存の `SCREENING_PARAM_KEYS`（`page` を含む、`lib/stocks/detail.ts`）と同じ定義を使う点も良いです。
- 振る舞いの変化（ユーザーの判断は不要と考えます）:
  - `/screening?…` を表示中にヘッダーの「スクリーニング」を押すと、これまでは標準の条件に戻りました。今後は既定のプリセットに戻ります。
  - これは AC12.4 の「開いたとき」の自然な解釈で、AC7.6 は詳細からの戻りの話なので、矛盾しません。
- API に既定を当てない解釈:
  - **妥当です。** API は呼び出し側が条件を明示するものです。API にも当てると、同じ `GET /api/screening` の結果がユーザーの設定で黙って変わります。
  - これまでの API のテストと、Sprint 14 の設計の前提も崩れません。
  - 画面の `/stocks/9U006` と `GET /api/stocks/9U006` の判定が違いうることは、CLAUDE.md に明記してください（C10-7 に「API は当てない」とあるので、それで足ります）。
- 実装上の注意（評価で確かめます）:
  - Next.js のクライアントのルーターのキャッシュが、古いリダイレクト（変更前の既定）を再利用しないこと。
  - C4-3 は、「管理」で既定を変えた後、**再読み込みせずに**ヘッダーの「スクリーニング」を押して確かめます（契約の文言にそう書くと確実です）。
  - `redirect()` は描画中に投げるので、C4-12 の時計のずれの検査が必要です。これは契約に入っています。
  - `requireAllowedUser()` の後にリダイレクトすることも必要です（未ログインは `/login?next=` が先）。
  - C4-2 の `curl -sI` は HEAD の要求です。Next.js はページの HEAD を GET と同じに処理するので 307 になるはずですが、評価では `curl -s -o /dev/null -w '%{http_code} %{redirect_url}'`（GET）でも確かめます。

### 適用を router.replace にする点、表示中の結果の条件を保存する点

- **router.replace**: 妥当です。Sprint 6 の「条件の操作は履歴を増やさない」と一貫しています。「最後に選んだプリセット」を持たず、URL との一致だけで「適用中」を決めるので、リロード・戻る・進むで表示がぶれません。
- **待っている書き換えの取り消し**（C2-6）と **`resetToken` による入力欄の作り直し**（C2-5）は、既存の仕組みに沿っています。
- **表示中の結果の条件を保存する**: Sprint 7 の `openDetail`（行から詳細への遷移の競合の対策）と同じ考え方です。「待っている書き換えをすぐに発行 → `isPending` が false になるまで確定を無効 → 更新後の条件を保存」という手順も、競合の対策と整合しています（C1-5 で判定できます）。
- 提案（任意）:
  - 入力欄に無効な値（「abc」）が残ったまま「現在の条件を保存」を押すと、保存されるのは表示中の条件です。例えば `cagr` は直前の有効な値になります。
  - ダイアログの要約に出るので誤解は小さいですが、入力欄にエラーがあるときは「入力中の無効な値は保存されません」と一言出すと親切です。
  - 保存のダイアログで「既定にする」を選び、既に別の既定があるときは、「『厳しめ』の代わりに既定になります」と示すと親切です（任意）。

## 確認した内容

- **R1（既定の切り替え）**: 反映済み。
  - 切り替えの関数は、次の順で処理します。
    1. ユーザーごとの advisory lock（insert の上限と同じキー）を取る
    2. 対象の行を `for update` で取る（RLS の下）
    3. 行が無ければ何も変えずに「見つからない」を返す
    4. 切り替える
  - この順番なので、他人の行・存在しない id を渡しても自分の既定は外れません。同時の切り替えも直列になり、後のコミットが勝ちます。
    - `for update` には update の権限と update のポリシーが要りますが、どちらも authenticated に付くので、問題ありません。
  - 「後のコミットが勝つ」を C6-1 で2つの接続を使って確かめる手順は、ロックの待ちまで再現できるので、判定できます。
  - POST・PATCH は1つの関数（1トランザクション）で行います。23505 は制約の名前で区別します。完了条件は C1-7（重複で失敗したら既定は変わらない）・C3-5（404 で既定のまま、名前と既定の同時の変更）・C5-4（owner2 の RPC）・C6-1 にあります。
  - PostgREST で `is_default` を直接 update すれば、関数のロックは通りません。その場合でも、部分一意索引が拒否します（C5-5-3）。したがって、既定が2個になる経路はありません。
- **R2（`query` の文字クラス）**: 反映済み。
  - パラメータごとの文字クラスの表があり、全体一致・並び固定・各パラメータ0か1回と決まりました。そのため、`%`・`#`・`/`・`\`・`?`・空白・改行・非 ASCII の文字と、重複は入りません。
  - PostgreSQL の ARE は、改行の扱いを変えるフラグが無ければ、`$` は文字列の末尾だけに当たります。末尾の `\n` は通りません。これを C5-5-5 と C6-1 で確かめます。
  - 業種 33 個（約 164 文字）は `[0-9,]{1,200}` に収まります。`cagr=99999` を通すことは C6-1 で確かめます。
  - リダイレクトの安全性の根拠（パスは固定、文字クラス）も、第2章の2に書かれています。
- **R3（一覧の読み出しの失敗）**: 反映済み。
  - 第2章の8で、次を決めています。
    - `preset-list-error`（「保存したプリセットはありません」は出さない）
    - 管理の画面は一覧も操作のボタンも出さない
    - 保存は無効にする
    - API は 500 `internal_error`
    - 詳細には注記を出す
  - C4-11 で、すべて判定できます。
- **推奨**: すべて反映済み。
  - 表示の優先順位は C2-12（チェックの印は一致するすべての項目に付ける）
  - 正規形でないクエリは無効と同じ扱い（`invalidFields` に `query`、専用の文言）
  - 更新日は JST
  - C4-3 は、再読み込みせずにヘッダーの「スクリーニング」で確かめる。振る舞いの変化の例も入っている
  - 保存のダイアログの2つの注記（C1-9）

### C4-11 を E2E で行う（select の権限を外す）ことの干渉
