## 1. 対象機能

F12。スクリーニングの条件の組み合わせに名前を付けて保存し、呼び出せるようにする。プリセットは、閾値、オン／オフ、市場・業種の絞り込み、並べ替えを含む。1つを「既定」にすると、スクリーニング画面を開いたときにその条件で表示する。プリセットはユーザーごとのデータで、他のユーザーからは見えない。

土台として使うもの:

| 使うもの | 出どころ |
|---|---|
| 条件の正本は URL。検証・正規形は `lib/screening/params.ts`（`parseScreeningParams`・`serializeScreeningParams`） | Sprint 6・10 |
| 条件パネル・`ScreeningView`（`router.replace`、入力の待ち、`resetToken` による入力欄の作り直し、詳細への遷移の競合の対策） | Sprint 6・7 |
| 銘柄詳細の判定の条件（`detailConditionsFromParams`。条件のパラメータが無ければ既定の条件） | Sprint 7 |
| 利用者が自分で書くテーブルの設計（RLS・BEFORE トリガー・authenticated は select／insert／update／delete だけ・空白の文字集合 `lib/ownership/memo.ts`） | Sprint 11 |
| API の認証（`requireApiUser()`）、同一オリジンの確認、`jsonNoStore` | Sprint 1・3 |
| 評価用ユーザー owner・owner2（許可）、intruder（許可リスト外） | Sprint 1・11 |

外部 API は呼ばない。取り込み（target）も増やさない。

## 2. 仕様上の論点と、このスプリントでの解釈

評価者は、この解釈が妥当かも判断してほしい。ユーザーの判断が必要な論点（★）は無い。どれも仕様の文言の範囲の具体化である。

### 1. プリセットに含めるもの

- 含める: 条件①〜④の閾値、オン／オフ、条件④のモード、「算出不可を含める」「判定不能の銘柄を含める」、市場区分、業種、並べ替え（列と向き）。
- 含めない: ページ（`page`）。適用すると常に1ページ目になる。
- **プリセットの中身は、正規形のクエリ文字列**（`serializeScreeningParams` の出力から `page` を除いたもの）で保存する。例: `cagr=20&margin=10&years=5&owner=20&ownermode=any&market=0113&sort=cagr&order=desc`。
  - 理由: スクリーニングの状態の正本は URL で、プリセットは「名前の付いた URL」と同じ意味にする。条件の文法・範囲の定義は `parseScreeningParams` の1か所のままにし、DB に同じ規則の2つ目の実装を作らない。適用はこのクエリを URL にすることなので、プリセットの意味と URL の意味がずれない。
  - 読み出したクエリは、URL と同じ `parseScreeningParams`（画面は寛容な解釈）で条件にする。無効な項目は既定値にして注記する（第2章の6）。

### 2. 保存（ユーザーごと）と、直接の書き込みへの防御

- 新しいテーブル `public.screening_presets`（名前は目安）。
  - 列: `id`（uuid）、`user_id`（`auth.users` への参照、削除で連鎖）、`name`、`query`、`is_default`、`created_at`、`updated_at`。
  - 一意: (`user_id`, `name`)。既定は各ユーザーで0か1個（`user_id` の部分一意索引 `where is_default`）。
- **これは利用者のデータで、市場データではない**。Sprint 11 の `ownership_overrides` と同じ方針にする。
  - 書き込みは、そのユーザー自身のセッション（RLS）で行う。サービスロールは使わない。
  - RLS: select・insert・update・delete のすべてで「`user_id = (select auth.uid())` かつ `(select public.current_user_is_allowed())`」。insert・update の with check も同じ。
  - anon には権限なし。authenticated には select・insert・update・delete だけを grant する（TRUNCATE・REFERENCES・TRIGGER は付けない）。CLAUDE.md の「書き込みは service_role のみ」の例外に、このテーブルを加える。
- **BEFORE INSERT OR UPDATE のトリガー**（行単位）が、行の中身を守る。
  - insert: `user_id` が NULL のときだけ `auth.uid()` を入れる。値が渡されたときはそのまま残す（違えば with check で拒否。Sprint 11 の契約レビューの注意1）。`created_at`・`updated_at` を `now()` にする。
  - update: `id`・`user_id` の変更は例外で拒否する。`created_at` は元の値に固定する。`updated_at` は、**`name` か `query` が変わったときだけ** `now()` にし、ほかは元の値に固定する。既定の切り替えだけでは「更新」にしない（Sprint 11 評価の m4 と同じ指摘を避ける）。
  - `name` の前後の空白を除く（第2章の5の文字集合）。
  - insert で、そのユーザーの行が既に **50 件**あれば拒否する。同じユーザーの同時の insert で上限を超えないよう、**ユーザーごとのロック**（`pg_advisory_xact_lock`。キーは `user_id` から作る）を取ってから数える。このロックは、下の既定の切り替えと同じキーにする（同じユーザーの insert と切り替えは直列になる）。
- **check 制約**:
  - `name`: 前後に空白が無く、1〜40 コードポイント、制御文字（U+0000〜U+001F、U+007F〜U+009F）と U+2028・U+2029 を含まない（第2章の5）。
  - `query`: 正規形の**形**だけを確かめる。パラメータの並びと名前を固定した正規表現を、**文字列の全体**（`^…$`）に当てる。
    - 形と、パラメータごとの値の文字クラス（R2）:

      | 位置 | パラメータ | 値の文字クラス |
      |---|---|---|
      | 必須・1〜4番目 | `cagr`・`margin`・`years`・`owner` | `-?[0-9.]{1,8}` |
      | 必須・5番目 | `ownermode` | `[a-z]{1,16}` |
      | 任意 | `off` | `[a-z,]{1,40}` |
      | 任意 | `unavailable` | `include` だけ |
      | 任意 | `undeterminable` | `include` だけ |
      | 任意 | `market` | `[0-9,]{1,200}` |
      | 任意 | `sector` | `[0-9,]{1,200}` |
      | 必須・最後から2番目 | `sort` | `[a-z]{1,16}` |
      | 必須・最後 | `order` | `asc` か `desc` |

      区切りは `&` と `=` だけ。任意のパラメータは上の順番で、それぞれ0回か1回。
    - したがって、`%`・`#`・`/`・`\`・`?`・空白・改行（CR・LF）・非 ASCII の文字は入れられない。同じパラメータの重複（`cagr=20&cagr=30…`）、順番の違い、`page`・未知のパラメータも入れられない。
      - 保存したクエリはそのまま `/screening?` の後ろに付けて URL にする（リダイレクト、銘柄詳細の戻り先、F13）。安全性の根拠は、この文字クラスである。パスは固定なので、外部へのリダイレクトにはならない。
      - PostgreSQL の正規表現で、末尾の改行が `$` を通らないことをテストで確かめる（C6-1）。
    - 長さは 1,000 文字まで。
    - 値の範囲・文法（例: `cagr=99999`、`cagr=1.2.3`、`ownermode=xyz`、`market=9999`）は DB では確かめない。形の検査は、C2-11 の `cagr=99999` を通す（C6-1）。
      - 範囲は `parseScreeningParams` の1か所で決め、読み出しで無効な項目を既定値にする（第2章の6）。
      - 利用者は同じ値を URL に直接書くこともできるので、プリセットに入っても害は本人の画面の注記だけである。
  - `is_default`: not null。
- **既定の切り替え**（R1）は、1つの関数（security invoker。例 `set_default_screening_preset(p_id uuid, p_default boolean)`）で、次の順に行う。
  1. ユーザーごとのロック（insert の上限と同じキー）を取る。同じユーザーの切り替え・insert は直列になる。
  2. `p_id` の行を `select … for update` で取る（RLS の下なので、自分の行だけが見える）。
  3. 行が無ければ（存在しない id・他人の行）、**何も変えずに**「見つからない」を返す（戻り値か、決めた SQLSTATE の例外。API は 404 にする）。
  4. 既定にするとき（`p_default = true`）: 同じユーザーのほかの行の既定を外し、この行を既定にする。解除するとき: この行の `is_default` を false にする。
- 同じユーザーで、別の行を既定にする切り替えを2つ同時に行うと、ロックで直列になる。**どちらも成功し、後の方が既定になる**（C6-1）。
- **POST で `isDefault: true`** のときは、insert と既定の切り替えを1つの関数（例 `create_screening_preset(p_name, p_query, p_default)`）で1トランザクションにする。途中で失敗したら、行も既定も残らない。
- PATCH の複数の変更（名前・クエリ・既定）も、1つの関数で1トランザクションにする。存在しない id・他人の行なら、何も変えずに「見つからない」を返す。
- **一意の違反（23505）は、制約（索引）の名前で区別する**。
  - 名前の一意の違反 → 409 `duplicate_name`。
  - 既定の部分一意索引の違反（直列化で本来は起きない）→ 500 `internal_error`。`duplicate_name` にはしない。
- 許可リストから外れたユーザーのプリセットは、行としては残るが、読めず書けない（RLS）。

### 3. 適用（AC12.2）

- プリセットを選ぶと、そのクエリを条件にし（`parseScreeningParams`）、`ScreeningView` の既存の経路（`apply`）で URL を書き換える。
  - 書き換えは今の条件の操作と同じ `router.replace` で、履歴を増やさない（Sprint 6 の方針。「戻る」はスクリーニングの前の画面に戻る）。
  - 待っている条件の書き換え（数値入力の 400ms など）は取り消し、プリセットの条件だけを書く。
  - 条件パネルを作り直す（`resetToken`）。入力欄に残った無効な値とエラーの表示は消える。
  - 1ページ目に戻る。
- 「適用中」の表示は、URL から求める。保存したクエリが、今の条件の正規形（`page` を除く）と**完全に一致する**プリセットを、セレクターに表示する。一致が無ければ「保存されていない条件」。条件を変えれば一致しなくなり、元の値に戻せば再び一致する。「最後に選んだプリセット」は持たない（リロードで状態が変わらないように）。
- 「標準の条件」（アプリの初期値。`DEFAULT_CONDITIONS`）も、常にセレクターの先頭に出す。
- **表示の優先順位**（一致が複数あるとき）: 次の順で、最初に当たったものをボタンに表示する。
  1. 一致するプリセットのうち、作成の最も古いもの
  2. 標準の条件
  3. 「保存されていない条件」
  
  例:
  - 同じクエリのプリセットが2つあれば、古い方を表示する。
  - プリセットのクエリが標準の条件と同じなら、プリセットの名前を表示する。
  
  メニューのチェックの印は、一致するすべての項目に付ける（同じ条件であることが分かるように）。
- 無効な項目のあるプリセット・正規形でないプリセット（第2章の6）は、一致とみなさない。

### 4. 既定のプリセット（AC12.4）

- **「スクリーニング画面を開いたとき」＝ URL に条件のパラメータ（`SCREENING_PARAM_KEYS`。`page` を含む）が1つも無いとき**。例: ヘッダーのナビゲーションの「スクリーニング」、ブックマークした `/screening`、銘柄詳細（条件のパラメータなし）のパンくず。
  - そのユーザーに既定のプリセットがあれば、サーバーが `/screening?<保存したクエリ>` へリダイレクトする（URL が状態の正本のまま。リロード・共有しても同じ条件）。
  - 保存したクエリは check 制約で必ず `cagr=` から始まるので、リダイレクトの先で再びリダイレクトすることは無い。
  - 条件のパラメータのある URL（スクリーニングの操作、詳細からの戻り先、明示的な URL）は、既定のプリセットで上書きしない。AC6.7・AC7.6 を保つ。
  - リダイレクトは `requireAllowedUser()` の後に行う（未ログインは今までどおり `/login?next=` が先）。
  - 既定を変えた直後に、再読み込みせずにヘッダーの「スクリーニング」を押しても、新しい既定のプリセットになる。クライアントのルーターのキャッシュが、変更前の既定へのリダイレクトを再利用しないこと（C4-3）。
- **振る舞いの変化（AC12.4 の解釈）**:
  - スクリーニングを表示中に、ヘッダーのナビゲーションの「スクリーニング」を押した場合、ナビゲーションのリンクは `/screening`（条件のパラメータなし）である。
  - 既定のプリセットがあれば、**既定のプリセットの条件に戻る**。これまでは標準の条件に戻った。
  - これは「スクリーニング画面を開いたとき」の自然な解釈とする。ナビゲーションの「スクリーニング」は画面を開き直す操作である。
  - AC7.6 は詳細からの戻りの話で、詳細を開いている間のヘッダーの「スクリーニング」は、今までどおり直前の条件の URL になる（`lib/navigation-href.ts`）。したがって矛盾しない。
  - 既定のプリセットが無ければ、今までどおり標準の条件になる。
- 既定のプリセットの読み出しに失敗したときは、例外を投げずに標準の条件で描画し、「既定のプリセットを読み込めませんでした（標準の条件で表示しています）」と注記する。
- 条件パネルの「既定の条件に戻す」は、既定のプリセットがあればその条件、無ければ標準の条件にする。ボタンの説明（`title`・`aria-description` など）で、どちらに戻すかを示す（例「既定のプリセット『グロースのみ』の条件に戻します」）。
- **銘柄詳細**: 条件のパラメータの無い詳細（`/stocks/9U006`）は、既定のプリセットがあればその条件で判定する。表示は「既定のプリセット『厳しめ』の条件で判定しています」。無ければ今までどおり「既定の条件で判定しています」。戻り先は今までどおり `/screening`（既定のプリセットへリダイレクトされる）。
- **API は既定のプリセットを当てない**。`GET /api/screening`・`GET /api/stocks/[code]` は、条件のパラメータが無ければ標準の条件のまま（今までと同じ）。API は呼び出し側が条件を明示するもので、既定のプリセットは「画面を開いたときの条件」だからである。プリセットの条件は、プリセットの API で得たクエリを付けて呼べば使える。

### 5. 名前の規則（画面・API・DB で同じ定義）

- 空白の文字集合は、Sprint 11 のメモと同じ（JavaScript の `\s` の集合。`lib/ownership/memo.ts` の定数を、共有の場所に移して使う）。
- 保存する値は、前後の空白を除いた値。
- 除いた後が **1〜40 コードポイント**（`[...s].length`。「𠮷」は1文字）。
- 途中に制御文字（タブ・改行など）と U+2028・U+2029 を含められない（1行の名前）。途中の半角・全角の空白は保つ。
- 一意性: 同じユーザーの中で、除いた後の文字列が完全に一致すれば重複（全角と半角、大文字と小文字は区別する）。別のユーザーとは重なってよい。
- 文言:
  - 「名前を入力してください」
  - 「名前は 40 文字以内で入力してください」
  - 「名前に改行やタブは使えません」
  - 「同じ名前のプリセットがあります」
  - 「プリセットは 50 件まで保存できます」
- 画面の入力欄に `maxlength` は付けない（UTF-16 の単位で数えるため「𠮷」を 20 個で止めてしまう）。文字数の表示「N / 40」はコードポイントで数える。

### 6. 無効な項目を持つプリセット

API は厳しく検証するので、画面と API からは無効なクエリを保存できない。ただし、次の場合に無効な項目を持つプリセットがありうる。

- 直接の書き込み（PostgREST）で、形は正しいが範囲外の値（`cagr=99999`）を入れた
- 将来、条件の範囲や業種の一覧が変わった

その場合の扱い:

- セレクターと管理の一覧で、その名前の横に注意の印と「一部の条件が無効です」を出す。
- 適用すると、無効な項目を既定値にして適用し、「プリセット『X』の条件の一部（cagr）が無効なため、既定値で適用しました」と注記する。
- 既定のプリセットなら、リダイレクト先の URL にその値が入るので、既存の「URL の条件の一部（cagr）が無効なため、既定値で表示しています」が出る。
- 無効な項目を持つプリセットは、今の条件と一致したとはみなさない（完全一致で比べるため）。
- **正規形でないクエリも、無効と同じ扱いにする**。対象は、形は正しく、値もすべて有効だが、`serializeScreeningParams(parseScreeningParams(q))` から `page` を除いたものが `q` と違うクエリ。
  - 例（直接の書き込みでだけ入りうる）: `cagr=020`、`market=0113,0113`、`market=0113,0111`（並びが昇順でない）、`off=margin,cagr`。
  - 扱い:
    - 同じ注意の印を出す。文言は「条件の書き方が標準の形ではありません」。
    - API の `invalidFields` には `query` を入れる。
    - 適用すると正規形の条件になる。「プリセット『X』の条件を標準の形に直して適用しました」と注記する。
    - 一致とはみなさない。
  - 利用者が、理由の分からない不一致に出会わないようにするためである。
  - 判定は1つの関数（`lib/screening/presets.ts` の、クエリから条件と `invalidFields` を求める関数）で行う。

### 7. 保存・上書きする条件

- 保存・上書きするのは、**表示中の結果の条件**（サーバーが URL から判定に使った条件の正規形から `page` を除いたもの）。
- 条件の書き換えを待っている・応答を待っているときに「保存」「上書き」を押した場合:
  - 待っている書き換えをすぐに発行する（Sprint 7 の `openDetail` と同じ）。
  - ダイアログの確定のボタンは、結果が更新されるまで無効にし、「結果の更新を待っています」と示す。
  - 更新された後の条件を保存する。入力欄の途中の値が保存に混ざることは無い。
- 保存・上書きのダイアログに、保存する条件の要約を出す（第4章）。利用者が、何を保存するかを確かめられるように。
- 条件パネルの入力欄に無効な値（「abc」など、エラーを表示中）が残ったまま保存・上書きを押した場合:
  - 保存されるのは、表示中の結果の条件（その閾値は直前の有効な値）。
  - ダイアログに「入力中の無効な値は保存されません（売上CAGR は 20% で保存します）」の形で注記する（`preset-invalid-input-note`）。
  - 入力欄のエラーの状態を `ScreeningView` が知る必要がある。`ThresholdField` から条件ごとのエラーの有無を上げる。

### 8. プリセットの一覧を読めないとき（R3）

「読めない」を「0件」として表示しない（CLAUDE.md の「集計の失敗は 0 件として扱わずエラー表示にする」と同じ方針）。

- 画面（`/screening`）は例外を投げずに描画する。既定のプリセットの判定も読めないので、リダイレクトせずに標準の条件で描画し、`preset-load-error` を出す（第2章の4）。
- セレクター:
  - ボタンの文字は、今の条件が標準なら「標準の条件」、違えば「保存されていない条件」（プリセットとの一致は判定できない）。
  - メニューには「標準の条件（アプリの初期値）」と、`preset-list-error`「プリセットを読み込めませんでした。再読み込みしてください」を出す。「保存したプリセットはありません」は出さない。
  - 「標準の条件」の適用は、今までどおりできる。
- 管理のダイアログ: 一覧の代わりに同じ `preset-list-error` を出す。操作のボタンは出さない。
- 「現在の条件を保存」は**無効にし**、「プリセットを読み込めないため保存できません」と示す。上限（50 件）や名前の重複を画面で判断できないため。
- `GET /api/screening/presets` の読み出しの失敗は 500 `{"error":"internal_error"}`（`jsonNoStore`）。空の配列を返さない。
- 銘柄詳細（条件のパラメータなし）は、既定のプリセットを読めなければ既定の条件（今までどおり）で判定する。「既定のプリセットを読み込めませんでした（既定の条件で判定しています）」と注記する。

    - 余裕が無ければ、プリセットの行を注記の直後（要約のカードの外）に置いてもよい。置き場所は self-review に書く。

      - 名前
      - 既定なら「既定」のバッジ（`preset-default-badge`）
      - 一致していればチェックの印（第2章の3）
      - 無効な項目があれば、注意の印と「一部の条件が無効です」。正規形でなければ「条件の書き方が標準の形ではありません」（第2章の6）

  - 名前の入力欄（ラベル「プリセットの名前」）と文字数「N / 40」。
  - チェックボックス「既定にする（スクリーニングを開いたときにこの条件で表示します）」。既に別の既定があるときは、チェックの下に「『厳しめ』の代わりに既定になります」と示す。

    - 「適用」

- 条件のパラメータが無く、既定のプリセットがあるとき、条件の判定の区画の説明を「既定のプリセット『<名前>』の条件で判定しています」にする（`data-condition-source="preset"`）。
  - スクリーニングから開いたときは `screening`、既定のプリセットが無いときは `default`（今までの文言）。

### エンドポイント

すべて `requireApiUser()`（未ログイン 401・許可リスト外 403・Auth 障害 503）、`jsonNoStore`。書き込みは同一オリジンの確認（違えば 403 `{"error":"cross_origin"}`）。読み書きはユーザーのセッション（RLS）。

| メソッドとパス | 内容 |
|---|---|
| `GET /api/screening/presets` | 自分のプリセット（作成の古い順）。200 `{"data": [<preset>]}` |
| `POST /api/screening/presets` | 本文 `{"name": "…", "query": "cagr=…", "isDefault": false}`（`isDefault` は省略可）。201 `{"data": <preset>}` |
| `PATCH /api/screening/presets/[id]` | 本文 `{"name"?, "query"?, "isDefault"?}`（1つ以上）。名前の変更・上書き・既定の切り替え。1回の要求の変更は1トランザクション。200 `{"data": <preset>}` |
| `DELETE /api/screening/presets/[id]` | 削除。200 `{"deleted": true}` |

- `query` は URL のクエリの文法で受け取り（先頭の `?` は付けない）、厳しく検証する（`parseScreeningParams` で `invalidFields` があれば 400）。
  - 保存するのは正規形（`serializeScreeningParams`）から `page` を除いたもの。
  - `page` と未知のパラメータは無視する（URL と同じ）。
- エラー:
  - 本文が JSON でない: 400 `invalid_body`
  - 値が不正: 400 `invalid_preset`。`fields` に `name`・`query`・`isDefault`。`query` の不正な項目は `queryFields`（例 `["cagr"]`）
  - PATCH の本文が空: 400 `invalid_preset`
  - 名前の重複: 409 `duplicate_name`
  - 上限: 409 `preset_limit`
  - id が uuid の形でない: 400 `invalid_id`
  - 無い、または他のユーザーのもの: 404 `not_found`（DB は変わらない。`isDefault` を含む PATCH でも、ほかの行の既定は外れない。第2章の2）
  - 読み出し・書き込みの DB の失敗、既定の部分一意索引の違反: 500 `internal_error`（第2章の2・8）
- 23505 は制約の名前で区別する（第2章の2）。
- `POST` の `isDefault: true` は、保存と既定の切り替えを1トランザクションで行う（既存の既定は外れる）。

`<preset>` の形:

```json
{
  "id": "0b7c…",
  "name": "グロースのみ",
  "query": "cagr=20&margin=10&years=5&owner=20&ownermode=any&market=0113&sort=cagr&order=desc",
  "isDefault": true,
  "conditions": { "cagr": "20", "margin": "10", "…": "（toApiConditions の形）" },
  "invalidFields": [],
  "createdAt": "2026-09-25T10:00:00+09:00",
  "updatedAt": "2026-09-25T10:00:00+09:00"
}
```

- `GET /api/screening`・`GET /api/stocks/[code]` は変えない（第2章の4。既定のプリセットは当てない）。

### 投入例 `e2e/fixtures/screening-presets-example.sql`（`postgres` ユーザーで実行。owner の3件、既定なし）

```sql
insert into public.screening_presets (user_id, name, query)
select u.id, p.name, p.query
  from auth.users u
 cross join (values
   ('グロースのみ', 'cagr=20&margin=10&years=5&owner=20&ownermode=any&market=0113&sort=cagr&order=desc'),
   ('厳しめ',       'cagr=20&margin=10&years=5&owner=40&ownermode=any&sort=owner&order=desc'),
   ('スタンダード④なし', 'cagr=20&margin=10&years=5&owner=20&ownermode=any&off=owner&market=0112&sort=code&order=asc')
 ) as p(name, query)
 where u.email = 'owner@quantis.local';
```

   - セレクターは「標準の条件」で、メニューに owner のプリセットが無い（「保存したプリセットはありません」）。

3. owner2 が「グロースのみ」（owner と同じ名前。重複にならない）を `off=owner` の条件で保存し、既定にする。owner の画面（リロード後）は変わらない（owner の「グロースのみ」の条件・既定のまま）。
4. owner2 の JWT（公開キー＋ owner2 のアクセストークン）で PostgREST を直接呼ぶ。
   - `screening_presets` の select は owner2 の行だけを返す。
   - owner の行の update・delete（`id=eq.<owner の行>`）は0行に作用し、owner の行は変わらない。
   - `user_id` に owner の id を指定した insert は RLS で拒否される。
   - **（R1）** `rpc/set_default_screening_preset` に owner の行（「厳しめ」）の id を渡す。
     - 「見つからない」（関数の戻り値か、決めたエラー）になる。
     - owner の既定は変わらない（「グロースのみ」のまま）。
     - owner2 自身の既定も変わらない（owner2 に既定がある状態で確かめる）。
   - 存在しない uuid を渡しても同じで、owner2 の既定は外れない。
5. owner の JWT で PostgREST を直接呼ぶ（直接の書き込みへの防御。第2章の2）。どれも拒否されるか、DB が値を決め直す。
   1. 自分の行の `user_id` を owner2 の id にする update、`id` を変える update → 拒否。行は変わらない。
   2. `created_at` を過去にする update → `created_at` は変わらない。`updated_at` を過去にする update（名前・クエリは同じ）→ `updated_at` は変わらない。
   3. 2つ目の行の `is_default = true` の update（既定が既にある）→ 一意制約で拒否。
   4. `name` が空・半角空白だけ・全角空白だけ・41 コードポイント・途中にタブや改行 → 拒否。前後に全角空白のある名前の insert → 除いた値で保存される。
   5. `query` が次のどれかなら拒否される（R2）。
      - 空、`foo=bar`
      - `page=2&cagr=20…`、正規形の末尾に `&page=2`
      - パラメータの順番の違う形（`margin=10&cagr=20…`）
      - 同じパラメータの重複（`cagr=20&cagr=30&margin=10…`）
      - 値に `%2C`（`market=0111%2C0113`）・`#`・`/`・`\`・`?`・半角空白・全角文字（`cagr=２０`）を含む
      - 改行を含む（値の途中の `\n`、末尾の `\n`、`\r\n`）
      - 1,001 文字
      
      一方、次は通る。
      - `cagr=99999&…`（範囲外。形は正しい）
      - `ownermode=xyz&…`（文法の外。形は正しい）
   6. `user_id` を省いた insert → owner の id で保存される。
   7. 51 件目の insert → 拒否。
6. anon（公開キーだけ）では、`screening_presets` の select が0行または権限エラー。insert は権限エラー。
7. intruder（許可リスト外）のセッションでは、API は 403。DB の読み書きもできない（`pnpm test:db`）。
8. 未ログインでは、`GET`・`POST /api/screening/presets` と `PATCH`・`DELETE /api/screening/presets/<id>` が 401 で、`Cache-Control: no-store`。行は作られない。
9. `POST`・`PATCH`・`DELETE` に別のオリジンの `Origin` を付けると 403 `cross_origin` で、DB は変わらない。
