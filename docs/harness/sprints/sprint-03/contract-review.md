# Sprint 03 契約レビュー

## 判定: 修正依頼

契約の大部分は妥当です。受け入れ基準 AC3.1〜AC3.7 は、どれも削られていません。完了条件も、画面・API・DB で合否を判定できる形になっています。キーが無い環境での判定方針（第8章）も妥当です。

ただし、第2章の4（保存する範囲）に、公式ドキュメントと照らして不足があります。また、本番の時間制限と、proxy の除外範囲について、完了条件の記述が足りません。下の必須修正3点を反映した改訂版を出してください。

## 事前に確認した事実

- `GET https://api.jquants.com/v2/equities/master` を実際に呼んで確かめました。
  - 無効なキー（`x-api-key: qa-dummy-key-7f3a9c`）を付けると、HTTP 403 `{"message": "The incoming api key is invalid or expired."}` が返ります。
  - キーを付けないと、HTTP 403 `{"message": "The api key is required."}` が返ります。
  - エンドポイント、ヘッダー方式、C4-1 の期待値（HTTP 403 のメッセージ）は、実在する振る舞いと一致しています。
- 公式ドキュメント（https://jpx-jquants.com/ja/spec/eq-master）の内容は次のとおりです。
  - 応答の項目は `Date, Code, CoName, CoNameEn, S17, S17Nm, S33, S33Nm, ScaleCat, Mkt, MktNm, Mrgn, MrgnNm, ProdCat`。
  - パラメータを付けないと、「APIを実行した日付時点における全銘柄情報一覧」が返ります。
  - 応答に `pagination_key` は付きません。
  - 翌営業日時点の情報は 17:30 以降に取得できます。
- 商品区分コード（`ProdCat`、https://jpx-jquants.com/ja/spec/eq-master/product-category）の値は次のとおりです。
  - 011 内国株券、012 優先出資証券、013 REIT、014 ETF、021 外国株券、022 外国REIT、023 外国ETF、024 外国株預託証券。
  - 「全期間・全銘柄で収録されており欠損はありません」と記載されています。

## 第2章の解釈の妥当性

| 論点 | 判断 | コメント |
|---|---|---|
| 1. V2・`x-api-key` | 妥当 | 実際の呼び出しで確認した。V1 のトークン方式に対応しないことも、仕様の制約（J-Quants Standard）に反しない |
| 2. 設定状態は環境変数の有無だけで判定 | 妥当 | 「画面は保存済みデータだけを見る」制約と整合する。無効なキーは C4 で失敗として記録される |
| 3. EDINET は表示だけ | 妥当 | AC8.1 は Sprint 8 の範囲 |
| 4. 市場区分の絞り込み | **不足（必須修正1）** | `Mkt` を 0111〜0113 に絞ることと、`S33≠9999` の方針自体は妥当。ただし、応答には商品区分 `ProdCat` がある。`Mkt`＋`S33` だけでは、プライム・スタンダード・グロースに上場している優先出資証券（012）と外国株券（021）、外国株預託証券（024）が入る可能性がある。これらは「有報を提出する国内の事業会社」という第2章の4の目的から外れる。判定に使える公式の項目があるので、使うべき |
| 5. 消えた銘柄は残す | 妥当 | 連鎖削除を防ぐ理由も正しい（`financial_metrics` は `on delete cascade`） |
| 6. 1トランザクションで保存・`partial` を使わない | 妥当 | ドキュメント上、ページ送りが無いので、1回の呼び出しで全件が返るという前提は正しい |
| 7. 「実行中」は全体で1つ（部分一意インデックス） | 妥当 | 手動と Cron の競合も DB で防げる。C6-4・C6-6 で検証できる |
| 8. 15 分で応答なしとみなす | おおむね妥当（必須修正2） | 根拠の「関数の最大実行時間」は Cron のルート（300 秒）にしか設定されていない。手動取り込みの `after()` は POST のルートの制限時間の中で動くので、そのルートにも同じ上限を明記する必要がある |
| 9. Cron 実行中なら 409 で記録しない | 妥当 | Vercel Cron は再試行しないので、その日の実行は飛ぶ。ただ、実行中の取り込みが同じ処理をしているので害は無い |
| Cron の保護 | おおむね妥当（必須修正3） | Bearer、定数時間の比較、`CRON_SECRET` が未設定なら常に 401、セッションでは起動できないこと、は良い。ただし、proxy の除外が `/api/cron/` の前方一致だけになっていることを確かめる条件が無い |
| スケジュール `0 11 * * *`（20:00 JST） | 妥当 | 17:30 以降の更新に間に合う。パラメータ無しの呼び出しは実行日時点の一覧を返すので、20:00 に当日分を取れる |

## キーが無い環境での判定可能性

判定は可能です。
- C9-5〜7 だけをキーありの対象にし、成功の経路は次で代わりに確かめる構成になっています。
  - C4-1: 無効なキーで実際の API を呼ぶ。403 を実際に確認しました。
  - C9-1〜3: フィクスチャと DB 込みの結合テスト。
  - C9-4: 投入した行が表示されること。
- キーが無い評価環境では、「成功: N 件を保存しました」という結果の表示を、画面では確かめられません。改善提案の2を参照してください。

## 必須修正

1. **保存の範囲に商品区分 `ProdCat` を加える（第2章の4、第6章、C9-1、C9-6）**
   - 保存する条件に `ProdCat = '011'`（内国株券）を加える。`Mkt` を 0111〜0113 に絞る条件は残す。`S33 ≠ 9999` は残しても外してもよい。どちらにしたかを契約に書く。
   - 外国株券（021）を含めたいなら、その理由を書く。
   - `public.stocks` に `product_category`（`ProdCat`）の列を加える。
   - 対象外の件数は、これまでどおり `details.skipped` に数える。
   - C9-1 のフィクスチャに、次の行を加える。
     - `ProdCat` の項目（すべての行に付ける）
     - プライムかスタンダードの優先出資証券（012）の行
     - グロースの外国株券（021）の行
     - `Mrgn`、`MrgnNm` の項目（ドキュメントの例と同じ項目名にするため）
   - 上の行が除外されることを確かめる。
   - C9-6 に「`product_category` が `011` 以外の行が無い」を加える。
   - `ProdCat` が欠けている行は「応答の形式が想定と異なります」として扱う。ドキュメントに「欠損なし」とあるので、この扱いで問題ない。
2. **手動取り込みのルートの時間制限を明記する（第2章の8、第4章）**
   - `POST /api/ingestion/runs` にも `maxDuration`（Cron と同じ 300 秒）を設定する。`after()` の処理は、このルートの制限時間の中で動くからである。
   - 契約に「どちらのルートも 300 秒。15 分はこれより長い」と書く。第2章の8の「800 秒」の記述も、実際の設定に合わせて直す。
   - 判定方法: コードを確認する。`next build` の出力か、ルートの設定値を見る。
3. **proxy の除外が `/api/cron/` の配下に限られることを、完了条件に加える（C7-10）**
   - 未ログインで次の URL を開いたとき、401 になるか、または認証の判定を通ったうえで 404 になり、データを返さないことを確かめる。
     - `/api/cron`（末尾のスラッシュ無し）
     - `/api/cronx`
     - `/api/cron-daily`
     - `/api/cron/..%2Fingestion`
     - `/api/cron/%2e%2e/ingestion`
     - `/API/cron/daily`
   - 除外の判定は `pathname.startsWith("/api/cron/")` に相当するものにし、`/api/cron` の前方一致にしない。E2E か Vitest に含める。

## 改善提案（任意）

1. 実行を終える関数は、`status = 'running'` の行だけを更新する。応答が無いものとして後片付けされ、すでに `failed` になった行を、遅れて終わった処理が `succeeded` で上書きしないようにするためである。上書きされない場合は、処理の側で警告のログを出す。
2. 取り込みが成功したときの結果の表示（「成功: N 件を保存しました」、`role="status"`、3桁区切り）は、キーが無い環境の画面では確かめられない。結果の文言を組み立てる関数を Vitest で確かめておくと、C9-5 の見た目の不具合を事前に防げる。
3. 公式ドキュメントに、応答に `pagination_key` が付かないとあることを、第2章の6に根拠として書く。そのうえで、もし `pagination_key` が付いていたら、一部だけを保存せず、「形式が想定と異なる」として失敗にする。この扱いにしておけば、黙って一部の銘柄だけを保存することは起きない。
4. `details` に、対象外にした理由ごとの内訳を入れる（例 `skippedByMarket`、`skippedByProduct`）。あとで件数を確かめるときに役立つ。
5. `CRON_SECRET` が極端に短い（例 16 文字未満）場合は、未設定として扱うか、起動時に警告する。任意。

## 実装時の注意（合否には影響しない）

- 一覧に同じ `Code` が2回現れると、次の2つが起きる可能性があります。
  - 1回の `insert ... on conflict do update` が「ON CONFLICT DO UPDATE command cannot affect row a second time」で失敗し、取り込み全体が止まる。
  - `fetched = processed_count + skipped` が成り立たなくなる。

  公式の一覧では起きない想定です。ただ、重複を見つけたら、形式エラーにするか、1件にまとめたうえで `details` に件数を残すか、どちらかにしておくと安全です。
- 16 文字未満の `CRON_SECRET` を未設定として扱う条件（C7-12）で、C1-4 の「未設定」の表示と、C7-5 の 401 がつながります。そのため、画面の表示と Route Handler の判定は、同じ関数を使ってください。
