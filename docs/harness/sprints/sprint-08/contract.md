# Sprint 08 契約: F8 EDINET 有価証券報告書の取り込み（大株主・役員）

## 1. 対象機能

F8。EDINET API（Version 2）から各社の直近の有価証券報告書（有報）を探し、「大株主の状況」（順位、氏名・名称、持株比率）と「役員の状況」（氏名、役職名）を抽出して保存する。J-Quants の銘柄とは証券コードで対応づける。銘柄詳細画面に「大株主の状況」「役員の状況」の区画を加え、取り込み状況の画面に有報の取り込みの状況を加える。

あわせて、**EDINET の取り込みの土台**（書類一覧の取得と取得済みの日の管理、書類の取得、XBRL の読み取り、処理済みの書類の管理、実行履歴への記録）を作る。Sprint 9（F15。有価証券届出書・有報の「主要な経営指標等の推移」から上場前の期を補う）は、この土台に「対象の書類の種類」と「抽出する項目」を足すだけで作れる形にする（第2章の8）。

このスプリントには、Sprint 7 評価の B1（スクリーニングで閾値の入力の直後に行をクリックすると遷移が失われる）の修正を含める（第2章の9、C9）。

### 仕様書の受け入れ基準（引用）

- AC8.1 EDINET のキーが未設定の環境で取り込むと、実行履歴に「EDINET の API キーが設定されていません」として失敗が記録される。J-Quants 側の取り込み結果には影響しない。
- AC8.2 （キーあり環境）取り込み後、有報を取得できた銘柄の数が取り込み状況画面に表示される。

- AC8.4 同じ会社に複数の有報（訂正報告書を含む）があるときは、最新の提出分が使われ、どの書類を使ったかが表示される。

- AC8.7 抽出ロジックには、実際の有報の形をしたテスト用フィクスチャ（個人株主、法人株主、信託口、役員の兼務表記を含む）を使った自動テストがあり、通る。

- 用語「筆頭株主」「大株主上位」は「直近の有価証券報告書」の「大株主の状況」。持株比率は「発行済株式（自己株式を除く）の総数に対する所有株式数の割合」。

## 2. 仕様上の論点と、このスプリントでの解釈

評価者は、この解釈が妥当かも判断してほしい。

### 1. 実 API で確かめられない部分の扱い（キーが無い環境）

現状、`.env`・`.env.local` に `EDINET_API_KEY` は設定されていない。したがって、このスプリントでは EDINET の実際の応答を取得して確かめることができない。次のように扱う。

- **形の根拠は公開の資料に限る**: 応答の形・書類の構造は、次の公開資料で確かめてから実装する。確かめた資料（名前・版・URL）と、資料で確かめられず推定のまま実装した点を、self-review の「実 API で未確認の点」に一覧で書く。
  1. 金融庁「EDINET API 仕様書（Version 2）」（書類一覧 API・書類取得 API の要求と応答、`docTypeCode`・`ordinanceCode`・`formCode`・`secCode`・`withdrawalStatus`・`xbrlFlag` などの項目、エラーの応答）
  2. 金融庁「EDINET タクソノミ」と「報告書インスタンス作成ガイドライン」（`jpcrp_cor` の大株主・役員の要素名、コンテキストとメンバーの付け方、比率の単位）
  3. **EDINET の閲覧サイトから、キー無しで公開の有報の XBRL の ZIP を取得することを必ず試みる**（閲覧サイトの「XBRL」のダウンロード。API のキーは使わない）。少なくとも次の形の書類を探して取得する: 通常の有報、訂正有報（大株主・役員の区画を含まないもの）、株主総会の前に提出され役員の表が2つある有報、議決権の割合の大株主の表を併記した有報、比率を小数点以下3桁で記載した有報。取得できたら、**フィクスチャはその実データの抜粋から作る**（書類IDを記録する）。取得できなかった形は、資料に沿って作ったことをフィクスチャのコメントと self-review に書く。
  4. 役員の要素名・閲覧ページの URL の形（末尾が `,,` か `=` か）は、上の実データで確かめる。
- **フィクスチャ**: テスト用の XBRL（`src/lib/ingestion/edinet/__fixtures__/`）は、実データの抜粋（取得できた場合）か、上の資料に沿った実際の有報の形（名前空間、`xbrli:context`・`xbrldi:explicitMember`、`contextRef`、`unitRef`、`decimals`、`xsi:nil`、要素の並び）で作る。抜粋は、テストに必要な区画（大株主・役員とそのコンテキスト・単位、表示リンクの順の根拠に使うファイル）に絞る（書類全体をリポジトリに入れない）。元にした書類ID・資料を各フィクスチャの先頭のコメントに書く。フィクスチャはテストからだけ import し、実行中のアプリの画面・DB に出ない（C12-6）。
- **テストは外部 API だけを差し替える**: 取り込み処理は `fetchImpl` を差し替えて動かし、DB・保存の関数・画面は本物を使う（Sprint 3〜5 と同じ方式）。書類取得 API の応答は、テストの中でフィクスチャから ZIP を作って返す。
- **キーが無い環境の振る舞いは明示的なエラー**: キーが未設定なら外部 API を呼ばずに「EDINET の API キーが設定されていません」で `failed`（AC8.1）。空データの成功や0件の成功として記録しない。
- **キーが設定されたときの確認手順**を CLAUDE.md に書く（手動の取り込みを1回動かし、実行履歴の `details`・取り込み状況の件数・1銘柄の詳細を確かめる。応答の形が違えば「EDINET の応答の形式が想定と異なります」で失敗し、書類ごとの失敗は理由のコードで残る）。キーありの確認（AC8.2 の実データでの件数）は、このスプリントの合否の条件にしない（Sprint 3〜5 のキーありの AC と同じ扱い）。
- **スタブ・ダミーの禁止**: アプリの本体に、サンプルの有報・大株主・役員を置かない。画面に出るのは DB の行（取り込んだもの、または評価者が投入したもの）だけ。

### 2. EDINET API の使い方

- ベース URL `https://api.edinet-fsa.go.jp/api/v2`（2026-08-29 のホストの移設後のもの。実装時に仕様書 Version 2（2026-06-03 更新）で確かめ、定数1つに置く）。
- **キーの送り方と漏えいの防止（R1）**: キーは仕様書のとおり送る。公開の事例ではクエリのパラメータ `?Subscription-Key=` なので、その前提で次を守る（仕様書でヘッダーでも送れると確かめられたら、ヘッダーを使ってよい。その場合も次は守る）。
  1. **要求の URL は秘密として扱う**。URL・要求のオブジェクト・fetch の例外（`TypeError` とその `cause`。`cause` に URL が含まれうる）を、`console.*`・例外のメッセージ・`error_message`・`details`・テストのスナップショットに出さない。接続の失敗は「接続できない」「タイムアウト」の分類だけを記録する（例外の `message` も記録しない）。
  2. **リダイレクトを追わない**。fetch は `redirect: "manual"` で呼び、3xx（`opaqueredirect` を含む）は「EDINET から予期しない応答がありました（リダイレクト）」でその要求を失敗にする（実行は打ち切る。旧ホストへの要求や移設のときに、キー付きの URL を別のホストへ送らない）。
  3. テスト（C6-6・C7-4）で、401・429・接続の失敗（`cause` に URL を持つ `TypeError`）・3xx のそれぞれについて、差し替えたキーの文字列が `error_message`・`details`・`console` の出力に無いことを確かめる。
- 書類一覧 API: `GET /documents.json?date=YYYY-MM-DD&type=2`。日付（提出日）ごとに、その日に提出された書類のメタデータを返す。
- 書類取得 API: `GET /documents/{docID}?type=1`（提出本文書と監査報告書、XBRL の ZIP）。ZIP の中の `XBRL/PublicDoc/` にある本文のインスタンス（`*.xbrl`）を読む。
- **応答の分類**（`edinet/http.ts` の1か所で行う。J-Quants の `requestJQuants()` と同じ考え方）。EDINET は **HTTP 200 のまま本文でエラーを返す**ことがある（キーの無効で `{"StatusCode":401,"message":"Access denied due to invalid subscription key..."}`）。そのため、HTTP のステータスだけでなく、本文の「実効のステータス」で分類する（R2）。
  - 実効のステータスの求め方: HTTP のステータスが 200 以外ならそれ。200 で本文が JSON なら、本文の `StatusCode`（数値）、または `metadata.status`（文字列）が `"200"` 以外ならその値。書類取得 API で本文が JSON なら、それは必ずエラー（ZIP ではない）なので、本文の値を使い、読めなければ「形式の違い」。
  - 書類取得の成功は、**本文の先頭が ZIP のシグネチャ `PK\x03\x04`** のときだけ（`Content-Type` だけで判定しない）。
  | 実効の応答 | 一覧 API | 書類取得 API |
  |---|---|---|
  | 200 の JSON で `metadata.status` が `"200"`、必須の項目がある | 成功 | — |
  | 200 で本文が ZIP のシグネチャで始まる | — | 成功 |
  | 401（HTTP、または本文の `StatusCode`／`metadata.status`）、403 でキーの無効・欠如を示す本文 | 実行を打ち切る。「EDINET の API キーが無効です（HTTP 401）」 | 同左（書類ごとの失敗にしない） |
  | 429、503 | 実行を打ち切る。「EDINET の呼び出しが制限されました（HTTP 429）。しばらくしてから再実行してください」 | 同左 |
  | 3xx | 実行を打ち切る（R1 の2） | 同左 |
  | 404（HTTP または本文） | その日を失敗（次の実行で再試行） | その書類だけ失敗（「書類を取得できない」）。取得済みにしない |
  | 400、500 など上以外（HTTP または本文） | その日を失敗 | その書類だけ失敗 |
  | 接続できない・タイムアウト（30 秒） | その日を失敗 | その書類だけ失敗 |
  | 200 だが HTML（`text/html`）・JSON として読めない・必須の項目が無い | 形式の違い。「EDINET の応答の形式が想定と異なります」でその日を失敗。**成功とも0件とも扱わない** | 形式の違い。ZIP のシグネチャでなく JSON でもない本文はその書類の失敗（取得済みにしない） |
  - 一覧で `metadata.resultset.count` と `results` の件数が合わないときも形式の違いとする（仕様書で項目を確かめる）。
- **要求の間隔**: 前の要求の開始から 1,000ms 以上（EDINET は上限を公開していないため控えめにする。定数1つで変えられる）。新しい要求はルートの開始から 210 秒まで（`REQUEST_BUDGET_MS`。Sprint 4・5 と同じ）。超えたら `partial`。
- **連続した失敗**: 日付・書類の取得の失敗が5回続いたら打ち切る（Sprint 5 と同じ）。

### 3. 対象の書類と保存の範囲

- 書類一覧から保存するのは、`ordinanceCode = "010"`（企業内容等の開示に関する内閣府令）で、`docTypeCode` が次のどれかの書類のメタデータ。`secCode` の要否は種類で分ける（R7）:
  - 120／130（有報・訂正有報）: `secCode` がある書類だけ（銘柄と対応づかない有報は使い道が無い）。
  - 030／040（届出書・訂正届出書）: **`secCode` が無くても `edinet_code` 付きで保存する**（上場前の届出書は証券コードが空のことがありうる。Sprint 9 は、同じ `edinet_code` の有報の `sec_code` などで銘柄に結び付ける）。取得済みの日の一覧を Sprint 9 で取り直さずに済むようにするため。
  - どの種類も `edinet_code` は必ず保存する。
  | docTypeCode | 種類 | このスプリントでの処理 |
  |---|---|---|
  | `120` | 有価証券報告書 | 大株主・役員を抽出する |
  | `130` | 訂正有価証券報告書 | 大株主・役員を抽出する（第4項） |
  | `030` | 有価証券届出書 | メタデータだけ保存（本文は取得しない。Sprint 9 で使う） |
  | `040` | 訂正有価証券届出書 | 同上 |
  - 届出書のメタデータを今保存するのは、Sprint 9 が同じ日付の書類一覧を取り直さずに済むようにするため（本文の取得・画面での表示はしない。先回りの機能ではなく、一覧の取得を1回で済ませるための保存）。
  - 有報の様式（`formCode`）は仕様書で確かめ、内国会社の有報（第三号様式）とその訂正に限る。外国会社・ファンドの書類は保存しない。
- `secCode`（5文字）が J-Quants の銘柄コード（5文字）と一致する。保存は `sec_code` の文字列のまま（銘柄マスタへの外部キーにはしない。一覧を取った時点で銘柄マスタに無い新規上場の銘柄も、後から銘柄マスタに入れば対応づく）。読み出し・本文の取得は、銘柄マスタにある銘柄だけを対象にする。
- **取り下げ・不開示（R5）**: 仕様書で次を確かめ、確かめた内容を self-review と CLAUDE.md に書く。
  - 取り下げが、取下日の一覧に同じ `docID` の行として出るか、元の提出日の一覧の行が書き換わるか。
  - `withdrawalStatus` の値の意味（公開の資料では「0: 通常、1: 取下書、2: 取り下げられた書類」とされる。実装時に確かめる）。
  - 取り下げ・不開示の行で `docTypeCode`・`secCode`・`ordinanceCode` などが null になるか。
  - `disclosureStatus`（不開示など）の値の意味。

  そのうえで次の規則にする。
  | 一覧の行 | 扱い |
  |---|---|
  | 取り下げを示す行（取り下げられた書類。値は仕様書で確かめる） | 絞り込みの条件（種類・`secCode`・`ordinanceCode`）を満たさなくても、**既にある `doc_id` の行を `withdrawn = true` に更新する**（無い `doc_id` は保存しない） |
  | 取下書そのものの行（`withdrawalStatus` が取下書を示す） | 保存しない（書類の本文ではない）。`parentDocID` などで取り下げの対象が分かる場合は、その `doc_id` の行を `withdrawn = true` にする |
  | 不開示を示す行（`disclosureStatus` が不開示など） | 既にある行を `withheld = true` に更新（無ければ条件を満たすときだけ保存）。不開示の書類は「使う書類」から外し、本文を取得しない（毎回の失敗で `partial` が続くのを避ける） |
  | 通常の行 | 条件を満たせば upsert |
  - **一度 true にした `withdrawn`・`withheld` は、古い日付の一覧を取り直しても false に戻さない**（取り下げの解除は EDINET に無い前提。仕様書で違えば仕様書どおりの値で上書きし、そう書く）。
  - 直近7日の一覧を毎回取り直すことで、取下日が直近の取り下げを反映する。取り下げが取下日の一覧に出ない（元の日付の行だけが書き換わる）と確かめた場合は、「取り下げの反映は、元の提出日が直近7日の範囲にあるものに限られる」ことを CLAUDE.md の既知の制限に書く（Sprint 12 で扱う）。
  - C4-4 で取り下げた書類は、詳細の siblings に「取り下げ」のラベル付きで出す（使う書類には選ばない）。
- **一覧を取る期間**: 実行日（JST）の 450 日前〜実行日（毎年1回提出される有報を、決算期の変更や提出の遅れを含めて1通以上拾える長さ）。定数1つで決め、Sprint 9 で届出書のために延ばせるようにする。
- **一覧を取る順番**: 直近7日（取得済みでも毎回取り直す）→ 未取得の日（新しい順）。日付ごとに、全件を読み終えてから、書類のメタデータの保存と「取得済み」の記録を1トランザクションで行う（Sprint 5 の `financial_fetched_dates` と同じ）。打ち切られても次の実行で続きから再開する。土日・祝日も要求する（EDINET の取引カレンダーは無く、J-Quants に依存させない）。

### 4. 「直近の有報」の選び方（AC8.4）

**(a) 対象の事業年度**
- 銘柄ごとに、取り下げ・不開示でない有報（120）・訂正有報（130）のうち、**事業年度の終了日が最も新しい**ものを対象の事業年度とする。
- 書類の事業年度の終了日 = 一覧の `periodEnd`。訂正有報で無ければ、元の書類（`parentDocID`）の値（元の書類が保存済みのとき）。
- **事業年度を決められない書類（R4）**（`periodEnd` が無く、元の書類も保存されていない。例: 元の有報が一覧の期間の外にある古い訂正）は、対象の事業年度の選択に**使わない**。SQL は `period_end is not null` で絞る（`order by … desc` で NULL が先頭に来ることを避ける。`nulls last` だけに頼らない）。そのような書類は、本文も取得しない。
- 銘柄に、事業年度を決められる書類が1通も無い（事業年度を決められない訂正だけがある）ときは「有価証券報告書が未取得です」と同じ扱いにする。

**(b) 区画ごとの書類（R3）**
- 対象の事業年度の書類（元の有報とその訂正。取り下げ・不開示を除く）を、**提出日時の新しい順**に並べる。これを「候補の列」と呼ぶ。
- **大株主・役員のそれぞれ（区画ごと）に**、候補の列を新しい順に見て、次の規則で使う書類を決める。
  - 処理済みで、その区画が `ok` または `invalid_values` の書類があれば、その最初の書類を使う。`invalid_values` は区画はあるが読めない状態なので、古い書類には戻さず、その理由を表示する。
  - その区画が `section_not_found`・`no_xbrl` の書類は飛ばして、次に古い書類を見る。訂正報告書は訂正箇所だけを記載することが多いため、その区画が無い訂正の場合は、元の有報（または前の訂正）の記載を使う。
  - 未処理の書類に当たったら、そこで止める（「取り込み待ち」）。未処理の書類より古い書類の値を、新しい書類を確かめる前に表示しない。
  - 候補をすべて見ても `section_not_found`・`no_xbrl` しか無ければ、最も新しい書類の理由を表示する（抽出できなかった）。
- **画面には必ず、区画ごとに使った書類を示す**。区画の書類が最新の提出分でないときは、「訂正有価証券報告書 S100B（2025-07-10 提出）には『大株主の状況』の記載が無いため、有価証券報告書 S100A（2025-06-26 提出）の記載を表示しています」と示す（黙って戻さない）。
- 出典の書類の表示（第4章）は、最新の提出分（候補の列の先頭）を「最新の提出分」として示す。区画ごとの書類は、その区画の見出しの下に書く。

**(c) 本文を取得する書類と処理済みの管理**
- 本文を取得するのは、(b) の規則で**次に確かめる必要がある書類だけ**。
  - まず、候補の列の先頭（最新の提出分）を取得する。
  - その書類で、ある区画が `section_not_found`・`no_xbrl` になったら、次に古い候補（元の有報など）を、次の処理の対象に加える（同じ実行の中で続けて処理してよい）。
  - 古い事業年度の有報、両方の区画がすでに決まった後の古い候補は取得しない。
- 新しい書類（訂正を含む）が一覧に現れたら、次の実行でその書類を取得し、表示は (b) の規則で切り替わる。
- 処理済み = 本文の取得に成功し、抽出の結果（区画ごとの成功、または理由付きの失敗）を保存したこと。処理済みの書類は取り直さない（AC8.6）。
- 取得の失敗（404・500・接続できない・ZIP でない）は処理済みにせず、次の実行で再試行する。何度も失敗する書類の書類ID は、`details.failedDocuments` に残す（上限 50 件。Sprint 12 で扱う）。
- 抽出の失敗（書類の形が想定と違う）は、理由とともに処理済みにする（毎日取り直さない）。抽出の規則を直したときに取り直すには、その書類の抽出の結果の行を消す（CLAUDE.md に書く）。
- 詳細画面では、同じ事業年度の書類が複数あるとき「同じ事業年度の書類が2件あります（訂正を含む）。最新の提出分（S100XXXX、2025-07-10 提出）を使っています」と示し、ほかの書類の書類ID・提出日も並べる。取り下げた書類には「取り下げ」のラベルを付ける。

### 5. 何を抽出するか（大株主・役員）

- 読むのは本文のインスタンス（`*.xbrl`）の事実（要素・コンテキスト・単位・値）。汎用の読み取り（`edinet/xbrl.ts`: 事実とコンテキストの一覧を返す）と、有報の項目の抽出（`edinet/annual-report.ts`）を分ける（Sprint 9 は前者を使い回し、「主要な経営指標等の推移」の抽出を足す）。
- **読むコンテキストを限定する（R8）**: 要素名だけで事実を集めない。区画ごとに、読むコンテキスト（期間の種類・軸とメンバー）を決め、それ以外の事実は捨てる。捨てた事実の数は `details` に残す（黙って混ぜない）。軸・メンバーの名前は第2章の1の資料・実データで確かめ、CLAUDE.md に書く。
- **大株主の状況**: `jpcrp_cor` の要素 `NameMajorShareholders`（氏名・名称）・`AddressMajorShareholders`（住所）・`NumberOfSharesHeld`（所有株式数、単位 `shares`）・`ShareholdingRatio`（割合）。評価者が公開の iXBRL で実在を確かめた（コンテキスト例 `CurrentYearInstant_No7MajorShareholdersMember`）。
  - 読むのは、期間が**当事業年度末の時点（`CurrentYearInstant`）**で、大株主の順位の軸のメンバー（`No1MajorShareholdersMember`〜）**だけ**を持つコンテキスト。1行 = 1メンバー。メンバーの無い合計の行（「計」）は含めない。
  - **議決権の割合の表を併記する書類**（種類株式のある会社など）: 所有株式数の割合の表だけを保存する（仕様の「発行済株式（自己株式を除く）の総数に対する所有株式数の割合」）。議決権の表は、別の要素か、別の軸・メンバーで区別される（実装時に実データ・タクソノミで確かめる）。そのため、限定したコンテキストと要素以外は読まない。議決権の表だけしか無い書類は `section_not_found`（理由「所有株式数の割合による大株主の表が見つかりません」）とする。
  - 順位 = メンバーの番号（書類の記載順）。
  - **持株比率の変換（R6）**: 浮動小数点を使わない。XBRL の値の文字列（例 `0.3210`、`0.0057`）の小数点を2桁右にずらして百分率の十進の文字列（`32.10`、`0.57`）にし、DB に文字列のまま numeric で渡す（`number` に変換しない）。記載の精度（`decimals`。例 `decimals="4"` の比率 → 百分率で小数点以下2桁、`decimals="5"` → 3桁）も保存する（`ratio_decimals`。百分率の小数点以下の桁数）。`decimals` が無い・`INF` のときは、値の文字列の桁から求める。値が十進の数として読めなければ `invalid_values`。
  - **所有株式数**: 整数の文字列のまま numeric で保存する（株）。表示は株の単位で、3桁区切り（例 `3,210,000`）。千株への換算はしない（1,000 で割り切れない記載があるため。規則を1つにする）。
  - 氏名・名称は書類の記載のまま保存する（全角空白・改行は、前後の空白を除くだけ。正規化・照合は Sprint 10）。
  - 信託口（例「日本マスタートラスト信託銀行株式会社（信託口）」）・法人・個人・外国の名義（例「THE BANK OF NEW YORK MELLON 140044」）を区別せず、同じ形で保存する（区分の判定は Sprint 10）。
- **役員の状況**: 役員の氏名と役職名の要素（候補 `NameInformationAboutDirectorsAndCorporateAuditors`・`OfficialTitleOrPositionInformationAboutDirectorsAndCorporateAuditors`。評価者も確かめられていないので、実データ・タクソノミで必ず確かめる）。役員ごとのメンバー（提出者の独自のメンバー）ごとに1行。
  - **役員の表が2つある書類（R8）**: 株主総会の前に提出した有報には、「提出日現在の役員」の表と、「定時株主総会の議案が承認された後の役員」の表の2つがありうる。2つは異なるコンテキスト（期間・軸）で区別される（実装時に確かめる）。**2つを混ぜない**。
    - 保存するのは「提出日現在の役員」（`FilingDateInstant` の表）とする。理由: 仕様の「直近の有価証券報告書の役員の状況」は書類の記載時点の役員で、総会後の役員は予定であるため。
    - 総会後の表もある書類では、その旨を抽出の結果に記録する（`officers_basis = 'filing_date'`、`officers_has_post_agm_table = true`）。詳細画面に「この有報には定時株主総会後の役員の予定も記載されています（表示は提出日現在の役員）」と注記する。
    - Sprint 10 の社長の特定でも、提出日現在の表を使う。変える場合は Sprint 10 の契約で決め、このスプリントで総会後の表の行も保存するかをそのとき決める。
  - **順番（R8）**: 役員の記載順は、**提出者別タクソノミの表示リンク（ZIP の中の `*_pre.xml`）での役員のメンバーの順**とする。表示リンクで順が決まらない場合は、ZIP の中のインライン XBRL（`*.htm`）の文書での事実の出現順を使う。インスタンス（`*.xbrl`）での出現順は根拠にしない。どちらの根拠を使ったかを `officers_order_source` に記録する。テストでは、インスタンスでの並びをわざと崩したフィクスチャで、表示リンクの順になることを確かめる。
  - 役職名は記載のまま（改行を含む）保存する。兼務の表記（例「代表取締役社長\n社長執行役員」「取締役（管理本部長兼経理部長）」「代表取締役会長 兼 CEO」）を1つの文字列として保つ。
  - 監査役・監査等委員・執行役も、書類の役員の状況の表にあれば含める（除外しない）。
  - 同じ役員のメンバーに氏名・役職名が2つ以上ある（コンテキストの限定の後でも重複する）ときは `invalid_values`（`duplicate_officer`）。
- **抽出の結果**（大株主・役員それぞれ）:
  | 結果 | 条件 | 画面の理由の文言 |
  |---|---|---|
  | `ok` | 1行以上あり、各行の必須の項目（大株主: 氏名・名称と持株比率、役員: 氏名と役職名）がそろう | — |
  | `no_xbrl` | 書類に XBRL が無い（`xbrlFlag` = 0、または ZIP に本文のインスタンスが無い） | 「書類に XBRL（機械で読めるデータ）が含まれていません」 |
  | `section_not_found` | その区画の要素が1つも無い | 「書類から『大株主の状況』の項目を見つけられませんでした」／「…『役員の状況』…」 |
  | `invalid_values` | 要素はあるが、必須の項目の欠け・数値として読めない比率・順位の重複がある | 「『大株主の状況』の記載を読み取れませんでした（持株比率が数値でない行があります）」など、原因の種類を示す |
  - 一部の行だけが壊れているとき、正しい行だけを保存して `ok` にしない（`invalid_values` にする。行を黙って落とさない）。
  - XBRL の詳細タグが無く、テキストブロック（表の HTML）だけにある書類の読み取りは**任意**（実装した場合はテストに含める。実装しない場合は `section_not_found` として理由を表示）。
- 金額・比率を算出しない（オーナー系の合計・判定は Sprint 10）。

### 6. 処理の順番・件数・実行履歴（AC8.6）

- target は既存の `edinet_reports`（表示名「有報」。`ingestion_runs` の check 制約にすでにある）。`runner.ts` の `SUPPORTED_TARGETS`・`RUNNERS` に加える。
- 1回の実行の順番: キーの確認 → 銘柄マスタが0件なら失敗（「銘柄マスタが未取り込みのため、有報を取り込めません。先に銘柄マスタを取り込んでください」）→ 書類一覧（第3項の順）→ 本文を取得する書類（第4項の (c)。提出日時の新しい順。訂正に区画が無く古い候補が加わったら、それも続けて処理する）の取得と抽出。
  - 書類一覧を**期限・打ち切り（キーの無効・429・3xx・連続の失敗）で取り終えていない**ときは、本文の取得に進まない（古い有報を無駄に取得しないため）。
  - 期限の前に、全部の日を試し終えたが一部の日が失敗（500 など）で残っているときは、本文の取得に進む（その日は次の実行で再試行する）。
- **処理件数（`processed_count`）= この実行で本文を取得して抽出の結果を保存した書類の数**（区画の不足で古い候補を加えて処理した分も含む）。一覧の取得は件数に入れない。処理済みの書類しか無ければ 0（AC8.6 は「2回目の実行の処理件数が 0、または新しく提出された書類の数だけ」で確かめる）。保存は書類ごとに行い、そのたびに件数を足す（打ち切られても、保存した分は残る）。
- 結果: 全部を処理 → `succeeded`。期限・連続の失敗・書類ごとの失敗が残る → `partial`（「時間内に処理しきれなかったため、残り 1,234 件の書類は次回の取り込みで処理します」「N 件の書類を取得できませんでした。次回の取り込みで再試行します」）。キーの無効・429・形式の違いで1件も進めない → `failed`。
- `ingestion_runs.details`（画面の要約と評価者の確認に使う）: `windowStart`・`windowEnd`、`listDatesInWindow`・`listDatesFetchedBefore`・`listDatesFetched`・`listDatesFailed`・`listDatesRemaining`、`documentsListed`（保存した書類のメタデータの件数。種類ごと）、`documentsTargeted`（使う書類のうち未処理）、`documentsProcessed`、`extraction`（大株主・役員それぞれの結果ごとの件数）、`documentsFailed`、`failedDocuments`（取得に失敗した書類IDと分類。上限 50 件）、`fallbackDocuments`（区画の不足で古い候補を加えた件数）、`documentsRemaining`、`withdrawnUpdated`・`withheldUpdated`、`discardedFacts`（コンテキストの限定で捨てた事実の数）、`apiCalls`、`stoppedReason`、`lastFailedStatus`。書類IDは公開の情報なので残してよいが、URL は残さない。
- 失敗の文言は `errors.ts` の決まった日本語だけ（キーの値・書類の本文・応答の本文を含めない）。

### 7. 定期実行・手動の実行

- 定期実行は新しいルート `GET /api/cron/edinet`（`handleCronRequest()` を使う。`maxDuration = 300`、HEAD は 405）。`vercel.json` に `{ "path": "/api/cron/edinet", "schedule": "0 15 * * *" }`（UTC。毎日 0:00 JST）。EDINET の書類はおおむね当日の 17:15 までに提出される。Hobby の1時間のずれを見込んでも、22:00 JST の財務の実行（最大 23:05 ごろまで）と重ならない。`schedule.ts` に `EDINET_CRON_JOB`（表示「毎日 0:00（日本時間）」「有報（EDINET）」）を加え、`schedule.test.ts`・`runner.test.ts`（全対象がちょうど1回ずつ定期実行に入る）を通す。
  - 0:00 JST を過ぎてから動くので、実行日（JST）は前日の書類の提出日の翌日になる。一覧の期間（実行日の 450 日前〜実行日）と直近7日の取り直しには前日が含まれる。このことを CLAUDE.md に書く。

- **初回の所要**: 一覧 450 日 ≒ 3回の実行。有報 約3,900 通は、1秒の間隔と ZIP（1〜数 MB）の受信・解凍を考えると1回で 100〜150 通程度で、約 26〜39 回かかる。毎日1回の定期実行だけでは1か月以上かかる。
  - 取り込み状況の画面には、固定の数字ではなく**直前の有報の実行の実績**を出す（「取り込み待ちの書類 N 件（直前の取り込みでは M 件を処理）」。実績が無ければ件数だけ）。手動の「今すぐ取り込み」を続けて押せば早く埋まることが分かるようにする。

  - この2つの見積もりを CLAUDE.md に書く。
- 手動: 取り込み状況の「今すぐ取り込み」の対象に「有報（EDINET）」（説明「直近の有価証券報告書の大株主・役員（書類一覧の取得と、未処理の書類の取得）」）を加える。`POST /api/ingestion/runs` の `target: "edinet_reports"` を受け付ける。

### 9. Sprint 7 評価の B1 の修正（スクリーニングの行のクリックの取りこぼし）

- 原因: `screening-view.tsx` の遅延した `router.replace('/screening?…')` が、行・リンクのクリックで始まった `router.push('/stocks/…')` の後に実行され、遷移を上書きする。
- 直し方（振る舞いの約束）:
  1. 詳細へ移る操作（行のクリック、コード・社名のリンクのクリック、リンクの上での Enter）を始めるとき、待っている URL の書き換え（遅延中の replace）を**取り消す**。遷移の後に `/screening` への replace が走らない（詳細に移った後に URL が戻らない）。
     - **すでに発行された書き換えも同じ（R9）**: 入力欄のフォーカスが外れた時点で、書き換えは遅延 0 で確定する（`threshold-field.tsx` の `commitNow()`）。マウスでは、フォーカスが外れるのはクリックより前の `mousedown` の時点である。そのため、クリックの処理の時点で `router.replace` がすでに発行され、サーバーの応答を待っている（`isPending`）ことがある。この場合も、詳細への遷移を後から上書きさせない。後に始めた遷移が勝つようにするか、詳細への遷移を始めた後に届いた `/screening` の書き換えの完了で URL を戻さない。方法はジェネレーターが決める。
     - どちらの場合も、クリックした時点で表示中の結果の条件（3）の詳細 URL に移り、1,500ms 後もその URL のままであることを約束とする。
  2. 取り消した書き換えの条件（最後に入力した条件）は捨てずに、**遷移の前に今の履歴の項目（スクリーニングの URL）に反映する**。これで、詳細からブラウザの「戻る」・パンくず・ナビゲーションで戻ったとき、最後に入力した値（例 14）で表示される。
  3. 詳細へのリンクの条件は、Sprint 7 のとおり**表示中の結果の条件**（サーバーが判定に使った条件）のまま（例 15）。詳細の判定と、クリックしたときに見えていた印・件数が一致する。
     - ただし、パンくず・「条件を変える」・ナビゲーションの戻り先は詳細の URL のクエリから作る（Sprint 7）ので、2 の「戻る」とは戻り先の条件が異なりうる。**この違いは受け入れる**（パンくずなどは「詳細の判定に使った条件のスクリーニング」、ブラウザの「戻る」は「直前に見ていたスクリーニング」）。契約レビュー（1回目）で評価者も受け入れた。
  4. ⌘／Ctrl／中クリックで新しいタブに開くとき（元のタブは移らない）は、待っている書き換えをそのまま続ける（元のタブの URL は通常どおり 14 になる）。

### 取り込み状況の画面の変更

- 「今すぐ取り込み」の対象に「有報（EDINET）」。

  - **有報を取得できた銘柄**（AC8.2。`data-testid="annual-report-stock-count"`）: 銘柄マスタの銘柄のうち、使う書類の本文を処理済みの銘柄数 / 銘柄マスタの銘柄数（例「1,234 / 3,912 銘柄」）。
  - 内訳: 大株主・役員とも抽出できた銘柄数、どちらかを抽出できなかった銘柄数、取り込み待ちの書類数（本文を取得する対象のうち未処理）と、直前の有報の実行で処理した書類数（第2章の7）。

  - 集計は DB 関数1回（ユーザーのセッション。security invoker）。データが0件なら「まだ有報が取り込まれていません」と、キーが未設定なら「EDINET の API キーが設定されていません（取り込みを実行すると失敗として記録されます）」。
- 実行履歴の対象の表示は既存の「有報」。結果の文言（`result-message.ts`）に有報の要約（「書類 12 件を処理（大株主・役員の抽出 11 件、抽出できず 1 件）」など）を加える。

     - `edinet_documents` には対象の書類だけが入る。`secCode` の無い届出書は `edinet_code` 付きで入り、`secCode` の無い有報は入らない。
     - 届出書は本文の要求が無い。取り下げの行で、既にある `doc_id` の行が `withdrawn = true` になる。
     - 大株主・役員が保存される。
2. **2回目**（新しい書類なし）: 書類取得 API への要求が0回、`processed_count = 0`、`succeeded`。一覧は直近7日だけを取り直す（未取得の日が無いため）。取り直した一覧に取り下げ前の形の行が出ても、`withdrawn` は true のまま（false に戻さない）。
3. **3回目**（直近の日に訂正有報が1通増える）: 書類取得 API への要求はその1通だけ（その訂正に両方の区画がある場合）、`processed_count = 1`、詳細の読み出しが訂正に切り替わる。
4. **期限で止まる**: 差し替えた時計の期限で一覧の途中で止まると `partial` になり、残りの日数が `details` と文言に出て、本文の取得は始めない。次の実行で続きの日から再開する。全部の日を試し終えて一部の日だけが失敗した場合は、本文の取得に進む。本文の途中で止まったときも、保存済みの書類は取り直さない。
5. **書類の取得の失敗**（500・200 の本文 404・ZIP でない本文・接続できない）: その書類を処理済みにせず `partial` にし、`details.failedDocuments` に書類ID と分類を残す。次の実行で再試行する。抽出の失敗（形の違い）は理由付きで処理済みになり、次の実行で取り直さない。
6. **打ち切り**: 401・**200 の本文 `StatusCode` 401**（書類取得でも）・429・3xx で打ち切る。一覧を1日も取れていなければ `failed`、取れていれば `partial`。キーの無効が書類ごとの失敗として5回数えられることは無い。
   - テストでは、差し替えたキーの文字列が `error_message`・`details`・`console` の出力に無いことを確かめる。確かめるのは、401、429、接続の失敗（`cause` に URL を持つ `TypeError`）、3xx の場合。
   - fetch が `redirect: "manual"` で呼ばれていることも確かめる。
7. 銘柄マスタが0件なら外部 API を呼ばずに失敗（第2章の6の文言）。
