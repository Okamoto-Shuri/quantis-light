# Sprint 08 契約レビュー（1回目）

## 結論: 修正依頼

F8 の AC8.1〜AC8.7 は、すべて完了条件（C1〜C7）に対応している。投入例の期待値（第5章の表と、取り込み状況の 4/6・3・1・1）も、投入 SQL と突き合わせて正しいことを確かめた。スコープの切り方（届出書はメタデータだけ、区分・判定は Sprint 10）も妥当。B1 の修正方針も受け入れる。

ただし、公開されている EDINET API の挙動と照らすと、契約のままでは実 API で壊れる箇所がある。キーの漏えい、失敗が成功に見える応答、訂正報告書で大株主のデータが消える、といった問題である。Sprint 9 の土台としても取りこぼしがある。この環境ではキーが無く、実 API で確かめられない。だからこそ、次の点は契約の段階で決めておく必要がある。

調べた資料: EDINET API関連資料のページ（仕様書 Version 2 は 2026-06-03 更新）、同仕様書の PDF（この環境では本文を抽出できなかった）、EDINET API v2 を使う公開リポジトリの不具合報告（下の R1・R2 の根拠）、EDINET の閲覧 URL の検索結果。

- https://disclosure2dl.edinet-fsa.go.jp/guide/static/disclosure/WZEK0110.html
- https://disclosure2dl.edinet-fsa.go.jp/guide/static/disclosure/download/ESE140206.pdf

## 修正必須

### R1: キーはクエリのパラメータ。URL を漏らさない・リダイレクトを追わないことを契約に書く
- 第2章の2は「キーは仕様書のとおり `Subscription-Key` で送る」としか書いておらず、ヘッダーかクエリかが決まっていない。公開の事例では、v2 のキーはクエリのパラメータ（`?Subscription-Key=`）で送る。そうすると、URL そのものが秘密になる。
- 契約に次を加えること。
  1. 送り方を仕様書で確かめて明記する。クエリなら、要求の URL を、ログ・例外・`error_message`・`details`・テストのスナップショットに出さない。fetch の `TypeError` やその `cause` をそのまま記録しない。
  2. `redirect: "manual"`（またはそれに相当するもの）を使い、3xx は追わずに失敗として扱う。2026-08-29 のホストの移設では、旧ホストが 301→302→HTML を返した。リダイレクトを追うと、キー付きの URL が別のホストに送られる。
  3. C6-6・C7-4 のテストに、接続エラーと 3xx の場合も加える。どちらでも、キーの文字列が `error_message`・`details` に無いことを確かめる。

### R2: HTTP 200 のまま本文でエラーを返す応答を分類に入れる
- キーが無効なとき、EDINET は **HTTP 200** で本文に `{"StatusCode":401,"message":"Access denied due to invalid subscription key..."}` を返すことが報告されている。第2章の2の表には「`metadata.status`」しか無く、本文の `StatusCode` を見ることが書かれていない。
- 書類取得 API については、表の「`Content-Type` が JSON（ZIP でない）→ その書類だけ失敗」のままだと、キーが無効でも「書類ごとの失敗」になる。その結果、5回失敗してから打ち切られ、文言も誤る。
- 次のように直すこと。
  - 一覧・書類取得の両方で、JSON の本文の `StatusCode`（と `metadata.status`）を読み、401 ならキーの無効として打ち切り、404 なら書類だけの失敗、とする。
  - 200 で HTML が返ったとき、一覧は「形式の違い」とし、書類は ZIP のシグネチャ（`PK\x03\x04`）を確かめる。成功とも0件とも扱わない。
  - C7-4 のケースに「200＋本文 401」「200＋本文 404（書類取得）」「200＋text/html」を加える。

### R3: 訂正有報に大株主・役員の記載が無いとき、1年分のデータを失わない
- 第2章の4は「訂正有報に XBRL が無い、または抽出に失敗した場合: その訂正を使い、抽出できなかった理由を表示（古い書類に戻さない）」としている。
- 訂正報告書の多くは、訂正箇所だけを記載した書類である（誤字の訂正、監査報告書の差し替えなど）。この場合、大株主・役員の区画は訂正報告書の本文に無い。その結果、訂正を1通出しただけの会社は、次の有報までの1年間「抽出できませんでした」になり、Sprint 10 の条件④が「判定不能」になる。訂正報告書は珍しくないので、実データでは大きな欠落になる。
- 次のように直すこと。
  - **区画ごと**（大株主・役員それぞれ）に、同じ事業年度の書類を提出日時の新しい順に見て、その区画の記載がある最初の書類の値を使う。訂正の本文にその区画が無い（`section_not_found`・`no_xbrl`）ときは、元の有報（または前の訂正）の値を使う。
  - その場合は画面で必ず示す（例「訂正報告書 S100B には『大株主の状況』の記載が無いため、有価証券報告書 S100A の記載を表示しています」）。黙って戻さない。
  - `invalid_values`（区画はあるが壊れている）のときは戻さない。今の方針のまま。
  - このため、訂正の本文を処理した結果によっては、元の書類の本文も取得の対象になる。処理済みの管理と件数の定義（第2章の6）も、これに合わせて書き直す。
  - 第5章に、訂正に大株主の区画が無く元の書類に戻る銘柄（例 9W007）を加え、C4 と `pnpm test:db`（C4-5）で確かめる。

### R4: 事業年度が分からない訂正を「最新の事業年度」にしない（NULL の並び）
- 訂正有報の `periodEnd` が一覧に無いときは「元の書類（`parentDocID`）の値を使う」とある。しかし、元の書類が一覧の期間（450 日）の外にあると、事業年度は NULL のままになる。
- Postgres の `order by period_end desc` では NULL が**先頭**に来る。何年も前の有報の訂正が、今年の有報より優先されるおそれがある。
- 事業年度を決められない書類は選ばない（または最後に回す）と明記すること。C4-5 のテストに「元の書類が期間外の訂正」を加えること。

### R5: 取り下げの反映の仕組みを仕様書で確かめ、契約に書く
- 契約は、直近7日の一覧を取り直して取り下げを反映するとしている。しかし、この方法が成り立つかは、取り下げがどの日付の一覧に、どの形で出るかによる。
  - 取下日の一覧に同じ docID で出るのか。
  - `withdrawalStatus` の「1」「2」の意味。
  - 取り下げた書類では `docTypeCode`・`secCode` などが null になるのか。
- 取り下げた書類の項目が null になる場合、第2章の3の絞り込み（`ordinanceCode`・`secCode`・`docTypeCode`）で行が捨てられる。そうなると、取り下げが既存の行に反映されない。
- 次のように直すこと。
  - 取り下げの行は、絞り込みの条件を満たさなくても、**既にある `doc_id` の行を更新する**。
  - 古い日付の一覧を取り直しても、`withdrawn = true` を false に戻さない（または、仕様書どおりの値で上書きする）。
  - 不開示（`disclosureStatus`）の書類の扱いも同じ表に加える。取得が毎回失敗して、ずっと `partial` になるのを避ける。
  - C6-1 の一覧に「取下日の一覧に出る取り下げの行」を含める。

### R6: 持株比率は十進の文字列で変換する（浮動小数点を使わない）。表示の桁の規則を1つに決める
- JS の浮動小数点では `0.0057*100` が `0.5700000000000001` になる（実際に確かめた）。この値が保存されると、Sprint 10 のオーナー系の合計と閾値 20% の比較の境界がずれる。
  - XBRL の値の文字列の小数点をずらして百分率にするか、numeric の演算で変換すること。
  - `0.0057`・`0.0129` のような値で完全に一致することを C7-2 で確かめること。
- 表示の規則が矛盾している。第4章は「小数点以下2桁（例 32.10%）」、第7章は「保存値の桁をそのまま（四捨五入しない）」としている。有報の中には小数点以下3桁で記載する会社もある。次の規則を採ることを推奨する。
  - 保存値の桁（記載の精度。`decimals` から分かる）を保つ。
  - 表示は「最低2桁。記載がそれより細かければその桁まで。丸めない」。
  - C3-2 に3桁の例を1行加える。
- 所有株式数の「千株」表示も、株数が1,000で割り切れないとき（`decimals` が 0 の会社）の規則を決めること。株のまま表示するのでもよい。

### R7: Sprint 9 の土台: `secCode` の無い届出書のメタデータも保存する
- 一覧の取得済みの日は二度と取り直さない。それなのに、第2章の3は `secCode` の無い書類を捨てる。
- 上場前に提出される有価証券届出書では、`secCode` が空の場合がありうる（EDINET の書類一覧では、証券コードは提出者の登録情報に依存する）。そうだった場合、Sprint 9 は取得済みの期間の一覧をすべて取り直す必要がある。これは「一覧の取得を1回で済ませるため」という第2章の3の目的に反する。
- 次のどちらかにすること。
  - 030／040 は `secCode` が無くても `edinet_code` 付きで保存する。後から有報の `edinet_code`→`sec_code` の対応で結び付けられるようにする。
  - 仕様書・実データで「届出書には常に `secCode` がある」と確かめ、その根拠を self-review に書く。

### R8: 抽出の対象のコンテキストを限定し、実データでよくある2つの形をフィクスチャに含める
次の2つは、要素名だけで事実を集めると行の重複・混入が起き、`invalid_values`（順位の重複）や、役員の二重登録になる。仕様書・タクソノミで確かめ、どのコンテキスト（軸とメンバー、`CurrentYearInstant`／`FilingDateInstant`）を読むかを契約に書き、フィクスチャに入れること。
- **株主総会の前に提出した有報で、役員の表が2つある形**。有報には「提出日現在の役員」と「定時株主総会で議案が承認された後の役員」の2つの表がある場合がある。Sprint 10 の社長の特定にどちらを使うかも含めて、方針を書く。ここでは少なくとも、2つを混ぜず、どちらを保存したかを記録する。
- **議決権の割合での大株主の表を併記する形**。種類株式のある会社などは、所有株式数の割合の表と、議決権の割合の表を併記することがある。
- 役員の「記載順」を「インスタンスでの出現順」とするのは、生成されたインスタンスの並びが保証されていなければ根拠が弱い。提出者別タクソノミの表示リンク（`*_pre.xml`）の順か、インライン XBRL の文書の順など、順の根拠を決めてテストすること。

### R9: B1 の完了条件 C9-3 の期待値が一意に決まらない。フォーカスが外れた時点の即時の確定も扱う
- 今のコードでは、入力欄のフォーカスが外れた時点で `commitNow()` が遅延 0 で確定する（`threshold-field.tsx`）。マウスでは、フォーカスが外れるのはクリックより前の `mousedown` の時点である。したがって、クリックの処理の時点では、書き換えがすでに発行されている場合がある。第2章の9の1は「待っている書き換えを取り消す」としか書いていないので、この場合も詳細の URL が戻らない方法にすると明記すること。
- C9-3（Tab でリンクに移って Enter）では、Tab でフォーカスが外れた時点で 14 が確定し、サーバーの結果（cagr 14）が Enter の前に届くことがある。その場合、リンクの条件は `cagr=14` になり、「同じ詳細（cagr=15）」という期待値は偶然に左右される。
  - 期待値を「Enter を押した時点で表示中の結果の条件の詳細 URL に移り、1,500ms 後も戻らない」に直すこと。
  - または手順を「Tab の後、結果が cagr 14 に更新されるのを待ってから Enter → `/stocks/99992?cagr=14…`」のように一意にすること。

## 推奨（合否に影響しない）
- **ジェネレーターの確認点1（要素名と URL）**:
  - 大株主の `NameMajorShareholders`・`NumberOfSharesHeld`・`ShareholdingRatio` とメンバー `No1MajorShareholdersMember`〜（コンテキスト例 `CurrentYearInstant_No7MajorShareholdersMember`、単位 `shares`）は、公開の iXBRL で実在を確かめられた。
  - 役員の要素名は、この環境では確かめられなかった。
  - 閲覧 URL は `https://disclosure2.edinet-fsa.go.jp/WZEK0040.aspx?S100XXXX…` の形が実在する（末尾が `,,` か `=` かは要確認）。
  - EDINET の閲覧サイトからは、キーが無くても書類の XBRL の ZIP をダウンロードできるはずである。第2章の1の3を「可能なら」ではなく「試みる。取得できたら、フィクスチャはその実データの抜粋から作る」にすることを強く推奨する。
- **確認点2（小数2桁）**: 規則を R6 のとおりにすれば妥当。
- **確認点3（約20回・約3週間）**:
  - 1秒の間隔と ZIP の受信・解凍（有報は1〜数 MB）を考えると、1回で 200 通は楽観的で、100〜150 通程度になりうる。
  - 画面の「1回で約200件」は、固定の数字にせず、直前の実行の実績（`documentsProcessed`）を示す方が誤解が無い。
  - 3月決算の会社が集中する6月末（数日で約2,000通）は、毎日の定期実行だけでは1〜2週間遅れる。CLAUDE.md の見積もりに書いておくこと。
- **確認点4（パンくずと「戻る」の戻り先の違い）**: 受け入れる。「戻る」は直前の画面、パンくずは判定に使った条件の画面、という説明は筋が通っている。C9-4 で「戻る」の後の結果が cagr 14 のものであることを確かめれば十分。
- 定期実行の表示「毎日 24:00（日本時間）」は、「毎日 0:00（日本時間）」の方が自然。0:00 を過ぎてから動くので、実行日（JST）は翌日になる。この点も、一覧の期間の計算とあわせて CLAUDE.md に書くとよい。
- C4-4 で `S8TEST12` を取り下げたとき、siblings に取り下げた書類を出すか出さないかを決めておくこと（出すなら「取り下げ」のラベルを付ける）。
- 取得に失敗し続ける書類（恒常的な 404 など）は毎日再試行され、実行がずっと `partial` になる。Sprint 12 で扱うのでよいが、`details` に書類IDの一覧（上限付き）を残しておくと追いやすい。
- 一覧の日の失敗（500 など）が残っていても、期限による打ち切りでなければ本文の取得に進む。第2章の6の「取り終えていない」の範囲を、そのように明確にしておくとよい。
