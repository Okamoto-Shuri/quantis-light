## ジェネレーターが契約と違えた6点の判断
すべて妥当と判断する。完了条件の意図は損なわれていない。

1. **役員の順はインライン XBRL の文書の順だけ（`_pre.xml` は使わない）**: 妥当。
   - 文書の順は、有報の画面の表の順そのものである。
   - 総会後の表も同じメンバーを使うので、メンバーの順は表の区別の根拠にならない。
   - テストは、コンテキストの定義の順と名前の順を文書の順と逆にしたフィクスチャで、文書の順になることを確かめている。これは契約レビュー（2回目）の「落ちたときの根拠のテスト」を満たす。
2. **総会後の役員の表は、要素名の末尾 `Proposal` で見分ける**: 妥当。
   - フィクスチャ `S100W4KN.htm` には、`NameInformationAboutDirectorsAndCorporateAuditorsProposal`（7件）と `OfficialTitleOrPositionInformationAboutDirectorsAndCorporateAuditorsProposal`（7件）がある。
   - 提出日現在の要素（11件）と同じ `FilingDateInstant_<役員>Member` のコンテキストを使っていることも確かめた。
   - 抽出は、要素名の完全一致で `Proposal` の無い要素だけを読む。
3. **インスタンス（`*.xbrl`）ではなく `*_ixbrl.htm` を読む**: 妥当。
   - EDINET の ZIP の `XBRL/PublicDoc/` にある本文のファイル名は、`0104010_honbun_jpcrp030000-asr-001_E00590-000_2019-03-31_01_2019-06-27_ixbrl.htm` の形である。これは、公開されている転載の URL で確かめた。
   - 実装の正規表現 `^XBRL/PublicDoc/[^/]+_ixbrl\.x?html?$` とも合う。
   - HTML の構文解析で後ろを飲み込まないよう、空要素（`<link:schemaRef/>`）を開始と終了の組に直してから読んでいる。
4. **直近7日の一覧を古い順に取る**: 妥当。元の書類を保存してから、同じ実行の中で取下書・不開示の情報を反映できる。
5. **不開示は解除（"3"）で false に戻す**: 妥当。
   - 契約は「仕様書で違えば仕様書どおり」としていた。
   - 操作日時（`disclosure_changed_at`）の新しい情報だけで更新する実装になっている。
   - 取り下げは戻さない。
6. **1桁の比率 9.6 → `9.60%`**: 契約の規則（最低2桁・丸めない）どおり。
   - フィクスチャ `S100W7OT.htm` の比率は、実際に `decimals="3" scale="-2"` で `9.6` だった。
   - 注記の「有報の記載どおり」とは、桁の見かけが1桁違う。改善提案 m6 に書いた。

self-review の実データの主張で、この環境で確かめられたもの:
- キー無しで `GET https://api.edinet-fsa.go.jp/api/v2/documents.json?date=2025-06-25&type=2` を呼ぶと、**HTTP 200** と `{"StatusCode": 401, ...}` が返った。書類取得 API（`/documents/S100W7OT?type=1`）も **HTTP 200・application/json** だった。
- `https://disclosure2.edinet-fsa.go.jp/WZEK0040.aspx?S100W7OT,,` は HTTP 200。
- フィクスチャ3通の要素名・コンテキスト・`decimals`・`scale` は、上の主張と合っている。

## 改善提案（合格判定には影響しないが推奨）
- **m1（375px）**: 大株主の表では、氏名と住所の列が幅を取る。いちばん重要な「持株比率」が、横スクロールしないと見えない。狭い幅では住所を氏名の下に小さく出すなど、比率の列が最初の画面に入る配分にするとよい。
- **m2（9W007 の見出しの文言）**: 出典の欄の「最新の提出分を使っています」と、大株主の区画の「元の有報の記載を表示しています」が同じ画面に並ぶ。区画の注記で分かるので誤解は小さいが、フォールバックがある銘柄では出典の欄を「最新の提出分: S8TEST62（区画によっては元の有報の記載を表示）」のようにするとよい。
- **m3**: 区画だけが取り込み待ちのときの文言「記載を確かめる書類が取り込み待ちです」に、書類ID（例 S8TEST61）を入れるとよい。全体の取り込み待ちの表示（9W005）と表記がそろう。
- **m4（B1 の修正の体感）**: 待っている書き換えの応答を受けてから詳細へ移るので、クリックから遷移まで dev で約 300ms、prod で約 120ms かかり、その間の反応が無い。応答の遅い回線では、クリックが効いていないように見える。行やカーソルに、待機中を示す表示を出すとよい。
- **m5（性能）**: `annual_report_detail(code)` は、区画のビュー（`annual_report_sections`。CTE が複数回参照されるので実体化する）を全銘柄について計算してから1銘柄に絞っている。4,000 銘柄・9,000 書類の合成データで、1回約 20ms（`annual_reports_summary()` は約 22ms）だった。今の規模では問題ないが、Sprint 10 で条件④をスクリーニングに組み込むときに、同じビューを一覧で使うなら、銘柄で絞れる形にしておくこと。
- **m6（比率の桁）**: 記載が1桁（`9.6`）の比率も `9.60%` と表示し、注記は「有報の記載どおり」となっている。契約の規則どおりだが、利用者が有報の表と見比べたときに桁の違いに気付く可能性がある。記載どおりの桁で出すか、注記の表現を検討してよい。
- **その他**: 対象の事業年度の最新の書類が不開示・取り下げのときは、前の事業年度の有報に切り替わる。これは契約の選び方どおりで、事業年度が見出しに出るので誤解は小さい。ただ、「新しい事業年度の有報が不開示のため、前の事業年度の記載を表示しています」のような一言があるとより親切である。
